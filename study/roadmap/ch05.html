CHAPTER 05

상태 관리 & 데이터 페칭

화면에 보이는 값 하나하나가 전부 같은 종류의 "상태"는 아니다. 서버에 원본이 있는 값을 useState로 직접 들고 있으면 로딩·에러·캐시·경쟁 조건을 전부 손으로 재발명하게 된다. 이 챕터는 상태를 5가지로 분류하는 법, TanStack Query로 서버 상태를 다루는 법, Zustand로 클라이언트 전역 상태를 다루는 법, 그리고 URL·폼 상태까지 각자 제자리를 찾아준다.

TanStack Query v5 Zustand 캐시 생명주기 낙관적 업데이트 URL 상태

이 챕터가 끝나면 다음 질문에 답할 수 있다. 이 값은 전역 상태로 만들어야 하나, 아니면 그냥 서버에서 다시 받아오면 되나? useEffect로 직접 fetch하면 구체적으로 뭐가 위험한가? staleTime과 gcTime은 뭐가 다른가? 낙관적 업데이트는 실패했을 때 어떻게 원상복구되나? Zustand는 Context와 뭐가 다른가?

§1상태를 분류하라

"상태 관리 라이브러리 뭐 쓸까요?"라는 질문은 순서가 틀렸다. 먼저 물어야 할 건 "이 값은 어떤 상태(state)인가?"다. 종류가 다른 상태를 같은 도구로 다루면 코드가 꼬인다. 서버에 원본이 있는 값을 Zustand 전역 스토어에 넣고 새로고침마다 수동으로 동기화하는 코드, 페이지 번호를 useState에만 넣어서 새로고침하면 1페이지로 리셋되는 코드 — 전부 상태 분류를 안 해서 생기는 문제다.

이 챕터의 핵심 문장 대부분의 "전역 상태 문제"는 사실 서버 상태 문제다. Redux/Zustand로 전역 스토어를 만들기 전에, 그 값이 애초에 서버에서 오는 데이터는 아닌지부터 확인하라.

5가지 상태 분류

① 서버 상태 (Server State)

원본이 서버 DB에 있고, 프론트는 그 사본을 잠깐 들고 있을 뿐인 값. 유저 정보, 게시글 목록, 주문 내역. 다른 사용자가 바꾸면 내 화면의 사본은 stale(오래된 값)이 된다. → TanStack Query 등 서버 상태 라이브러리.

② 클라이언트 전역 상태

서버에는 없고 브라우저 안에서만 의미 있는데, 여러 컴포넌트 트리에서 공유해야 하는 값. 다크모드 여부, 로그인 모달 열림 여부, 장바구니 UI 임시 상태. → Zustand, Context 등.

③ URL 상태

새로고침해도 유지되어야 하고, 링크로 공유 가능해야 하는 값. 검색어, 필터, 현재 페이지 번호, 탭 선택. → URLSearchParams, 라우터의 쿼리 파라미터.

④ 폼 상태

사용자가 입력 중이라 아직 제출 전인 값. 유효성 검사, 더티(dirty) 여부, 제출 중 여부까지 딸려온다. → useState 또는 폼 전용 라이브러리.

⑤ 로컬 UI 상태

딱 그 컴포넌트 안에서만 의미 있는 값. 아코디언 열림 여부, 호버 여부, 입력창 포커스 여부. → 그냥 useState.

§2useEffect로 직접 fetch할 때 생기는 문제

useEffect로 fetch를 직접 호출하는 코드는 튜토리얼에서 흔히 보이지만, 실무 규모로 가면 아래 5가지 문제가 거의 반드시 터진다[4]. 아래 라이브 예제는 전부 지연 시간이 있는 가짜 API(setTimeout 기반)로 문제를 실제로 재현한 것이다. 코드를 고쳐서 직접 실행해봐도 된다.

문제 1 — 로딩/에러 처리의 반복(보일러플레이트)

데이터를 가져오는 컴포넌트마다 loading, error, data 3개의 useState와 try/catch(또는 .then/.catch) 로직을 매번 새로 쓰게 된다. 아래 예제는 사용자 정보와 게시글, 완전히 다른 데이터를 가져오는데도 구조가 토씨 하나 안 다르게 반복된다.

무슨 일이 일어나는가

UserBox와 PostBox는 서로 다른 데이터를 가져오지만, 로딩·에러 처리 골격이 완전히 동일하다. 컴포넌트가 10개, 20개가 되면 이 골격을 20번 복사-붙여넣기 하게 된다.

  • useState(true) — 로딩 상태를 각자 따로 관리
  • .finally(() => setLoading(false)) — 성공/실패 모두에서 로딩 해제, 이것도 매번 반복
  • 20% 확률로 실패하도록 만들어서 ▶ 실행을 몇 번 눌러보면 에러 분기도 볼 수 있다

문제 2 — 레이스 컨디션(race condition)

사용자가 id=1을 선택했다가 재빨리 id=2로 바꾸면, 두 개의 요청이 동시에 날아간다. 만약 id=1의 응답이 더 늦게 도착하면, 이미 id=2를 보고 있는 화면을 id=1의 데이터로 덮어써 버린다. 이건 눈에 보이는 버그다 — 아래에서 직접 재현해보자.

sequenceDiagram
  participant U as 사용자
  participant C as 컴포넌트
  participant API as 서버(가짜)
  U->>C: 사용자 1 선택 (응답 2.5s 걸림)
  C->>API: GET /user/1
  U->>C: 0.5s 뒤 사용자 2 선택 (응답 0.3s)
  C->>API: GET /user/2
  API-->>C: user/2 응답 도착 (0.3s 후)
  C->>C: 화면에 "사용자 2" 표시 (정답)
  API-->>C: user/1 응답 도착 (2.5s 후, 더 늦게)
  C->>C: 가드가 없으면 화면을 "사용자 1"로 덮어씀 (오답!)
그림 2. 나중에 보낸 요청이 먼저 도착하면, 가드 없는 useEffect는 화면을 잘못된 데이터로 덮어쓴다.

무슨 일이 일어나는가

UserPanel의 useEffect는 응답이 오면 무조건 setUser를 호출한다. 응답이 도착했을 때 사용자가 이미 다른 id를 선택했는지는 확인하지 않는다.

  • id가 작을수록(1) 응답을 일부러 느리게(2.5초) 만들었다
  • "사용자 1" 클릭 후 0.5초 안에 "사용자 2" 클릭 → 화면은 잠깐 2를 보여주다가 2.5초 뒤 다시 1로 바뀐다
  • 현재 선택(userId)과 화면에 표시된 데이터(user.id)가 다르면 빨간 글씨로 경고를 표시했다
  • 해결책: 클린업 함수에서 "이 요청은 취소됐다" 플래그를 세우거나 AbortController로 실제 요청을 취소한다[3]. TanStack Query는 이걸 자동으로 해준다(§3).

문제 3 & 4 — 중복 요청과 캐시 없음

같은 데이터를 필요로 하는 컴포넌트가 화면에 두 번 있으면, useEffect는 그 사실을 모르기 때문에 네트워크 요청도 두 번 나간다[6]. 그리고 컴포넌트가 언마운트됐다가 다시 마운트되면 방금 받았던 데이터인데도 처음부터 다시 요청한다 — 캐시가 없기 때문이다.

무슨 일이 일어나는가

배지 A와 배지 B는 같은 사용자 1의 데이터가 필요하지만, 서로의 존재를 모른다. 각자 자기 useEffect에서 fetch를 호출한다.

  • networkCallCount는 실제로 함수가 몇 번 호출됐는지 세는 모듈 전역 카운터(데모 편의상 넣은 것이지 실무 패턴은 아니다)
  • 같은 사용자 1인데 요청 번호(callNo)가 배지마다 다르게 찍힌다 — 중복 요청
  • "다시 그리기"를 누르면 이미 받았던 데이터인데도 networkCallCount가 또 올라간다 — 캐시 없음

문제 5 — 언마운트 후 setState 시도

느린 요청이 진행 중인데 사용자가 다른 화면으로 이동해서 컴포넌트가 언마운트되면 어떻게 될까? 이미 사라진 컴포넌트를 위해 만들어졌던 콜백은 그래도 실행된다. 가드가 없으면 이미 아무도 안 읽는 상태를 계속 업데이트하려 시도하는 낭비 작업, 혹은 외부 리소스(타이머, 구독)를 정리하지 않는 메모리 누수로 이어질 수 있다.

무슨 일이 일어나는가

staleCallbackCount는 "컴포넌트가 이미 사라진 뒤에도 실행된 콜백"의 수를 센다. 진짜 앱이었다면 이 콜백이 이미 정리된 타이머를 다시 만들거나, 존재하지 않는 DOM에 접근하려다 에러를 낼 수도 있다.

  • "지금 언마운트하기" → mounted를 false로, SlowLoader가 화면에서 사라짐
  • 2초 뒤 fetch가 resolve되면서 staleCallbackCount가 증가 — 하지만 컴포넌트는 이미 없다
  • 클린업으로 "취소됨" 플래그를 두고 if (cancelled) return;으로 막는 게 정석 대응이다
그래서 이 5가지 문제(반복 코드, 레이스 컨디션, 중복 요청, 캐시 없음, 언마운트 후 콜백)를 전부 손으로 해결하려면 매 컴포넌트마다 AbortController, ref 플래그, 캐시 Map을 직접 짜야 한다. React 공식 문서도 데이터 페칭에는 프레임워크나 캐싱 라이브러리를 권장한다[5]. 다음 절부터는 TanStack Query가 이 문제들을 어떻게 구조적으로 없애는지 본다.

§2TanStack Query v5 개념

TanStack Query[10](구 React Query)는 "서버 상태 전용" 라이브러리다. 클라이언트 전역 상태 도구가 아니다 — 서버에서 받아온 데이터를 캐싱하고, 언제 다시 받아와야 하는지 규칙을 정하고, 로딩/에러 상태를 표준화해준다.

QueryClient와 useQuery

QueryClient는 모든 쿼리 캐시를 담는 저장소 하나다. 앱 최상단에서 한 번 만들어 QueryClientProvider로 감싸면, 그 밑의 모든 컴포넌트가 useQuery로 캐시를 공유한다[11].

src/main.tsx
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 30_000 }, // 모든 쿼리의 기본 staleTime
  },
});

function Root() {
  return (
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  );
}

queryKey — 캐시의 주소

queryKey는 배열이다. 같은 키를 쓰는 useQuery 호출은 전부 같은 캐시 항목을 공유한다 — 이게 §2의 "중복 요청" 문제가 구조적으로 사라지는 이유다. 키가 다르면(예: ["user", 1] vs ["user", 2]) 별개의 캐시로 취급한다[12].

src/hooks/useUser.ts
import { useQuery } from "@tanstack/react-query";

function useUser(id: string) {
  return useQuery({
    queryKey: ["user", id],       // 이 배열이 캐시의 "주소"다
    queryFn: async () => {
      const res = await fetch(`/api/users/${id}`);
      if (!res.ok) throw new Error("사용자 조회 실패");
      return res.json();
    },
  });
}

staleTime vs gcTime

이 둘을 헷갈리면 캐시 동작을 예측할 수 없다. 이름이 비슷하지만 하는 일이 완전히 다르다.

옵션기본값(v5)의미
staleTime0ms데이터가 "신선하다(fresh)"고 간주되는 시간. 이 시간 안에는 재요청하지 않고 캐시를 그대로 보여준다.
gcTime5분구독하는 컴포넌트가 0개가 된 뒤 캐시를 메모리에서 실제로 지우기까지 기다리는 시간(v4의 cacheTime과 같은 개념, v5에서 이름이 바뀌었다).

staleTime이 0이라는 기본값은 "항상 최신 상태를 우선한다"는 뜻이다[13]. 즉 기본 설정에서는 컴포넌트가 마운트되거나 창이 다시 포커스될 때마다 백그라운드 리페치가 일어날 수 있다 — 화면이 깜빡이며 로딩으로 돌아가지는 않고, 캐시된 값을 계속 보여주면서 뒤에서 갱신한다.

캐시 상태 머신

쿼리 하나는 시간이 지나며 fresh → stale → (재요청 트리거 시) fetching 을 오간다. 구독자가 없어지면 inactive로 빠지고, gcTime이 지나면 완전히 삭제된다.

stateDiagram-v2
  [*] --> fetching : 첫 useQuery 호출
  fetching --> fresh : 성공, staleTime 동안 유지
  fetching --> paused : 네트워크 끊김
  paused --> fetching : 네트워크 복귀
  fresh --> stale : staleTime 경과
  stale --> fetching : 리페치 트리거
  stale --> inactive : 구독 컴포넌트 0개
  fresh --> inactive : 구독 컴포넌트 0개
  inactive --> [*] : gcTime 경과, 캐시 삭제
  inactive --> fetching : gcTime 이내 재구독
그림 3. TanStack Query 캐시 생명주기. 출처: TanStack Query 공식 문서의 Important Defaults를 도식화[13].

리페치가 자동으로 일어나는 시점

기본 설정에서 TanStack Query는 아래 상황에 stale한 쿼리를 자동으로 다시 요청한다[18]. 하나도 손으로 구현할 필요가 없다.

  • 윈도우 포커스 — 다른 탭에 갔다가 이 탭으로 돌아왔을 때(refetchOnWindowFocus)
  • 네트워크 재연결 — 오프라인이었다가 다시 온라인이 됐을 때(refetchOnReconnect)
  • 컴포넌트 마운트 — 같은 queryKey를 쓰는 컴포넌트가 새로 마운트될 때(refetchOnMount)

§3useQuery 실전

실제 라이브러리의 useQuery는 아래처럼 쓴다. 이건 그대로 실행되는 코드가 아니라 정적 예시다 — 이 챕터의 플레이그라운드는 외부 패키지를 import할 수 없으므로, 바로 아래에서 원리를 그대로 옮긴 40줄짜리 미니 버전을 직접 만들어 라이브로 실행해본다.

src/components/UserCard.tsx
import { useQuery } from "@tanstack/react-query";

function UserCard({ id }: { id: string }) {
  const { data, isPending, isError, error } = useQuery({
    queryKey: ["user", id],
    queryFn: () => fetch(`/api/users/${id}`).then((r) => r.json()),
    staleTime: 60_000, // 1분간은 신선하다고 간주 — 재요청 안 함
    gcTime: 5 * 60_000,
  });

  if (isPending) return <p>로딩 중…</p>;
  if (isError) return <p>에러: {error.message}</p>;
  return <p>{data.name}</p>;
}
v5에서 바뀐 이름 v4의 isLoading은 "데이터가 없고 로딩 중"을 뜻했는데, v5는 이를 isPending으로 이름을 바꾸고 isLoading은 isPending && isFetching의 파생값으로 재정의했다. 새 코드에서는 isPending을 쓴다.

원리 재현 — 미니 useQuery 직접 만들기

아래는 캐시 Map + staleTime + 중복 요청 제거(dedupe)만 구현한 학습용 버전이다. 실제 TanStack Query는 이보다 훨씬 많은 기능(재시도, 페이지네이션, 무효화, devtools…)을 갖고 있지만, 핵심 아이디어는 이 40줄 안에 다 있다.

무슨 일이 일어나는가

queryCache는 key → { data, error, promise, updatedAt }를 담는 Map이다. 요청 중인 promise 자체를 캐시에 저장해두는 게 중복 요청 제거의 핵심이다.

  • isFresh — Date.now() - updatedAt < staleTime이면 재요청하지 않는다
  • alreadyFetching — 이미 같은 key로 요청이 나가 있으면(promise가 있으면) 또 보내지 않는다 → 이게 문제 3(중복 요청)의 해결책
  • listeners Map은 같은 key를 구독하는 모든 컴포넌트에게 "데이터 도착"을 알려서 리렌더시킨다
  • 패널 A, B 둘 다 같은 key="price"를 쓰지만 네트워크 호출은 1번만 나가는 걸 카운터로 확인한다

§4변경(Mutation)

조회는 useQuery, 변경(생성/수정/삭제)은 useMutation이다. useMutation은 자동 캐싱이나 재요청을 하지 않는다 — 대신 성공/실패 콜백에서 캐시를 직접 조작할 수 있는 훅을 제공한다.

src/hooks/useToggleTodo.ts
import { useMutation, useQueryClient } from "@tanstack/react-query";

function useToggleTodo() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (vars: { id: string; done: boolean }) =>
      fetch(`/api/todos/${vars.id}`, {
        method: "PATCH",
        body: JSON.stringify({ done: vars.done }),
      }),

    // 1. 서버 응답 전에 캐시를 먼저 낙관적으로 바꾼다
    onMutate: async (vars) => {
      await queryClient.cancelQueries({ queryKey: ["todos"] });
      const previous = queryClient.getQueryData(["todos"]);
      queryClient.setQueryData(["todos"], (old) =>
        old?.map((t) => (t.id === vars.id ? { ...t, done: vars.done } : t))
      );
      return { previous }; // onError에서 쓸 롤백용 스냅샷
    },

    // 2. 실패하면 저장해둔 스냅샷으로 되돌린다
    onError: (_err, _vars, context) => {
      queryClient.setQueryData(["todos"], context?.previous);
    },

    // 3. 성공/실패 관계없이 서버 진짜 값으로 다시 확인한다
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ["todos"] });
    },
  });
}

invalidateQueries

invalidateQueries({ queryKey: [...] })는 해당 키의 캐시를 stale로 표시하고, 지금 화면에 구독 중이면 즉시 리페치를 트리거한다[14]. "서버 값이 바뀌었을 테니 확인해라"라는 신호를 보내는 방법이다.

낙관적 업데이트 흐름

낙관적 업데이트(optimistic update)는 체크박스 클릭처럼 실패 확률이 낮은 작업에서 체감 속도를 크게 올린다. 흐름은 항상 onMutate → (성공|실패) → onSettled 순이다.

sequenceDiagram
  participant UI as 화면
  participant M as useMutation
  participant QC as QueryClient 캐시
  participant S as 서버
  UI->>M: mutate(변경값)
  M->>QC: onMutate — 캐시를 낙관적으로 미리 변경
  QC-->>UI: 즉시 새 값으로 다시 렌더링
  M->>S: 실제 요청 전송
  alt 성공
    S-->>M: 200 OK
    M->>QC: onSettled — invalidateQueries로 서버값 재확인
  else 실패
    S-->>M: 에러 응답
    M->>QC: onError — onMutate에서 저장한 스냅샷으로 롤백
    QC-->>UI: 롤백된 값으로 다시 렌더링
  end
그림 4. 낙관적 업데이트의 표준 흐름 — 성공하든 실패하든 onSettled는 항상 실행된다[15].

원리 재현 — 낙관적 업데이트 + 롤백 직접 만들기

무슨 일이 일어나는가

useMiniMutation은 실제 useMutation과 같은 모양의 onMutate/onError/onSettled 콜백을 받는다. 체크박스를 클릭하면 서버 응답을 기다리지 않고 즉시 화면이 바뀐다.

  • onMutate에서 변경 전 todos를 prevTodos로 스냅샷 떠두고, 낙관적으로 상태를 바꾼다
  • "다음 저장은 실패하게 만들기"를 켜면 fakeSaveTodo가 항상 reject한다
  • 실패하면 onError가 ctx.prevTodos로 되돌린다 — 0.9초 뒤 체크가 저절로 풀리는 게 롤백이다

§5페이지네이션 & 무한 스크롤

페이지를 넘길 때 이전 데이터가 사라지고 로딩 스피너가 잠깐 뜨는 깜빡임은 placeholderData로 없앨 수 있다. UI 구현(가상 스크롤, 무한 스크롤 리스트 최적화)의 자세한 내용은 ch08 성능 최적화에서 다루고, 여기서는 TanStack Query 쪽 API만 짚는다.

placeholderData로 깜빡임 없애기

v5는 keepPreviousData를 boolean 옵션이 아니라 placeholderData에 넘기는 함수로 바꿨다. 페이지가 바뀌어도 새 데이터가 도착할 때까지 이전 페이지 데이터를 계속 보여준다[16].

src/hooks/usePage.ts
import { useQuery, keepPreviousData } from "@tanstack/react-query";

function usePage(page: number) {
  return useQuery({
    queryKey: ["items", page],
    queryFn: () => fetchItems(page),
    placeholderData: keepPreviousData, // 새 페이지 로딩 중에도 이전 페이지를 계속 보여준다
  });
}

useInfiniteQuery

무한 스크롤은 페이지가 아니라 "다음 페이지를 가리키는 커서"를 계속 쌓아나가는 구조다. v5부터 initialPageParam을 명시적으로 지정해야 한다[17].

src/hooks/useInfiniteItems.ts
import { useInfiniteQuery } from "@tanstack/react-query";

function useInfiniteItems() {
  return useInfiniteQuery({
    queryKey: ["items"],
    queryFn: ({ pageParam }) => fetchItems({ cursor: pageParam }),
    initialPageParam: 0,
    getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,
  });
}

// 사용: data.pages는 지금까지 받아온 페이지 배열
// fetchNextPage()를 호출하면 다음 페이지를 이어붙인다

§6클라이언트 전역 상태 — Zustand

§1에서 걸러내고 남은 "서버에는 없지만 여러 트리에서 공유해야 하는" 상태가 진짜 클라이언트 전역 상태다. Zustand[19]는 Context Provider 없이 훅 하나로 스토어를 만드는 라이브러리다.

store 생성, selector, 불변 업데이트

src/store/cartStore.ts
import { create } from "zustand";

interface CartItem { id: string; qty: number }
interface CartState {
  items: CartItem[];
  addItem: (item: CartItem) => void;
  clear: () => void;
}

export const useCartStore = create<CartState>()((set) => ({
  items: [],
  addItem: (item) =>
    set((state) => ({ items: [...state.items, item] })), // 불변 업데이트: 새 배열을 만든다
  clear: () => set({ items: [] }),
}));

// 컴포넌트에서: selector로 필요한 값만 구독한다
function CartBadge() {
  const count = useCartStore((state) => state.items.length);
  return <span>{count}</span>;
}

selector((state) => state.items.length)가 핵심이다. 이 컴포넌트는 items.length가 바뀔 때만 리렌더링된다 — 스토어의 다른 값이 바뀌어도 무관하다. Zustand는 기본적으로 selector 결과를 얕은 비교가 아니라 Object.is로 비교하므로, 객체/배열을 새로 만들어 반환하는 selector는 매번 다른 참조라 리렌더링을 유발할 수 있다는 점은 주의한다.

미들웨어 — persist, devtools

Zustand의 미들웨어는 store 생성 함수를 감싸는 함수다. persist는 localStorage에 자동 저장/복원하고, devtools는 Redux DevTools 확장에서 상태 변화를 볼 수 있게 한다[20][21].

src/store/cartStore.ts
import { create } from "zustand";
import { persist, devtools } from "zustand/middleware";

export const useCartStore = create<CartState>()(
  devtools(
    persist(
      (set) => ({
        items: [],
        addItem: (item) => set((state) => ({ items: [...state.items, item] })),
        clear: () => set({ items: [] }),
      }),
      { name: "cart-storage" } // localStorage 키 이름
    )
  )
);

리렌더링 범위Context 값이 바뀌면 그 Context를 구독하는 모든 컴포넌트가 리렌더링(공식 문서 참고[9])selector 단위로 필요한 값만 구독 → 세밀한 리렌더 제어
보일러플레이트action type, reducer, dispatch, Provider 다 직접 작성[8]store 객체 하나로 끝

원리 재현 — 미니 Zustand 직접 만들기

Zustand의 핵심은 두 가지뿐이다. ① 외부 스토어 하나(구독자 Set + 상태), ② React 18의 useSyncExternalStore로 그 외부 스토어를 리액트 렌더링에 연결하는 것[7]. 아래는 그 둘만으로 만든 create()다.

무슨 일이 일어나는가

create는 listeners Set과 state 변수를 클로저로 감싸 반환한다. setState가 호출되면 state를 새 객체로 교체하고(불변 업데이트) 모든 리스너를 호출한다.

  • useSyncExternalStore(subscribe, getSnapshot) — React 스케줄러 밖에서 바뀌는 값을 안전하게 구독하는 공식 API
  • useStore(selector)는 매 렌더마다 selector(getState())를 getSnapshot으로 넘긴다
  • CountView는 count만, OtherView는 other만 구독 — "other 토글"을 눌러도 CountView의 렌더 횟수는 그대로다

§7언제 무엇을 쓰나

도구분류언제 쓰나장점단점
TanStack Query서버 상태서버 데이터를 조회/변경하는 모든 곳캐시·재시도·리페치 전부 내장, 보일러플레이트 최소서버 상태 전용 — 클라이언트 전역 상태에는 안 맞음

Context + useReducer클라이언트 전역거의 안 바뀌는 값(테마, 로케일), 작은 규모추가 설치 불필요, React 표준 패턴값이 바뀌면 구독자 전체 리렌더, action/reducer 보일러플레이트

Jotai클라이언트 전역상태를 작은 단위(atom)로 잘게 쪼개고 싶을 때atom 단위로 자동 리렌더 최적화, 파생 상태 조합이 쉬움atom이 많아지면 전체 그림 파악이 어려워질 수 있음
과설계 경고 전역 상태 라이브러리부터 고르지 마라. 십중팔구는 §1 결정 트리를 따라가면 "이거 그냥 TanStack Query가 캐싱해줄 서버 데이터잖아" 또는 "이거 그냥 이 컴포넌트 안에서만 쓰는 로컬 상태잖아"로 끝난다. 정말로 여러 트리가 공유하는 클라이언트 상태가 남았을 때만 Zustand/Redux/Jotai를 고려한다.

§8폼 상태와 URL 상태

제어 컴포넌트의 한계

ch03에서 배운 제어 컴포넌트(controlled component) 패턴은 필드 하나짜리 폼엔 충분하다. 하지만 필드가 20개인 회원가입 폼에서 글자 하나 칠 때마다 useState 20개 중 하나가 바뀌고, 그때마다 폼 전체가 리렌더링되면 느려진다. 이건 이 챕터가 아니라 폼 전용 라이브러리(react-hook-form 등)가 다루는 영역이지만, 원인은 알아둘 필요가 있다 — 모든 입력값을 React state로 만들면, 모든 키 입력이 리렌더를 유발한다.

URLSearchParams로 필터·페이지 상태 관리

useState로 필터를 관리하면 새로고침 시 다 날아가고, 그 화면 링크를 동료에게 공유해도 필터가 재현되지 않는다. URLSearchParams[1]는 쿼리스트링을 다루는 표준 웹 API고, React Router 같은 라우터의 useSearchParams도 내부적으로 이걸 감싼 것이다.

URL 상태의 이점 ① 새로고침해도 필터가 유지된다. ② 링크를 복사해서 공유하면 상대방도 같은 필터/페이지를 본다. ③ 브라우저 뒤로가기[2]가 "필터 변경 취소"처럼 자연스럽게 동작한다.

무슨 일이 일어나는가

이 데모는 실제 브라우저 주소창 대신, 같은 원리를 URLSearchParams + 스택 배열로 재현한 것이다(플레이그라운드가 iframe이라 실제 주소창을 바꿀 수 없다).

  • new URLSearchParams() 뒤 .set(key, value)로 쿼리스트링을 조립한다
  • .toString()이 category=notice&page=2 같은 문자열을 만들어준다
  • 필터가 바뀔 때마다 히스토리 스택에 쌓이고, "뒤로가기 시뮬레이션"으로 이전 필터 상태를 복원한다 — 실제 브라우저의 popstate와 같은 개념
src/hooks/useFilterParams.ts (React Router 예시)
import { useSearchParams } from "react-router-dom";

function ProductList() {
  const [searchParams, setSearchParams] = useSearchParams();
  const category = searchParams.get("category") ?? "all";
  const page = Number(searchParams.get("page") ?? "1");

  function setCategory(next: string) {
    setSearchParams((prev) => {
      prev.set("category", next);
      prev.set("page", "1"); // 카테고리 바뀌면 1페이지로
      return prev;
    });
  }

  // category, page를 그대로 useQuery의 queryKey로 넘기면
  // 서버 상태(§2)와 URL 상태(§8)가 자연스럽게 연결된다
  // useQuery({ queryKey: ["products", category, page], ... })
}

§9이해도 점검

  • 어떤 값이 주어졌을 때 5가지 상태 분류(서버/클라이언트 전역/URL/폼/로컬 UI) 중 어디에 속하는지 결정 트리를 따라 판단할 수 있다.
  • useEffect 직접 fetch에서 레이스 컨디션이 왜 발생하는지, 어떤 조건에서 재현되는지 설명할 수 있다.
  • staleTime과 gcTime의 차이를 코드 없이 말로 설명할 수 있다.
  • queryKey가 왜 캐시의 "주소" 역할을 하는지, 같은 키를 쓰는 컴포넌트 두 개가 왜 요청을 1번만 보내는지 설명할 수 있다.
  • 낙관적 업데이트의 onMutate → onError → onSettled 흐름과 각 단계의 역할을 그림 없이 순서대로 말할 수 있다.
  • cursor 기반 페이지네이션이 offset 기반보다 나은 상황을 예 하나로 들 수 있다.
  • Zustand store에서 selector를 안 쓰고 전체 state를 구독했을 때 생기는 문제를 설명할 수 있다.
  • Context+useReducer와 Zustand 중 어느 쪽을 쓸지, 상태가 얼마나 자주 바뀌는지를 기준으로 판단할 수 있다.
  • 필터/페이지 상태를 useState 대신 URL에 저장했을 때 얻는 구체적인 이점 2가지 이상을 말할 수 있다.
