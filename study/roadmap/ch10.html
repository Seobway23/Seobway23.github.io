§1왜 테스트하나

기능을 하나 고치고 나면 "혹시 다른 데가 깨지지 않았을까"라는 불안이 남는다. 코드가 커질수록 사람이 매번 화면을 손으로 눌러보며 확인하는 건 불가능해진다. 테스트는 이 확인 작업을 코드로 대신 시키는 것이다.

회귀를 막는 안전망

회귀(regression)는 소프트웨어가 시간이 지나며 커질 때 가장 자주 일어나는 사고 유형이다. A 기능을 고치다가 전혀 관련 없어 보이는 B 기능이 죽는 식이다. 테스트가 있으면 코드를 바꾼 직후 자동으로 "예전에 보장했던 동작들이 여전히 맞는지"를 몇 초 안에 확인할 수 있다. 사람이 매번 모든 화면을 순회하며 눈으로 확인하는 것보다 훨씬 빠르고 훨씬 안 빼먹는다.

리팩터링을 가능하게 하는 문서

리팩터링(refactoring)은 테스트 없이는 사실상 도박이다. 테스트가 없는 코드를 고치면 "고치기 전과 똑같이 동작하는지"를 증명할 방법이 없어서, 결국 아무도 그 코드를 건드리지 않으려는 코드(= 레거시)가 된다. 잘 만든 테스트는 코드가 무엇을 보장해야 하는지를 실행 가능한 형태로 적어 둔 문서 역할도 한다. 함수 이름과 주석은 거짓말을 할 수 있지만, 통과하는 테스트는 "적어도 이 입력에 대해서는 이 출력이 나온다"는 걸 실제로 검증한 상태로 남는다.

테스트 피라미드 vs 테스트 트로피

테스트는 범위에 따라 크게 세 층으로 나뉜다. 단위 테스트(unit test)는 함수나 컴포넌트 하나를 다른 것과 분리해 검증한다. 통합 테스트(integration test)는 여러 모듈이 실제로 맞물려 동작하는지 확인한다. E2E 테스트는 진짜 브라우저에서 사용자의 전체 흐름을 그대로 재현한다.

전통적인 "테스트 피라미드" 모델은 단위 테스트를 가장 많이, E2E를 가장 적게 만들라고 말한다. 반면 프론트엔드 진영에서 널리 쓰이는 "테스트 트로피" 모델은 정적 분석(타입 검사·린트)을 기본 바닥에 깔고, 그 위에 통합 테스트를 가장 두껍게 둔다[1]. 이유는 단순하다. UI 컴포넌트는 대부분 다른 컴포넌트·훅·상태와 얽혀서 의미를 가지기 때문에, 각 조각을 완전히 고립시켜 단위 테스트만 촘촘히 쌓아도 "실제로 화면에서 잘 동작하는지"는 잘 보장되지 않는다.

그림 1. 피라미드는 단위 테스트를 가장 두껍게, 트로피는 통합 테스트를 가장 두껍게 쌓는다. 너비는 "이 층에 투자하는 상대적 비중"을 뜻하며 절대적인 개수 비율은 아니다. 출처: Testing Library, Guiding Principles[1]

프론트엔드에서 통합 테스트 비중이 높은 이유

버튼 컴포넌트 하나를 완전히 고립시켜 "클릭하면 onClick이 호출된다"만 확인하는 단위 테스트는 실제 버그를 거의 못 잡는다. 실무에서 나는 버그는 대부분 "이 컴포넌트와 저 훅이 만났을 때", "폼 상태와 API 응답이 합쳐졌을 때"처럼 조합 지점에서 발생한다. 그래서 React 컴포넌트를 테스트할 때는 자식 컴포넌트까지 실제로 렌더링한 상태에서, 사용자가 클릭·입력하는 흐름을 그대로 재현하는 통합 테스트 비중이 자연스럽게 높아진다. 이 접근은 §4에서 다루는 React Testing Library의 철학과 그대로 이어진다.

구분속도실제 버그 포착력실패 시 원인 특정
단위 테스트매우 빠름 (밀리초)낮음 — 조합 지점의 버그를 놓친다쉬움 — 함수 하나만 본다
통합 테스트빠름 (수십~수백 밀리초)높음 — 실제 사용 흐름과 가깝다보통 — 여러 모듈이 얽혀 있다
E2E 테스트느림 (초 단위)가장 높음 — 브라우저·네트워크까지 포함어려움 — 원인 후보가 가장 많다
요약테스트는 회귀 방지 + 리팩터링 안전망 + 실행 가능한 문서 세 가지 역할을 한다. 프론트엔드에서는 단위 테스트보다 통합 테스트에 더 무게를 싣는 편이 실제 버그를 더 많이 잡는다.

§2테스트의 기본 문법

Vitest, Jest, Playwright 등 거의 모든 JS 테스트 도구는 같은 뼈대 문법을 공유한다. 이 뼈대를 먼저 익히면 어떤 러너를 쓰든 코드를 그대로 읽을 수 있다.

describe / it / expect 구조

describe(이름, 함수)는 관련 있는 테스트들을 하나의 그룹으로 묶는 역할만 한다(실행에는 영향을 주지 않는다). it(이름, 함수) — test라는 이름으로도 쓴다 — 는 "검증 가능한 동작 하나"를 정의한다. 그 안에서 expect(실제값)에 .toBe(), .toEqual() 같은 매처(matcher)를 이어 붙여서 "이 값이 이래야 한다"는 단언을 적는다. 매처가 조건을 만족하지 않으면 에러를 던지고(throw), 테스트 러너는 그 에러를 잡아서 해당 테스트를 실패로 기록한다.

AAA 패턴

좋은 테스트 본문은 대부분 세 부분으로 나뉜다. Arrange(준비) — 테스트에 필요한 데이터와 상태를 만든다. Act(실행) — 검증하려는 동작을 실제로 수행한다. Assert(단언) — 결과가 기대와 같은지 확인한다. 이 순서를 지키면 테스트 하나가 "무엇을, 어떻게 했더니, 무엇이 나와야 하는가"를 한눈에 읽히게 만든다. 세 단계를 뒤섞거나 한 테스트 안에서 여러 개의 서로 다른 행동을 검증하면, 실패했을 때 어느 부분이 문제인지 찾기 어려워진다.

좋은 테스트 이름

테스트 이름은 함수 이름이 아니라 "어떤 상황에서 무엇을 해야 하는가"를 문장으로 서술해야 한다. it('sum')보다 it('두 수를 더하면 합을 반환한다')가 낫고, 더 나아가 it('빈 배열을 넘기면 0을 반환한다')처럼 경계 조건을 이름에 명시하면 테스트 목록만 봐도 이 코드가 어떤 상황들을 다루는지 문서처럼 읽힌다. 테스트가 실패했을 때도 러너가 출력하는 이름만으로 "무엇이 깨졌는지"를 바로 알 수 있어야 한다.

무슨 일이 일어나는가

실제 테스트 러너(Vitest, Jest)는 내부적으로 크게 복잡하지 않다. it은 함수를 실행해보고 예외가 나는지 안 나는지만 보고, expect().toBe()는 "값이 다르면 에러를 던지는" 함수일 뿐이다. 아래 코드는 그 핵심 아이디어만 60줄 이하로 직접 구현한 것이다. 실행 버튼을 눌러 통과하는 테스트와 일부러 실패시킨 테스트가 콘솔에 각각 어떻게 찍히는지 확인해 보자.

  • expect(actual) — 매처 객체를 돌려준다.
  • .toBe(expected) — === 비교, 다르면 에러를 던진다.
  • it(name, fn) — fn()을 실행하고 예외 여부로 PASS/FAIL을 콘솔에 찍는다.
  • 두 번째 테스트는 일부러 틀린 기대값을 적어서 FAIL이 어떻게 보이는지 보여준다.
실제 러너와의 차이실제 Vitest/Jest는 여기에 beforeEach/afterEach(각 테스트 전후 훅), 비동기 it, 스냅샷, 목(mock) 추적, 병렬 실행, 예쁜 diff 출력 같은 기능이 훨씬 많이 얹혀 있다. 하지만 뼈대는 방금 만든 것과 같다 — "함수를 실행하고, 예외가 안 나면 통과".

§3Vitest

왜 Vite 프로젝트에서 Vitest인가

Vitest는 Vite와 설정을 그대로 공유한다. Vite가 이미 처리하고 있는 alias, 환경변수, JSX/TS 변환 같은 것들을 테스트에서도 똑같이 쓸 수 있어서, Vite로 빌드하는 프로젝트라면 별도의 변환 설정을 다시 만들 필요가 없다. Jest는 Babel 기반의 독립된 변환 파이프라인을 쓰기 때문에, Vite 프로젝트에 Jest를 얹으면 사실상 같은 일을 하는 설정을 두 벌 유지해야 한다. Vitest는 API도 대부분 Jest와 호환되도록 설계돼서(describe/it/expect/vi) 마이그레이션 비용도 낮다[2].

설치와 설정

Yarn Berry 기준 설치와 vitest.config.ts 설정은 다음과 같다[3]. environment: 'jsdom'은 Node.js 환경에 jsdom으로 가짜 DOM을 만들어서, React 컴포넌트를 실제 브라우저 없이도 렌더링·조작할 수 있게 한다. setupFiles는 모든 테스트 파일 실행 전에 공통으로 한 번 실행할 초기화 코드(예: jest-dom 매처 확장)를 지정한다.

bash
yarn add -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event
vitest.config.ts
/// <reference types="vitest" />
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: ['./src/test/setup.ts'],
    globals: true, // describe/it/expect를 import 없이 전역으로 사용
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
    },
  },
});
src/test/setup.ts
import '@testing-library/jest-dom/vitest';
package.json
{
  "scripts": {
    "test": "vitest",
    "test:coverage": "vitest run --coverage"
  }
}

테스트 파일 위치 컨벤션

Vitest는 기본적으로 *.test.ts, *.spec.ts 패턴에 맞는 파일을 모두 찾아서 실행한다. 실무에서는 크게 두 가지 배치 방식을 쓴다. 콜로케이션(co-location)은 테스트 파일을 검증 대상 옆에 나란히 둔다 — 어떤 파일에 테스트가 있고 없는지 파일 트리만 봐도 바로 보인다. 분리형(__tests__ 폴더)은 소스 코드와 테스트를 물리적으로 분리해서, 프로덕션 번들에 테스트 관련 파일이 섞여 들어갈 걱정을 원천적으로 없앤다. 둘 중 정답은 없지만, 한 프로젝트 안에서는 하나로 통일해야 "이 파일 테스트는 어디 있지"를 매번 찾아 헤매지 않는다.

파일 구조 예시 — 콜로케이션
src/
  components/
    LoginForm.tsx
    LoginForm.test.tsx   # 바로 옆에 둔다
  hooks/
    useDebounce.ts
    useDebounce.test.ts

watch 모드와 커버리지

vitest를 인자 없이 실행하면 기본이 watch 모드다. 파일을 저장할 때마다 영향을 받은 테스트만 다시 돌려서 즉시 피드백을 준다. CI처럼 한 번만 실행하고 끝내야 하는 환경에서는 vitest run을 쓴다. --coverage 플래그를 붙이면 커버리지 리포트가 생성된다 — 어떤 줄이 테스트에서 한 번도 실행되지 않았는지 보여준다. 커버리지 숫자를 목표로 삼는 것의 함정은 §5에서 다룬다.

watch 모드 단축키동작
a전체 테스트 다시 실행
f실패한 테스트만 다시 실행
p파일 이름 패턴으로 필터링
qwatch 모드 종료

모킹: vi.fn / vi.mock / vi.useFakeTimers

모킹(mocking)은 테스트 대상을 진짜 의존성(API 서버, 타이머, 파일 시스템)으로부터 떼어내기 위한 기법이다[4]. vi.fn()은 호출된 인자와 횟수를 기록하는 가짜 함수를 만든다. vi.mock('./api')은 모듈 전체를 가짜 구현으로 통째로 치환한다. vi.useFakeTimers()는 setTimeout/setInterval 같은 타이머를 가짜 시계로 바꿔서, 실제로 3초를 기다리지 않고도 "3초 후" 로직을 즉시 검증할 수 있게 한다.

vi.fn()의 핵심 아이디어

실제 vi.fn()은 브라우저 플레이그라운드에서 import할 수 없으므로(외부 라이브러리 import 불가), 같은 아이디어를 직접 20줄로 구현했다. 호출될 때마다 인자를 배열에 기록해두고, 나중에 "이 인자로 호출된 적 있나?"를 검사하는 것이 핵심이다. 실제 vi.fn()도 원리는 동일하고, 여기에 mockReturnValue, mockResolvedValue 같은 편의 기능이 더 붙어 있을 뿐이다.

실제 Vitest에서는 위 아이디어가 vi.fn, vi.mock, vi.useFakeTimers로 이미 제공된다. 아래는 실무에서 흔히 쓰는 조합 예시다.

src/greet.test.ts
import { describe, it, expect, vi } from 'vitest';
import { fetchUser } from './api';
import { greetUserLater } from './greet';

vi.mock('./api', () => ({
  fetchUser: vi.fn(() => Promise.resolve({ id: 1, name: '홍길동' })),
}));

describe('greetUserLater', () => {
  it('3초 후 사용자 이름으로 인사말을 콜백에 전달한다', async () => {
    vi.useFakeTimers();
    const cb = vi.fn();

    greetUserLater(1, cb);
    await vi.runAllTimersAsync(); // 3초를 실제로 기다리지 않고 즉시 통과

    expect(fetchUser).toHaveBeenCalledWith(1);
    expect(cb).toHaveBeenCalledWith('안녕하세요, 홍길동님');

    vi.useRealTimers();
  });
});

스냅샷 테스트

스냅샷 테스트는 expect(x).toMatchSnapshot()을 처음 실행하면 결과를 파일로 저장하고, 다음부터는 그 파일과 비교해서 달라졌으면 실패시킨다[5].

src/PriceTag.test.tsx
import { it, expect } from 'vitest';
import { renderToStaticMarkup } from 'react-dom/server';
import { PriceTag } from './PriceTag';

§4React Testing Library

철학: 사용자가 하듯 테스트

React Testing Library(RTL)의 핵심 철학은 "구현이 아니라 사용자가 경험하는 결과를 테스트하라"다[6]. state 변수 이름이 무엇인지, 내부에서 어떤 함수를 호출했는지는 테스트하지 않는다. 대신 "화면에 이 텍스트가 보이는가", "이 버튼을 누르면 이 문구가 나타나는가"처럼 사용자가 직접 확인할 수 있는 것만 검증한다. 이렇게 하면 내부 구현을 리팩터링해도(state를 useReducer로 바꾸든, 컴포넌트를 쪼개든) 사용자에게 보이는 동작이 같다면 테스트는 계속 통과한다.

render와 screen

render(<Component />)는 컴포넌트를 jsdom 안에 실제로 그려 넣는다. screen은 "지금 렌더링된 문서 전체"에서 요소를 찾는 도구 모음이다(screen.getByRole(...) 같은 형태로 사용). 아래는 이후 예제들이 계속 테스트할 대상인 로그인 폼이다. 직접 입력해 보면서 어떤 요소들이 있는지 살펴보자.

이 컴포넌트를 아래 코드블록들이 테스트한다

이메일에 @가 없거나 비밀번호가 4자 미만이면 role="alert"인 에러 문구를 보여준다. RTL 코드에서는 getByLabelText('이메일'), getByRole('button', {'{'} name: '로그인' {'}'}), getByRole('alert')로 이 요소들을 찾는다 — 모두 사용자가 화면에서 인지하는 방식과 같다.

  • htmlFor/id로 label과 input을 연결 — getByLabelText가 이걸 이용한다.
  • <button type="submit"> — role은 자동으로 button이 된다.
  • role="alert" — 스크린 리더가 즉시 읽어주는 영역이라는 뜻도 겸한다.

쿼리 우선순위

RTL은 요소를 찾는 방법을 getByRole부터 getByTestId까지 우선순위 순으로 정리해 둔다[7]. 위쪽일수록 실제 사용자(그리고 스크린 리더 사용자)가 요소를 인지하는 방식에 가깝다.

우선순위쿼리언제 쓰나이유
1getByRolebutton, link, checkbox 등 인터랙티브 요소 대부분스크린 리더가 인지하는 접근성 트리 기준과 가장 가깝다
2getByLabelTextinput, textarea, select 같은 form 필드실사용자는 라벨을 보고 필드를 찾는다
3getByPlaceholderText라벨 없이 placeholder만 있는 필드차선책. placeholder는 라벨의 접근성 대체재가 아니다
4getByText버튼·링크가 아닌 일반 텍스트사용자가 읽는 문구 그대로 찾는다
5getByDisplayValue이미 값이 채워진 form 요소현재 입력값 자체로 찾아야 할 때
6getByAltTextimg, area 등대체 텍스트로 이미지를 식별
7getByTitletitle 속성스크린 리더 지원이 일관되지 않아 우선순위가 낮다
8getByTestId위 방법으로 도저히 특정할 수 없을 때사용자는 test id를 볼 수 없다 — 최후의 수단

userEvent vs fireEvent

fireEvent.click(el)은 단 하나의 DOM 이벤트만 발생시킨다. userEvent.click(el)은 실제 사용자가 마우스를 올리고(hover), 포커스를 옮기고, 눌렀다 떼는 것까지 여러 이벤트를 실제 브라우저 순서 그대로 발생시킨다[8]. 예를 들어 input에 값을 넣을 때 fireEvent.change는 값만 한 번에 바꾸지만, userEvent.type은 키 하나하나를 눌러서 onChange가 글자 수만큼 여러 번 호출되는 실제 상황을 재현한다. 그래서 최신 RTL 가이드는 fireEvent보다 userEvent를 기본으로 쓰길 권장한다.

src/LoginForm.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { LoginForm } from './LoginForm';

test('이메일 형식이 아니면 에러 메시지를 보여준다', async () => {
  const user = userEvent.setup();
  render(<LoginForm />);

  await user.type(screen.getByLabelText('이메일'), 'not-an-email');
  await user.type(screen.getByLabelText('비밀번호'), '1234');
  await user.click(screen.getByRole('button', { name: '로그인' }));

  expect(screen.getByRole('alert')).toHaveTextContent('올바른 이메일을 입력하세요.');
});

findBy와 비동기 대기

API 호출 결과처럼 화면에 나중에 나타나는 요소는 getBy로 바로 찾을 수 없다(아직 DOM에 없어서 에러가 난다). findBy는 내부적으로 waitFor와 getBy를 합쳐서, 요소가 나타날 때까지 짧은 간격으로 재시도하다가 나타나면 반환하는 비동기(async) 쿼리다. 반드시 await과 함께 써야 한다.

MSW로 네트워크 모킹

실제 API 서버 없이 네트워크 요청을 가로채서 가짜 응답을 돌려주는 도구로 Mock Service Worker(MSW)가 널리 쓰인다. 컴포넌트의 fetch 호출 코드는 전혀 건드리지 않고, 테스트 쪽에서만 "이 경로로 요청이 오면 이 JSON을 돌려줘"라고 핸들러를 등록한다.

src/UserProfile.test.tsx
import { render, screen } from '@testing-library/react';
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';
import { UserProfile } from './UserProfile';

const server = setupServer(
  http.get('/api/users/1', () => HttpResponse.json({ id: 1, name: '홍길동' }))
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test('사용자 정보를 불러와 이름을 표시한다', async () => {
  render(<UserProfile userId={1} />);

  expect(await screen.findByText('홍길동')).toBeInTheDocument();
});
요약RTL은 getByRole을 최우선으로, userEvent로 실제 상호작용을 재현하고, findBy + MSW로 비동기 API 흐름까지 사용자 관점에서 검증한다.

§5무엇을 테스트하고 무엇을 하지 않나

구현 세부사항 테스트 금지

구현 세부사항(implementation detail)을 테스트에 끌어들이면, 코드를 리팩터링할 때마다(동작은 그대로인데도) 테스트가 같이 깨진다. 아래 실습은 "화면 텍스트로 찾는 쿼리"는 내부 구현이 바뀌어도 살아남고, "구현 세부사항에 의존한 검사"는 구현이 바뀌는 순간 깨지는 걸 직접 보여준다.

같은 화면, 다른 내부 구현

카운터를 두 가지 방식으로 구현했다 — 하나는 count 변수를, 하나는 value 변수를 쓴다. 둘 다 화면에는 똑같이 "숫자: N"을 보여준다. 화면 텍스트로 검증하면 두 구현 모두 통과하지만, 내부 변수 이름에 직접 접근하는 검증은 구현이 바뀌면 실패한다.

실행해 보면 화면 텍스트 기준 검증은 두 구현 모두 통과하지만, 내부 변수 이름에 의존한 검증은 구현 B에서 실패한다. 동작은 똑같이 잘 되는데도 테스트만 깨진 것이다 — 이런 테스트는 리팩터링을 방해하는 짐이 된다.

커버리지 숫자의 함정

커버리지 100%는 "모든 줄이 실행됐다"는 뜻이지 "모든 상황이 검증됐다"는 뜻이 아니다. 함수를 호출만 하고 결과를 expect로 확인하지 않아도 그 줄은 "커버됐다"고 표시된다. 커버리지는 목표가 아니라 "테스트가 아예 없는 사각지대를 찾는 용도"로만 쓰는 편이 안전하다. 숫자를 팀 KPI로 강제하면 의미 없는 테스트를 억지로 채워 넣는 역효과가 난다.

테스트하기 좋은 컴포넌트 설계

테스트하기 쉬운 컴포넌트는 대체로 설계도 좋은 컴포넌트다. 컴포넌트를 작게 쪼개고, API 호출 같은 부수효과는 커스텀 훅으로 분리하고(useEffect 참고), 의존성을 props나 인자로 주입받게 만들면 각 조각을 독립적으로 검증하기 쉬워진다. 반대로 컴포넌트 하나가 데이터 페칭, 폼 검증, 렌더링을 전부 떠안고 있으면 테스트 하나를 짜는 데도 온갖 목(mock)을 다 준비해야 한다 — 이건 테스트의 문제가 아니라 설계의 신호다.

테스트에 필요한 가짜 데이터를 매번 손으로 { id: 1, name: '홍길동', ... }처럼 나열하면, 필드가 하나 늘 때마다 모든 테스트 파일을 고쳐야 한다. 테스트 데이터 팩토리는 기본값을 가진 함수 하나로 이 문제를 없앤다 — 필요한 필드만 덮어써서 쓴다.

src/test/factories.ts
import type { User } from '../types';

export function makeUser(overrides: Partial<User> = {}): User {
  return {
    id: 1,
    name: '홍길동',
    email: 'hong@example.com',
    role: 'member',
    ...overrides,
  };
}

// 사용: 관리자 케이스만 다르게
const admin = makeUser({ role: 'admin' });
흔한 실수useState 훅을 직접 렌더링해서 반환값을 검사하거나, 컴포넌트 내부 함수를 이름으로 꺼내 단독 호출하는 테스트는 대표적인 구현 세부사항 테스트다. "이 함수가 호출됐는가"보다 "화면에 무엇이 보이는가"를 물어야 한다.

§6E2E

Playwright는 실제 브라우저(Chromium, Firefox, WebKit)를 자동으로 조작해서 사용자의 전체 흐름을 검증하는 E2E 테스트 도구다[9].

설치

bash
yarn create playwright
# 또는 수동 설치
yarn add -D @playwright/test
npx playwright install

첫 테스트 작성

e2e/login.spec.ts
import { test, expect } from '@playwright/test';

test('로그인 후 대시보드로 이동한다', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('이메일').fill('user@example.com');
  await page.getByLabel('비밀번호').fill('secret123');
  await page.getByRole('button', { name: '로그인' }).click();

  await expect(page.getByRole('heading', { name: '대시보드' })).toBeVisible();
});

baseURL을 설정 파일에 지정해두면 테스트마다 전체 주소를 반복하지 않고 /login처럼 경로만 써도 된다. webServer는 테스트를 시작하기 전에 개발 서버를 Playwright가 직접 띄우고, 테스트가 끝나면 정리하게 한다.

playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  use: {
    baseURL: 'http://localhost:5174',
    trace: 'on-first-retry',
  },
  webServer: {
    command: 'yarn dev',
    url: 'http://localhost:5174',
    reuseExistingServer: !process.env.CI,
  },
});

로케이터 전략

로케이터(locator)는 RTL의 쿼리와 같은 우선순위를 따른다 — getByRole/getByLabel/getByText를 우선 쓰고, CSS 선택자나 XPath는 정말 방법이 없을 때만 쓴다[10]. 클래스명 같은 구현 세부사항으로 요소를 찾으면 스타일만 바꿔도 테스트가 깨진다.

auto-waiting

Playwright의 로케이터는 클릭·입력 같은 동작을 실행하기 전에 해당 요소가 DOM에 붙어 있고, 보이고, 다른 요소에 가려지지 않고, 활성화돼 있는지까지 자동으로 재시도하며 기다린다. 그래서 page.waitForTimeout(1000) 같은 임의의 sleep을 코드에 넣을 필요가 거의 없다 — 그런 sleep은 느리기만 하고, 환경에 따라 부족하거나 과할 수 있어 오히려 flaky(불안정)한 테스트의 원인이 된다.

트레이스 뷰어

--trace on 옵션으로 실행하면 각 단계의 스크린샷, DOM 스냅샷, 네트워크 로그, 콘솔 로그를 타임라인 형태로 기록한다. 테스트가 CI에서만 실패했을 때, 로컬에서 재현하기보다 이 트레이스 파일을 열어서 "그 순간 화면이 실제로 어땠는지"를 그대로 재생해 보는 게 훨씬 빠르다[11].

CI에서 실행

CI 환경은 로컬보다 느리고 리소스가 제한적이라 타임아웃과 재시도(retry) 설정을 CI 전용으로 따로 두는 경우가 많다[12]. 구체적인 워크플로 예시는 §11에서 다룬다.

E2E를 몇 개만 유지해야 하는 이유

E2E는 실제 브라우저를 띄우고 렌더링까지 기다려야 해서 단위 테스트보다 몇 배에서 몇십 배 느리다. 또 네트워크 지연, 애니메이션 타이밍, 외부 서비스 상태 같은 통제하기 어려운 변수에 노출돼서 flaky해지기 쉽다. 그래서 §1의 트로피 모델처럼 E2E는 "로그인", "결제"처럼 실패하면 서비스 전체가 마비되는 핵심 흐름(critical path) 몇 개만 남기고, 나머지 세부 동작 검증은 훨씬 빠르고 안정적인 단위·통합 테스트로 옮기는 것이 정석이다.

요약Playwright는 role 기반 로케이터 + auto-waiting으로 안정적인 E2E를 만든다. 다만 E2E는 느리고 불안정해지기 쉬우므로 핵심 흐름 몇 개만 유지한다.

§7린트

린트(lint)는 코드를 실행하지 않고도 "이 패턴은 버그가 될 가능성이 높다"거나 "이 스타일은 팀 규칙과 다르다"를 잡아낸다.

typescript-eslint 패키지는 ESLint가 TypeScript 문법을 이해하게 해주고, 나아가 tsconfig.json과 연결해서 타입 정보 기반(type-aware) 규칙까지 제공한다 — 예를 들어 await 없이 Promise를 그냥 버려두는 코드를 잡아낼 수 있다. 다만 타입 정보를 쓰려면 타입 체크 과정이 같이 도는 만큼 일반 규칙보다 느리다.

eslint-plugin-react-hooks

훅의 두 가지 규칙(최상위에서만 호출, 조건문 안에서 호출 금지)을 강제하고, exhaustive-deps 규칙으로 useEffect의 의존성 배열에 실제로 사용 중인 값이 빠져 있는지 검사한다. 이 규칙을 끄고 싶은 유혹이 들 때가 많지만, 대부분은 의존성이 빠진 게 아니라 로직 구조 자체를 다시 봐야 한다는 신호다.

jsx-a11y

JSX 코드에서 접근성 문제를 정적으로 검사한다 — alt 없는 img, 클릭 핸들러만 있고 키보드로는 조작할 수 없는 div, 폼 요소에 연결된 라벨이 없는 경우 등을 빌드 전에 잡아낸다. WCAG/ARIA 기준 자체는 렌더링 전략 챕터의 접근성 절에서 더 다룬다.

규칙을 끄기 전에 생각할 것

// eslint-disable-next-line을 습관적으로 붙이기 전에, 그 규칙이 왜 존재하는지부터 확인한다. 대부분의 규칙은 실제로 사고를 낸 패턴을 근거로 추가된 것이다. 정말 예외적인 상황이라면 (1) 파일 전체가 아니라 그 줄만 끄고, (2) 왜 예외인지 주석을 남기고, (3) 팀 전체 설정에서 규칙 자체를 끄는 건 최후의 수단으로 남겨둔다.

§9Git 실전

작업트리 · 스테이징 · 커밋

작업트리(working tree)는 지금 눈에 보이는 실제 파일 상태다. 스테이징 영역(staging area, index)은 "다음 커밋에 포함시킬 변경사항"만 따로 담아두는 중간 단계다. 커밋(commit)은 그 스테이징 상태를 히스토리에 영구적으로 기록하는 행위다. 이 3단계 구조 덕분에 "작업 중인 파일 10개 중 관련 있는 2개만" 골라서 커밋하는 것이 가능하다.

flowchart LR
  A["작업트리
(Working Tree)"] -- "git add" --> B["스테이징 영역
(Staging Area)"]
  B -- "git commit" --> C["저장소 히스토리
(Repository)"]
  C -. "git reset --soft" .-> B
  C -. "git checkout -- 파일" .-> A
그림 2. git add는 작업트리 → 스테이징, git commit은 스테이징 → 저장소로 상태를 옮긴다. 점선은 되돌리는 방향이다. 출처: Pro Git Book, Git Basics[16]

브랜치는 포인터다

브랜치(branch)는 특정 커밋을 가리키는 이름표일 뿐이다[16]. 브랜치를 새로 만드는 건 그 시점의 파일을 통째로 복사하는 게 아니라, "여기를 가리키는 이름표 하나"를 추가하는 것뿐이라 즉시 끝나고 용량도 거의 안 든다. 그 브랜치에서 커밋을 하나 더 만들면, 그 브랜치라는 이름표만 새 커밋을 가리키도록 자동으로 이동한다.

gitGraph
   commit id: "C1"
   commit id: "C2"
   branch feature
   checkout feature
   commit id: "C3"
그림 3. main과 feature는 각자 특정 커밋을 가리키는 포인터일 뿐이다. feature에서 커밋할 때마다 feature라는 이름표만 앞으로 이동하고, main은 그대로 C2를 가리킨다. 출처: Pro Git Book, Branches in a Nutshell[16]

merge vs rebase

merge는 두 브랜치를 합치면서 "두 부모를 가진" 새 커밋(머지 커밋)을 만든다. 분기했다가 다시 합류한 실제 히스토리가 그래프에 그대로 남는다.

gitGraph
   commit id: "C1"
   commit id: "C2"
   branch feature
   checkout feature
   commit id: "C3"
   commit id: "C4"
   checkout main
   commit id: "C5"
   merge feature id: "M1"
그림 4. merge — C3, C4, C5가 각각 그대로 남고, 두 브랜치를 합치는 새 커밋 M1이 추가된다. 분기와 합류가 히스토리에 보존된다. 출처: Pro Git Book, Basic Branching and Merging[16]

rebase는 feature 브랜치의 커밋들을 main의 최신 커밋 뒤에 하나씩 다시 적용한다. 겉보기엔 같은 변경 내용이지만 실제로는 새로운 커밋(해시가 다른 C3', C4')이 만들어지고, 히스토리가 분기 없이 한 줄로 곧게 펴진다.

gitGraph
   commit id: "C1"
   commit id: "C2"
   branch feature
   checkout feature
   commit id: "C3"
   commit id: "C4"
   checkout main
   commit id: "C5"
그림 5. rebase 전 — C3, C4는 C2에서 갈라져 나온 상태로, main은 이미 C5까지 진행됐다. 출처: Pro Git Book, Rebasing[19]
gitGraph
   commit id: "C1"
   commit id: "C2"
   commit id: "C5"
   branch feature
   checkout feature
   commit id: "C3-new"
   commit id: "C4-new"
그림 6. rebase 후 — feature의 커밋들이 C5 뒤로 다시 적용돼(C3', C4') 히스토리가 한 줄로 펴진다. C3, C4라는 원래 커밋은 더 이상 어떤 브랜치도 가리키지 않는다. 출처: Pro Git Book, Rebasing[19]
골든 룰rebase는 커밋을 새로 만들어(해시가 바뀜) 히스토리를 다시 쓴다. 이미 push해서 다른 사람이 pull받은 브랜치를 rebase하면, 그 사람의 로컬 히스토리와 어긋나서 큰 혼란이 생긴다. 공유된(다른 사람이 이미 받아간) 히스토리는 절대 rebase하지 않는다 — 내 로컬에만 있는 커밋을 정리할 때만 쓴다[19].

충돌 해결 절차

충돌(conflict)이 나면 다음 순서로 처리한다.

1. 충돌 파일 확인

git status로 "both modified"로 표시된 파일 목록을 확인한다.

2. 마커 정리

파일을 열어 <<<<<<< / ======= / >>>>>>> 마커 사이에서 남길 코드를 고르고 마커를 지운다.

3. 해결 표시

git add <file>로 "이 파일은 정리했다"고 표시한다.

4. 이어가기

merge 중이었다면 git commit, rebase 중이었다면 git rebase --continue.

되돌리기: reset / revert / restore / stash

네 명령 모두 "되돌린다"는 점은 같지만 대상과 안전 범위가 다르다. reset은 히스토리 자체를 옮기고[17], revert는 히스토리를 보존한 채 새 커밋으로 상쇄하고, restore는 파일 단위로만 되돌리고, stash는 커밋하지 않은 변경을 잠깐 다른 곳에 치워둔다[18].

상황명령효과
커밋 안 한 특정 파일을 원래대로 되돌리고 싶다git restore <file>작업트리의 그 파일만 마지막 커밋 상태로 되돌림
스테이징만 취소하고 싶다 (내용은 유지)git restore --staged <file>스테이징 영역에서만 제외, 작업트리 내용은 그대로
로컬 커밋 몇 개를 완전히 없던 일로 하고 싶다git reset --hard <commit>히스토리와 작업트리를 모두 되돌림 (변경 내용 소실)
커밋은 취소하되 변경 내용은 남겨 다시 정리하고 싶다git reset --soft / --mixed <commit>히스토리만 되돌리고 변경 내용은 스테이징/작업트리에 남김
이미 push해서 남도 받아간 커밋을 되돌리고 싶다git revert <commit>히스토리를 지우지 않고 반대 내용의 새 커밋을 추가 — 공유 브랜치에 안전
커밋 안 한 변경을 잠깐 치워두고 다른 브랜치로 가고 싶다git stash작업트리 변경을 임시 저장하고 깨끗한 상태로 되돌림, stash pop으로 복원

실제 git 없이 되돌리기 개념 실습

커밋 히스토리를 문자열 배열로 흉내내서, reset --hard(히스토리에서 잘라내기)와 revert(반대 내용의 새 커밋 추가)가 결과적으로 히스토리 배열을 어떻게 다르게 바꾸는지 콘솔로 비교한다.

요약브랜치는 가벼운 포인터다. merge는 히스토리를 보존하고, rebase는 히스토리를 한 줄로 펴되 공유된 히스토리에는 쓰지 않는다. 되돌릴 땐 "아직 공유 안 됐나(reset)" vs "이미 공유됐나(revert)"를 먼저 판단한다.

§10브랜치 전략과 릴리즈

trunk-based vs git-flow

trunk-based development는 브랜치 수명을 하루~며칠로 짧게 유지하고 main에 자주 병합한다. git-flow는 develop/feature/release/hotfix처럼 여러 장기 브랜치를 역할별로 두는 무거운 모델이다.

항목trunk-basedgit-flow
브랜치 수명짧다 (하루~며칠)길다 (develop·release가 몇 주씩 유지)
병합 빈도main에 자주, 작은 단위로기능 완료 후 한 번에
미완성 기능 처리feature flag로 숨기고 배포별도 feature 브랜치에 격리
적합한 배포 방식지속적 배포(CD), SaaS 웹 서비스정해진 주기로 릴리즈하는 버전형 소프트웨어
충돌 위험자주 합치므로 충돌이 작고 잦음오래 격리하다 한 번에 합치므로 충돌이 크고 드묾

브랜치 이름 규칙

trunk-based든 git-flow든, 브랜치 이름만 봐도 "무슨 작업인지, 어떤 이슈와 연결되는지"가 드러나야 나중에 찾기 쉽다. 이슈 트래커(Jira 등)를 쓰는 프로젝트에서는 이슈 키를 브랜치 이름에 그대로 넣는 방식이 흔하다.

브랜치 이름 예시
feature/SCRUM-42-kpi-webhook   # 새 기능, 이슈 SCRUM-42
fix/SCRUM-55-event-store-null  # 버그 수정, 이슈 SCRUM-55
chore/SCRUM-60-upgrade-vite    # 잡무성 변경

브랜치 타입(feature/fix/chore)은 아래에서 다룰 Conventional Commits의 type과 자연스럽게 맞물린다 — 브랜치에서 작업한 내용을 커밋할 때 같은 분류 감각을 그대로 이어 쓰면 된다.

Conventional Commits

Conventional Commits는 커밋 메시지를 type(scope): subject 형식으로 통일한다[20].

type의미예시
feat새 기능 추가feat(auth): add oauth login
fix버그 수정fix(kpi): null 값 처리 오류 수정
docs문서만 변경docs: update README install 절차
style동작에 영향 없는 포맷팅style: run prettier
refactor기능 변경 없는 구조 개선refactor: extract useCounter hook
perf성능 개선perf: memoize expensive selector
test테스트 추가/수정test: add LoginForm RTL test
build빌드 시스템·의존성 변경build: bump vite to v6
ciCI 설정 변경ci: add coverage upload step
chore그 외 잡무chore: update .gitignore
revert이전 커밋 되돌림revert: revert "feat(auth): ..."

type 뒤에 !를 붙이거나 본문에 BREAKING CHANGE:를 적으면 하위 호환이 깨진다는 뜻이고, 이는 §의 semver에서 MAJOR 버전 상승으로 이어진다.

커밋 메시지로 버전 상승 폭 판정하기

정규식으로 type(scope)!: subject 형태를 파싱하고, breaking 여부 → feat → fix 순서로 버전을 얼마나 올려야 하는지 판정한다. 실제 semantic-release 같은 도구가 하는 일의 핵심 원리다.

시맨틱 버전과 CHANGELOG 자동화

시맨틱 버전(semver)은 MAJOR.MINOR.PATCH 형태다[21]. MAJOR는 하위 호환이 깨지는 변경, MINOR는 하위 호환을 유지하며 기능을 추가한 변경, PATCH는 버그 수정을 뜻한다.

Conventional Commits로 커밋 타입이 통일돼 있으면, 도구가 커밋 로그를 스캔해서 다음 버전 번호를 자동으로 정하고 CHANGELOG.md도 자동 생성할 수 있다. 사람이 매 릴리즈마다 "이번엔 major인지 minor인지" 회의하지 않아도 된다.

PR 리뷰 체크리스트

PR(Pull Request)을 올리고 리뷰를 요청하기 전에, 그리고 리뷰어로서 볼 때 확인할 항목이다[22].

  • 이 PR의 목적(왜)이 설명에 한두 문장으로 적혀 있는가 — 무엇을 바꿨는지는 diff가 이미 보여준다.
  • 테스트가 추가/수정됐는가, 아니면 왜 필요 없는지 설명이 있는가.
  • CI(lint, test, build)가 모두 통과했는가.
  • 커밋 메시지가 Conventional Commits 형식을 따르는가.
  • PR 하나가 리뷰 가능한 크기인가 — 너무 크면 쪼갤 수 없는지 먼저 물어본다.
  • 기존 동작을 바꿨다면 그 영향 범위(다른 화면·API 소비부)를 같이 확인했는가.

§11자동화

Husky + lint-staged

Husky는 커밋 직전처럼 Git이 제공하는 Git 훅(hook)을 팀 전체에 쉽게 심어주는 도구다. lint-staged는 그 훅 안에서 "지금 커밋하려는 파일만" 골라 린트·포맷을 돌려서, 매번 코드베이스 전체를 검사하는 낭비를 없앤다.

bash
yarn add -D husky lint-staged
npx husky init   # Husky v9 기준. .husky/pre-commit 파일을 생성한다
.husky/pre-commit
npx lint-staged
package.json
{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": ["eslint --fix", "prettier --write"],
    "*.{json,css,md}": ["prettier --write"]
  }
}

GitHub Actions로 lint/test/build

로컬 pre-commit 훅은 우회할 수 있으므로(--no-verify), 최종 관문은 항상 CI다. push나 PR마다 lint → test → build를 자동으로 돌려서, 통과하지 못하면 머지할 수 없게 만든다[23].

flowchart LR
  A["git push / PR 생성"] --> B["Job: lint
eslint ."]
  B --> C["Job: test
vitest run --coverage"]
  C --> D["Job: build
vite build"]
  D --> E{"모두 통과?"}
  E -- "예" --> F["머지 가능 상태"]
  E -- "아니오" --> G["PR에 실패 표시"]
그림 7. lint → test → build 순서로 실행하면, 가장 빠르고 저렴한 검사(lint)에서 먼저 실패시켜 느린 build까지 기다리지 않게 한다. 출처: GitHub Docs, Actions[23]
.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: yarn
      - run: yarn install --immutable
      - run: yarn lint

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: yarn
      - run: yarn install --immutable
      - run: yarn test run --coverage

  build:
    runs-on: ubuntu-latest
    needs: [lint, test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: yarn
      - run: yarn install --immutable
      - run: yarn build

needs: [lint, test]로 build job이 앞선 두 job의 성공을 전제로 실행되게 만든다. Yarn Berry 프로젝트에서는 npm ci 대신 yarn install --immutable을 써서 lockfile과 어긋나는 설치를 CI에서 차단한다. actions/setup-node의 cache: yarn 옵션은 의존성 캐시를 워크플로 실행 사이에 재사용해서, 매번 처음부터 전체 패키지를 내려받지 않게 한다 — 저장소가 클수록 빌드 시간 차이가 크다.

§10과 연결: 릴리즈 자동화

§10에서 다룬 Conventional Commits와 semver를 CI에 연결하면, main에 머지될 때마다 커밋 로그를 스캔해서 다음 버전 번호를 정하고 CHANGELOG.md와 Git 태그, GitHub Release까지 자동으로 만드는 릴리즈 워크플로를 구성할 수 있다. build job 뒤에 release job을 하나 더 추가하는 형태다.

.github/workflows/ci.yml — release job 추가
  release:
    runs-on: ubuntu-latest
    needs: [build]
    if: github.ref == 'refs/heads/main'
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0 # 커밋 로그 전체를 스캔하려면 전체 히스토리가 필요하다
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: yarn
      - run: yarn install --immutable
      - run: yarn release # semver 계산 + CHANGELOG 갱신 + 태그/릴리즈 생성
요약Husky + lint-staged는 "커밋하기 전에" 빠르게, GitHub Actions는 "머지하기 전에" 확실하게 검사한다. 로컬 훅은 우회 가능하므로 최종 방어선은 항상 CI다. 커밋 메시지 규칙(§10)을 지키면 릴리즈 자동화까지 자연스럽게 이어진다.

§12이해도 점검

  • 테스트가 회귀 방지, 리팩터링 안전망, 실행 가능한 문서 역할을 한다는 것을 설명할 수 있다.
  • 테스트 피라미드와 테스트 트로피의 차이, 그리고 프론트엔드가 통합 테스트를 더 두껍게 두는 이유를 설명할 수 있다.
  • describe/it/expect가 내부적으로 어떻게 동작하는지, AAA 패턴이 왜 필요한지 안다.
  • Vite 프로젝트에 Jest 대신 Vitest를 쓰는 이유와 vitest.config.ts의 environment/setupFiles 역할을 안다.
  • vi.fn/vi.mock/vi.useFakeTimers가 각각 무엇을 가짜로 만드는지 설명할 수 있다.
  • RTL의 "사용자처럼 테스트" 철학과 쿼리 우선순위(getByRole 우선, getByTestId 최후)를 이해한다.
  • userEvent와 fireEvent의 차이, findBy를 언제 쓰는지 안다.
  • 구현 세부사항을 테스트하면 안 되는 이유와, 커버리지 숫자가 왜 목표가 될 수 없는지 설명할 수 있다.
  • Playwright의 auto-waiting이 왜 임의의 sleep보다 나은지, E2E를 왜 소수만 유지해야 하는지 안다.
  • ESLint flat config의 배열 우선순위 구조와 typescript-eslint/react-hooks/jsx-a11y 각각의 역할을 안다.
  • Prettier와 ESLint의 역할 분리, Biome을 도입할 때 고려할 트레이드오프를 설명할 수 있다.
  • 작업트리·스테이징·커밋의 흐름과 "브랜치는 포인터다"를 그림 없이도 설명할 수 있다.
  • merge와 rebase의 결과 히스토리 차이, 그리고 공유 히스토리를 rebase하면 안 되는 이유를 안다.
  • reset/revert/restore/stash를 상황별로 골라 쓸 수 있다.
  • Conventional Commits의 type이 semver 버전 상승과 어떻게 연결되는지 설명할 수 있다.
  • Husky+lint-staged(커밋 전)와 GitHub Actions(머지 전)의 역할 차이를 안다.
