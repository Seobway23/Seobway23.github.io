CHAPTER 01

JavaScript 동작 원리

브라우저는 HTML을 읽다가 스크립트를 만나면 무슨 일을 하는가. 값을 복사했는데 왜 원본까지 같이 바뀌는가. 클로저는 왜 메모리에 계속 남아있는가. setTimeout(fn, 0)과 Promise.then은 왜 실행 순서가 다른가. 이 챕터는 이후 모든 챕터(React, TypeScript, 상태 관리)가 딛고 서는 바닥을 다진다.

이 챕터에서 답할 질문: 브라우저는 HTML을 파싱하다가 <script>를 만나면 무슨 순서로 처리하는가? 원시 타입과 참조 타입은 메모리에 어떻게 다르게 저장되는가? var/let/const는 왜 호이스팅 동작이 다른가? 클로저는 정확히 무엇이고 왜 실무에서 쓰는가? this는 왜 호출할 때마다 값이 바뀌는가? 콜 스택이 비었을 때 브라우저는 어떤 순서로 대기 중인 작업을 처리하는가?

§1브라우저에서 JS가 실행되기까지

HTML 파싱과 DOM

브라우저는 서버가 보낸 HTML을 파싱하면서 위에서 아래로 순서대로 읽는다. 태그를 만날 때마다 노드를 만들어 DOM(Document Object Model) 트리에 붙인다. 이 파서는 기본적으로 동기적이라서, 파싱 도중 무언가가 파서를 멈추게 하면 그 순간부터 화면에 아무것도 더 그려지지 않는다.

문제는 <script> 태그다. 스크립트는 document.write로 DOM을 바꿀 수도 있기 때문에, 브라우저는 안전하게 스크립트를 실행할 때까지 파싱을 잠시 멈춰야 한다. 이것이 "스크립트는 렌더링을 막을 수 있다"는 말의 정체다.

스크립트 로드: 일반 / defer / async

스크립트 태그에 속성을 어떻게 붙이느냐에 따라 "언제 다운로드하고 언제 실행하는지"가 완전히 달라진다.

방식다운로드 시점실행 시점파싱을 막는가
<script src="a.js">만나는 즉시다운로드 끝나자마자 바로다운로드+실행 동안 막는다
<script defer src="a.js">파싱과 동시에(병행)DOM 파싱이 끝난 직후, 문서 등장 순서대로안 막는다
<script async src="a.js">파싱과 동시에(병행)다운로드가 끝나는 즉시(순서 보장 없음)실행되는 짧은 순간만 막는다
그림 2. 같은 페이지를 세 방식으로 불러왔을 때의 시간 흐름. 일반 <script>는 태그를 만나는 순간 다운로드와 실행이 끝날 때까지 파싱을 멈추므로, 파싱 완료가 ②까지 밀린다. defer는 파싱과 동시에 내려받고 파싱이 끝난 시점 ① 이후 문서 등장 순서대로 실행한 뒤 DOMContentLoaded가 발생한다. async도 병렬로 내려받지만 다운로드가 끝나는 즉시 실행되어(순서 보장 없음) 그 짧은 구간만 파싱을 멈춘다. ①과 ②의 간격이 곧 일반 <script>가 만드는 지연이다. 출처: WHATWG HTML Standard[1]
실무 기준 Vite/Webpack 같은 번들러가 만드는 <script type="module">은 기본적으로 defer와 같은 순서 보장을 갖는다. 그래서 최신 프론트엔드 프로젝트에서는 스크립트 로드 순서를 직접 고민할 일이 거의 없다. 다만 원리를 모르면 "왜 내 서드파티 스크립트가 body 태그를 못 찾는지" 같은 문제를 디버깅할 수 없다.

CSS가 JS 실행을 막는 경우

HTML 파서는 <link rel="stylesheet">를 만나도 파싱을 멈추지 않고 계속 진행한다(스타일시트는 화면을 그릴 때만 필요하니까). 하지만 그 뒤에 일반 <script>가 나오면 이야기가 다르다. 스크립트는 getComputedStyle()처럼 스타일 값을 즉시 읽을 수도 있기 때문에, 브라우저는 스크립트를 실행하기 전에 그 앞의 스타일시트가 CSSOM 생성을 끝낼 때까지 기다린다. 결과적으로 "스타일시트 로딩이 스크립트 실행을 지연시킬 수 있다"는 것이 실무에서 자주 놓치는 함정이다.

실무 함정 <head>에 무거운 CSS 파일을 넣고 그 바로 뒤에 일반 <script>를 두면, 스크립트는 CSS 다운로드+파싱이 끝날 때까지 기다렸다가 실행된다. defer를 쓰면 어차피 DOM 파싱이 끝난 뒤 실행되므로 이 문제에서 자유롭다.

정리: DOMContentLoaded와 load

DOMContentLoaded는 DOM 트리와 defer 스크립트 실행까지 끝난 시점에 발생하고, load는 이미지·폰트 같은 모든 리소스까지 다 받아온 뒤에 발생한다. React 같은 라이브러리가 "DOM이 준비되면" 마운트를 시작할 수 있는 것도 이 순서 보장 덕분이다.

§2값과 타입

원시 타입 vs 참조 타입

JS의 모든 값은 원시 타입(primitive) 아니면 참조 타입(reference) 둘 중 하나다.

타입예시typeof 결과
string"hi""string"
number42, NaN"number"
booleantrue"boolean"
undefined값을 할당하지 않은 변수"undefined"
null"의도적으로 비어있음""object" (역사적 버그)
symbolSymbol("id")"symbol"
bigint10n"bigint"

object, array, function은 전부 참조 타입이다. 이 둘의 차이는 눈으로 보이지 않지만, 메모리 구조를 보면 왜 "복사했는데 원본까지 바뀌는" 버그가 생기는지 명확해진다.

그런데 왜 "hi".length가 되지? 문자열은 분명 원시 타입인데 .length나 .toUpperCase() 같은 메서드를 쓸 수 있다. JS 엔진이 "hi".length를 실행하는 순간 잠깐 String 래퍼 객체로 감쌌다가(오토박싱, autoboxing) 메서드 호출이 끝나면 즉시 버린다. 원시값 자체가 객체로 바뀌는 것은 아니다.
그림 3. a, b는 스택에 독립된 값으로 저장되지만, user와 user2는 같은 힙 객체를 가리키는 참조(주소)를 복사한 것이라 하나를 바꾸면 다른 쪽도 바뀐 것처럼 보인다.

값 복사 vs 참조 복사

원시 타입을 다른 변수에 대입하면 값 자체가 새로 복사되어 서로 독립적이다. 반면 객체를 대입하면 참조(주소)만 복사되어 두 변수가 같은 객체를 가리키게 된다. "얕은 복사인 줄 알았는데 원본이 바뀌었다"는 버그는 대부분 이 원리를 몰라서 생긴다.

=== vs ==, NaN, null vs undefined

===(일치 연산자)는 타입까지 비교하고, ==(동등 연산자)는 타입이 다르면 먼저 변환한 뒤 비교한다[2]. 실무에서는 예측 가능성 때문에 ===를 기본으로 쓴다.

NaN은 IEEE 754 스펙상 자기 자신과도 같지 않다. 그래서 NaN === NaN은 false이고, NaN을 검사하려면 Number.isNaN()을 써야 한다[3].

undefined는 "값을 할당한 적이 없음", null은 "의도적으로 비웠음"을 뜻한다. 관례상 null은 개발자가 직접 대입하고, undefined는 JS 엔진이 자동으로 부여한다(선언만 하고 초기화 안 한 변수, 없는 프로퍼티 등).

참고: Object.is() ===도 완벽하진 않다. Object.is(NaN, NaN)은 true(===는 false), Object.is(0, -0)은 false(===는 true)를 반환한다 — 부호 있는 0과 NaN을 정확히 구분해야 하는 드문 경우에만 쓴다. 일반적인 비교는 여전히 ===가 기본이다.

얕은 복사 vs 깊은 복사

얕은 복사(스프레드 {...obj}, Object.assign)는 1단계 속성만 새로 복사한다. 중첩된 객체가 있으면 그 내부는 여전히 원본과 같은 참조를 공유한다. 완전히 독립된 사본이 필요하면 깊은 복사가 필요하고, 브라우저 내장 structuredClone()이 표준적인 방법이다[4].

무슨 일이 일어나는가

아래 코드를 왼쪽부터 순서대로 읽으면서 예측한 뒤 ▶ 실행으로 확인한다.

  • b = a — 숫자는 값이 복사되어 서로 독립적이다.
  • user2 = user — 객체는 참조가 복사되어 하나를 바꾸면 둘 다 바뀐다.
  • Number.isNaN — NaN === NaN이 항상 거짓이기 때문에 필요하다.
  • {...original} — 얕은 복사라 중첩 객체(address)는 공유된다.
  • structuredClone — 중첩까지 완전히 새로 복사하는 깊은 복사다.
흔한 실수 const로 선언한 배열/객체를 "상수라서 안전하다"고 착각하는 경우가 많다. const는 재할당만 막을 뿐, 객체 내부 속성 변경은 막지 않는다. 완전히 못 바꾸게 하려면 Object.freeze()가 필요하다(단, 얕은 freeze).

타입 변환(coercion)

JS는 타입이 맞지 않는 연산을 만나면 조용히 값을 다른 타입으로 바꾼 뒤 계속 진행한다. ECMA-262 스펙은 이 과정을 ToNumber, ToString, ToBoolean 같은 내부 변환 규칙(추상 연산)으로 정의한다[19]. 실무에서 버그를 만드는 대표적인 규칙 두 가지만 기억하면 된다: +는 피연산자 중 하나라도 문자열이면 문자열 이어붙이기로 동작하고, 그 외 산술 연산자(-, *, /)는 항상 숫자로 변환해서 계산한다.

표현식결과이유
1 + '2''12'+에서 문자열이 하나라도 있으면 이어붙이기
1 - '2'-1-는 항상 숫자로 변환
'5' * '2'10산술 연산자는 숫자로 강제 변환
[] + []''배열이 먼저 문자열로 변환된 뒤 이어붙이기
Boolean('')falsefalsy 값

falsy 값(Boolean()으로 변환하면 false가 되는 값)은 딱 8개뿐이다: false, 0, -0, 0n, "", null, undefined, NaN. 이 목록 밖의 모든 값(빈 객체 {}, 빈 배열 [] 포함)은 truthy다.

symbol과 bigint는 언제 쓰나

나머지 5가지 원시 타입에 비해 symbol과 bigint는 등장 빈도가 낮지만 용도가 뚜렷하다. Symbol()은 호출할 때마다 세상에 단 하나뿐인 값을 만든다 — 객체 프로퍼티 키가 다른 코드와 절대 충돌하지 않아야 할 때(라이브러리 내부 전용 키 등) 쓴다. bigint는 Number.MAX_SAFE_INTEGER(253-1)를 넘는 정수를 오차 없이 다뤄야 할 때 10000000000000000n처럼 끝에 n을 붙여 만든다.

알아두면 좋음 bigint와 number는 서로 다른 타입이라 1n === 1은 false이고, 1n + 1처럼 섞어서 연산하면 TypeError가 난다. 반드시 같은 타입끼리만 계산해야 한다.

§3스코프와 호이스팅

var / let / const

var는 함수 스코프, let/const는 블록 스코프를 갖는다. { } 블록 안에서 선언한 var는 블록 밖에서도 보이지만, let/const는 그 블록을 벗어나면 접근할 수 없다[5].

호이스팅과 TDZ

호이스팅(hoisting)은 JS 엔진이 코드를 실행하기 전, 스코프 안의 선언들을 미리 등록해두는 동작을 말한다[6]. var는 선언과 동시에 undefined로 초기화되기 때문에 선언 이전에 읽어도 에러 없이 undefined가 나온다. 반면 let/const는 선언은 끌어올려지지만 초기화되지 않은 상태로 남아있고, 이 구간을 TDZ(Temporal Dead Zone)라 부른다. TDZ에서 변수를 읽으면 ReferenceError가 발생한다[용어사전: TDZ].

스코프재선언재할당선언 전 접근
var함수가능가능undefined (에러 없음)
let블록불가가능ReferenceError (TDZ)
const블록불가불가ReferenceError (TDZ)

렉시컬 스코프와 스코프 체인

렉시컬 스코프(lexical scope)는 함수가 어디서 정의되었는지로 상위 스코프가 결정되는 규칙이다(어디서 호출되었는지는 상관없다). 변수를 찾을 때는 현재 스코프 → 바깥 스코프 → 그 바깥 → ... → 전역까지 순서대로 올라가며 찾는데, 이 연결 구조를 스코프 체인(scope chain)이라 한다.

그림 4. inner() 안에서 변수를 못 찾으면 바깥(outer) → 전역 순서로 스코프 체인을 타고 올라가며 찾는다.

무슨 일이 일어나는가

  • console.log(varValue)는 var가 호이스팅되며 undefined로 초기화되어 있어 에러가 안 난다.
  • console.log(letValue)는 TDZ 구간이라 ReferenceError가 난다.
  • if 블록 안 var는 함수 전체에서 보이지만 let은 블록을 못 벗어난다.
  • const는 재할당만 금지할 뿐, 배열/객체의 내부 값은 바꿀 수 있다.

함수 선언문 vs 함수 표현식의 호이스팅

function foo() {}처럼 쓰는 함수 선언문(function declaration)은 본문 전체가 호이스팅된다 — 그래서 선언보다 위에서 호출해도 정상 동작한다. 반면 const foo = function () {}나 const foo = () => {}처럼 쓰는 함수 표현식(function expression)은 const/let 변수 규칙을 그대로 따른다 — 선언부(변수)만 호이스팅되고 TDZ에 걸려, 위에서 호출하면 에러가 난다.

function-vs-expression.js
sayHi(); // OK -- 함수 선언문은 본문까지 통째로 호이스팅됨

function sayHi() {
  console.log("hi");
}

sayBye(); // TypeError: sayBye is not a function (호이스팅은 되지만 아직 undefined)

var sayBye = function () {
  console.log("bye");
};

§4클로저

정의: 왜 생기는가

클로저(closure)는 함수와, 그 함수가 정의된 렉시컬 스코프의 조합이다[7]. 함수 안에서 함수를 만들어 반환하면, 안쪽 함수는 바깥 함수의 변수를 계속 "기억"한다. 원래대로면 바깥 함수 실행이 끝나는 순간 그 지역 변수들은 스택에서 사라져야 하지만, 안쪽 함수가 그 변수를 참조하고 있는 한 JS 엔진은 해당 스코프를 힙에 남겨두고 계속 접근할 수 있게 해준다.

그림 5. increment 함수가 makeCounter의 스코프를 계속 참조하고 있어, count가 담긴 스코프는 가비지 컬렉션되지 않고 힙에 살아남는다.

실전 용도

모듈 패턴

내부 상태를 private하게 숨기고, 필요한 함수만 공개 API로 노출한다. ESM이 널리 쓰이기 전 가장 흔한 캡슐화 기법이었다.

이벤트 핸들러

등록 시점의 값(예: 리스트의 id)을 핸들러 함수 안에 "가둬서" 나중에 클릭될 때도 정확한 값을 참조하게 만든다.

디바운스 / 쓰로틀

타이머 id 같은 상태를 클로저에 저장해두고, 함수가 여러 번 호출돼도 같은 상태를 계속 참조하며 제어한다.

React Hooks

useState, useEffect 콜백이 렌더링 시점의 값을 참조하는 것도 클로저 원리다. ch04 Hooks 심화에서 이어서 다룬다.

counterModule.js
// counterModule.js -- 클로저로 만드는 간단한 모듈 패턴
const counterModule = (function () {
  let count = 0; // 외부에서 직접 접근 불가 (private)

  function increment() {
    count += 1;
    return count;
  }

  function reset() {
    count = 0;
  }

  return { increment, reset }; // 필요한 것만 공개
})();

counterModule.increment(); // 1
counterModule.increment(); // 2
console.log(counterModule.count); // undefined -- 클로저 밖에서는 안 보인다

이벤트 핸들러에서도 같은 원리가 쓰인다. 리스트를 순회하며 버튼을 만들 때, 각 버튼의 클릭 핸들러가 "그 버튼에 해당하는 id"를 클로저로 기억하게 만들면 나중에 어떤 버튼을 눌러도 정확한 id로 동작한다.

renderButtons.js
function renderButtons(items) {
  items.forEach(function (item) {
    const btn = document.createElement("button");
    btn.textContent = item.label;
    // item.id는 이 클릭 핸들러(클로저) 안에 계속 붙잡혀 있다
    btn.addEventListener("click", function () {
      console.log("클릭된 항목 id:", item.id);
    });
    document.body.appendChild(btn);
  });
}

클로저는 메모이제이션(memoization)에도 쓰인다 — 이전에 계산한 결과를 클로저 안의 캐시 객체에 저장해두고, 같은 입력이 다시 들어오면 재계산 없이 캐시된 값을 바로 돌려준다.

memoize.js
function memoize(fn) {
  const cache = new Map(); // 클로저 안에 캐시를 가둬둔다
  return function (arg) {
    if (cache.has(arg)) return cache.get(arg);
    const result = fn(arg);
    cache.set(arg, result);
    return result;
  };
}

const slowSquare = (n) => { /* 무거운 계산이라고 가정 */ return n * n; };
const fastSquare = memoize(slowSquare);
fastSquare(5); // 계산해서 캐시에 저장
fastSquare(5); // 캐시에서 즉시 반환

반복문 + 클로저 함정

가장 흔한 클로저 버그는 반복문에서 나온다. var는 함수 스코프라서 반복문 전체가 같은 변수 하나를 공유한다. 콜백들이 나중에 실행될 시점엔 반복문이 이미 끝나 변수가 마지막 값으로 고정돼 있다. let은 매 반복마다 새로운 바인딩을 만들기 때문에 이 문제가 생기지 않는다[5].

무슨 일이 일어나는가

  • makeCounter()는 호출될 때마다 새로운 count 스코프를 만든다. counter()를 부를수록 그 스코프의 값이 누적된다.
  • var i 루프는 함수 3개가 전부 같은 i를 참조해 [3,3,3]이 나온다.
  • let j 루프는 반복마다 새 j가 생겨 [0,1,2]가 나온다.
  • debounce는 timerId를 클로저로 기억해, 연속 호출 시 이전 타이머를 계속 취소한다.

§5this와 함수

일반 함수 vs 화살표 함수

this는 함수를 어떻게 호출했는지에 따라 런타임에 결정된다[8]. obj.method()처럼 호출하면 this는 obj가 되고, 그냥 fn()처럼 호출하면 this는 undefined(strict mode 기준)가 된다. 화살표 함수는 이 규칙에서 예외다 — 자신만의 this를 갖지 않고, 정의된 위치의 this를 그대로 물려받는다(렉시컬 this).

호출 방식this가 되는 값
fn() (그냥 호출)undefined (strict mode)
obj.method()obj
fn.call(x) / fn.apply(x)x (명시적으로 지정)
fn.bind(x)()x (영구 고정)
new Fn()새로 생성된 인스턴스
화살표 함수정의된 위치의 this를 그대로 물려받음 (규칙 없음, 상속)

call / apply / bind

call(thisArg, a, b)

즉시 호출하면서 인자를 하나씩 나열해 전달한다.

apply(thisArg, [a, b])

즉시 호출하면서 인자를 배열로 묶어 전달한다.

bind(thisArg)

즉시 호출하지 않고, this가 고정된 새 함수를 반환한다[9].

메서드 분리 시 this 유실

객체에서 메서드만 꺼내서 다른 변수에 담아 호출하면 this 연결이 끊긴다. React 클래스 컴포넌트에서 onClick={this.handleClick}처럼 메서드를 참조로만 넘기면 실제 호출은 <button>이 하기 때문에 이 문제가 그대로 발생한다.

무슨 일이 일어나는가

  • person.greetNormal()은 person.으로 호출했으므로 this === person.
  • person.greetArrow()는 화살표라서 정의 시점(객체 리터럴이 만들어질 때, 즉 전역)의 this를 쓴다 — person이 아니다.
  • const detached = person.greetNormal은 함수만 떼어내 this 연결이 끊긴 채 호출된다.
  • call/apply/bind로 this를 직접 지정할 수 있다.

new 키워드와 생성자 함수의 this

함수를 new와 함께 호출하면 JS 엔진은 빈 객체를 하나 만들고, 그 객체를 this로 삼아 함수를 실행한 뒤, 특별한 반환값이 없으면 그 객체를 돌려준다. class 문법은 이 과정을 더 읽기 쉽게 감싼 문법 설탕(syntactic sugar)이다 — 내부 동작은 생성자 함수와 같다. 화살표 함수는 자신만의 this가 없기 때문에 new로 호출할 수 없다(TypeError).

strict mode 일반 함수를 그냥 fn()처럼 호출하면, strict mode(ESM/class 내부는 항상 strict mode)에서는 this가 undefined가 되고, 그렇지 않은 경우(구식 스크립트)에는 전역 객체(브라우저에서는 window)가 된다. 최신 프론트엔드 코드는 번들러가 항상 ESM으로 다루므로 this가 undefined인 쪽을 기본으로 생각하면 된다.

React에서 화살표 함수를 쓰는 이유

React 클래스 컴포넌트에서는 이벤트 핸들러를 constructor에서 bind하거나, 클래스 필드에 화살표 함수로 정의해야 했다. 함수 컴포넌트 + Hooks 방식에서는 컴포넌트 자체가 매 렌더링마다 새로 호출되는 함수이고, 그 안의 화살표 함수도 렉시컬 this 규칙을 그대로 따르기 때문에 bind가 필요 없어진다. 이것이 함수 컴포넌트가 this 문제에서 자유로운 이유다.

ClassToggle.tsx
class Toggle extends React.Component<{}, { on: boolean }> {
  constructor(props: {}) {
    super(props);
    this.state = { on: false };
    // this를 고정하지 않으면 onClick에서 this가 undefined가 된다
    this.handleClick = this.handleClick.bind(this);
  }
  handleClick() {
    this.setState({ on: !this.state.on });
  }
  render() {
    return (
      <button onClick={this.handleClick}>
        {this.state.on ? "ON" : "OFF"}
      </button>
    );
  }
}
FunctionToggle.tsx
function Toggle() {
  const [on, setOn] = useState(false);
  // 화살표 함수라서 별도 bind 없이도 this 문제 자체가 없다
  const handleClick = () => setOn((prev) => !prev);

  return (
    <button onClick={handleClick}>
      {on ? "ON" : "OFF"}
    </button>
  );
}

§6이벤트 루프

콜 스택 / Web API / 큐 / 렌더링

JS 엔진은 한 번에 하나의 코드만 실행하는 싱글 스레드다. 함수를 호출하면 콜 스택에 쌓이고, 끝나면 빠진다. setTimeout, fetch 같은 비동기 작업은 JS 엔진이 아니라 브라우저가 제공하는 Web API가 백그라운드에서 처리하고, 끝나면 결과를 콜백과 함께 큐에 넣어둔다. 이벤트 루프는 "콜 스택이 비었는지" 계속 확인하다가, 비면 큐에서 작업을 꺼내 콜 스택으로 옮기는 역할을 한다[10].

큐는 하나가 아니다. 마이크로태스크 큐(Promise.then, queueMicrotask)와 태스크 큐(매크로태스크)(setTimeout, 클릭 이벤트)가 따로 있고, 우선순위가 다르다: 콜 스택이 비면 마이크로태스크 큐를 전부 비운 뒤에야 태스크 큐에서 하나만 꺼내 실행한다.

sequenceDiagram
  participant Stack as "콜 스택"
  participant WebAPI as "Web API"
  participant Micro as "마이크로태스크 큐"
  participant Macro as "태스크 큐(매크로)"
  Stack->>Stack: "console.log('1') 실행"
  Stack->>WebAPI: "setTimeout(fn, 0) 등록"
  Stack->>Micro: "Promise.resolve().then(fn2) 등록"
  Stack->>Stack: "console.log('4') 실행"
  Note over Stack: "동기 코드 끝, 콜 스택이 빈다"
  Micro->>Stack: "마이크로태스크(fn2) 먼저 실행 -> '3'"
  WebAPI->>Macro: "타이머 만료, 콜백을 태스크 큐로 이동"
  Macro->>Stack: "콜 스택이 빌 때 태스크(fn) 실행 -> '2'"
그림 6. 동기 코드(1, 4)가 먼저 끝나고, 콜 스택이 비면 마이크로태스크(3)가 태스크(2)보다 먼저 실행된다. 출처: MDN, 이벤트 루프[10]

라이브 확인: setTimeout(0) vs Promise.then

직접 예측한 뒤 실행 버튼을 눌러 확인한다. 정답은 1 → 4 → 3 → 2다.

무슨 일이 일어나는가

  • console.log('1')은 동기 코드라 즉시 실행된다.
  • setTimeout(fn, 0)은 0ms 뒤에 실행을 "예약"만 할 뿐, 지금 당장 실행되지 않는다. Web API로 넘어가고 타이머가 끝나면 태스크 큐에 들어간다.
  • Promise.resolve().then(fn2)은 마이크로태스크 큐에 바로 등록된다.
  • console.log('4')까지가 동기 코드 블록이다. 여기까지 끝나야 콜 스택이 빈다.
  • 콜 스택이 비면 마이크로태스크 큐(3)를 먼저, 전부 비우고, 그다음에야 태스크 큐(2)에서 하나를 꺼낸다.

마이크로태스크가 태스크보다 먼저인 이유

Promise 콜백처럼 "지금 막 끝난 작업의 결과를 최대한 빨리 처리해야 하는" 작업을 마이크로태스크로 분류해, 렌더링이나 다음 매크로태스크보다 먼저 실행되도록 우선순위를 준 것이다. 대신 마이크로태스크 안에서 또 마이크로태스크를 계속 등록하면 태스크 큐와 렌더링이 무한정 밀릴 수 있다는 점은 주의해야 한다.

브라우저의 이벤트 루프

탭(창)마다 독립적인 이벤트 루프를 가지며, 렌더링(스타일/레이아웃/페인트) 단계가 큐 처리 사이사이에 끼어든다. 이 챕터에서 다룬 모델이 이 기준이다.

Node.js의 이벤트 루프

화면을 그릴 필요가 없어 렌더링 단계가 없는 대신, timers → pending callbacks → poll → check → close callbacks 같은 여러 단계(phase)로 세분화되어 있다. process.nextTick은 마이크로태스크보다도 먼저 처리되는 Node 전용 큐다.

주의 JS는 싱글 스레드이므로 콜 스택이 오래 걸리는 동기 작업(무거운 반복문 등)으로 채워져 있으면, 이벤트 루프는 그 작업이 끝날 때까지 아무 큐도 처리할 수 없다. 화면이 멈춘 것처럼 보이는 "프리징"은 대부분 이 현상이다.

긴 작업을 잘게 쪼개기

배열 10만 개를 한 번에 순회하며 무거운 계산을 하면 그동안 콜 스택이 계속 차 있어 화면이 멈춘다. 해결책은 작업을 작은 덩어리로 나누고, 덩어리 사이사이에 setTimeout(fn, 0)으로 제어권을 잠깐 이벤트 루프에 돌려주는 것이다. setTimeout은 태스크 큐에 들어가므로, 그 사이에 브라우저가 렌더링할 기회(그림 7)를 얻는다.

chunked-processing.js
function processInChunks(items, chunkSize, worker) {
  let i = 0;
  function step() {
    const end = Math.min(i + chunkSize, items.length);
    for (; i < end; i++) worker(items[i]);
    if (i < items.length) {
      setTimeout(step, 0); // 제어권을 이벤트 루프에 잠깐 돌려준다
    }
  }
  step();
}

processInChunks(hugeArray, 1000, (item) => heavyCompute(item));

requestAnimationFrame과 렌더링 타이밍

렌더링(스타일 계산 → 레이아웃 → 페인트)은 태스크 큐 항목 하나를 처리한 뒤, 다음 태스크를 처리하기 전의 틈에서 일어난다(그림 7). 애니메이션처럼 "다음 화면이 그려지기 직전"에 실행돼야 하는 코드는 setTimeout 대신 requestAnimationFrame을 쓴다. 브라우저가 실제로 화면을 그리기 바로 전에 콜백을 호출해주기 때문에, setTimeout(fn, 16)처럼 프레임 시간을 직접 추측할 필요가 없다.

마이크로태스크 기아(starvation) 그림 7에서 보듯 마이크로태스크 큐는 "완전히 빌 때까지" 반복해서 처리된다. 만약 마이크로태스크 콜백이 실행되는 도중 또 다른 마이크로태스크를 계속 등록하면(예: Promise.resolve().then()을 재귀적으로 반복), 큐가 영원히 안 비워져서 태스크 큐도, 렌더링도 무한정 밀린다. 아래는 실행하지 말고 눈으로만 봐야 하는 안티패턴이다. 
// 절대 이렇게 쓰지 말 것 -- 태스크 큐와 렌더링을 영원히 굶긴다
function loop() {
  Promise.resolve().then(loop);
}
loop();

§7비동기

콜백 지옥

콜백지옥(callback hell)은 비동기 작업이 끝난 뒤 할 일을 콜백 함수로 넘기는 방식을 중첩해서 쓸 때 생긴다. "A가 끝나면 B, B가 끝나면 C..."를 계속 중첩하면 코드가 오른쪽으로 계단처럼 밀리고 에러 처리도 각 단계마다 반복해야 한다. 이 문제를 해결하기 위해 Promise가 등장했다.

Promise: 3가지 상태

상태의미전이 후
pending아직 끝나지 않음(대기)fulfilled 또는 rejected로 한 번만 바뀜
fulfilled성공.then()의 성공 콜백 실행
rejected실패.catch() 또는 .then()의 실패 콜백 실행
 
stateDiagram-v2
  [*] --> pending
  pending --> fulfilled : "resolve(value) 호출"
  pending --> rejected : "reject(error) 호출"
  fulfilled --> [*] : "then() 성공 콜백"
  rejected --> [*] : "catch() 또는 then()의 실패 콜백"
그림 8. Promise는 pending에서 시작해 fulfilled 또는 rejected로 한 번만 전이되고, 이후에는 상태가 다시 바뀌지 않는다. 출처: MDN, Using promises[11]

.then()은 성공 시, .catch()는 실패 시, .finally()는 성공/실패와 무관하게 항상 실행된다[11]. .then()은 항상 새로운 Promise를 반환하기 때문에 계속 이어붙일(체이닝) 수 있고, 중간 어디서 에러가 나든 그 아래 첫 번째 .catch()가 잡아낸다.

promise-chaining.js
fetchUser(id)
  .then((user) => fetchPosts(user.id)) // 이전 then의 반환값을 다음 then이 이어받는다
  .then((posts) => posts.filter((p) => p.published))
  .catch((err) => {
    // fetchUser든 fetchPosts든, 위 체인 어디서 에러가 나도 여기서 한 번에 잡힌다
    console.error("실패:", err.message);
  })
  .finally(() => {
    hideLoadingSpinner(); // 성공/실패 상관없이 항상 실행
  });

Promise.all / allSettled / race / any

Promise.all

모두 성공해야 성공. 하나라도 실패하면 즉시 그 실패로 끝난다(fail-fast).

Promise.allSettled

성공/실패 상관없이 전부 끝날 때까지 기다려, 각각의 결과를 상태와 함께 배열로 준다.

Promise.race

가장 먼저 끝나는 것(성공이든 실패든) 하나만 결과로 준다.

Promise.any

가장 먼저 성공하는 것 하나를 준다. 전부 실패해야만 실패로 끝난다.

async/await와 try/catch

async 함수는 항상 Promise를 반환하고, 그 안에서 await는 Promise가 끝날 때까지 그 함수 내부의 실행만 일시정지한다(전체 프로그램이 멈추는 게 아니다). 에러 처리는 .catch() 대신 익숙한 try/catch로 할 수 있다[12].

병렬 vs 직렬 await

await를 한 줄씩 순서대로 쓰면(직렬) 앞의 작업이 끝나야 다음이 시작된다. 서로 의존하지 않는 작업이라면 Promise.all로 동시에 시작(병렬)해서 전체 시간을 크게 줄일 수 있다.

무슨 일이 일어나는가

  • serial()은 A를 다 기다린 뒤 B를 시작한다 — 총 600ms 이상.
  • parallel()은 A와 B를 동시에 시작하고 둘 다 끝나길 기다린다 — 총 300ms대.
  • Promise.allSettled는 하나가 실패해도 나머지 성공 결과를 잃지 않는다.
  • try/catch는 await가 reject된 Promise를 던지는 에러를 그대로 잡아낸다.

fetch와 AbortController

AbortController는 이미 시작된 fetch 요청을 외부에서 취소할 수 있게 해준다[13]. 컴포넌트가 언마운트되거나 타임아웃이 필요할 때 실무에서 자주 쓰는 패턴이다. ch05 상태 관리 & 데이터 페칭에서 TanStack Query가 이 취소 로직을 내부적으로 어떻게 자동화하는지 다룬다.

src/api/fetchWithTimeout.js
async function fetchWithTimeout(url, timeoutMs = 5000) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const res = await fetch(url, { signal: controller.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    if (err.name === "AbortError") {
      throw new Error("요청이 시간 초과로 취소되었습니다.");
    }
    throw err;
  } finally {
    clearTimeout(timer);
  }
}

구조분해, 스프레드/rest

구조분해할당(destructuring)은 const { name } = user처럼 값을 바로 꺼내 담는다[15]. 스프레드(spread)는 { ...obj }처럼 값을 펼쳐 새 배열/객체를 만들 때, rest는 const [first, ...rest] = arr처럼 "나머지"를 배열로 모을 때 쓴다. 둘 다 ...를 쓰지만 위치가 반대다(펼치기 vs 모으기).

옵셔널 체이닝과 nullish 병합

옵셔널 체이닝(?.)은 중첩된 값을 읽다가 중간에 null/undefined를 만나면 에러 대신 undefined를 반환한다[16]. nullish 병합(??)은 왼쪽이 null/undefined일 때만 오른쪽 기본값을 쓴다[17] — ||와 달리 0이나 빈 문자열 같은 falsy 값은 그대로 살려둔다.

흔한 실수 value || 0은 value가 0이어도 오른쪽 기본값으로 덮어써버린다("재고 0개"가 "기본값"으로 둔갑). 숫자 0이나 빈 문자열을 유효한 값으로 다뤄야 한다면 반드시 ??를 써야 한다.

Object.entries/keys/values와 정렬 주의점

객체를 순회하며 변환해야 할 때는 Object.entries(obj)로 [key, value] 쌍의 배열을 만들어 배열 메서드를 그대로 쓸 수 있다. Object.keys()/Object.values()는 각각 키만, 값만 뽑는다.

object-entries.js
const priceByCity = { Seoul: 1200, Busan: 900, Incheon: 1000 };

const rows = Object.entries(priceByCity).map(([city, price]) => ({
  city,
  price,
  label: `${city}: ${price}원`
}));

console.log(rows);
// [{city:"Seoul",...}, {city:"Busan",...}, {city:"Incheon",...}]

Array.from()은 배열이 아닌 배열 같은 값(유사 배열, iterable)을 진짜 배열로 바꿔준다. document.querySelectorAll()이 반환하는 NodeList나 Set을 배열 메서드로 다루고 싶을 때 자주 쓴다.

주의 array.sort()는 원본 배열을 직접 변경(mutate)한다 — map/filter와 다르다. React 상태나 원본 데이터를 실수로 정렬해버리지 않으려면 [...array].sort()처럼 복사본을 먼저 만들고 정렬해야 한다. 숫자 배열을 sort()에 비교 함수 없이 넘기면 문자열 기준으로 정렬되어 [10, 2, 1]이 [1, 10, 2]가 되는 것도 흔한 실수다.

실습: API 응답 → 화면용 데이터 변환

실무에서 가장 많이 하는 작업은 서버가 준 원본 데이터를 화면에 맞는 모양으로 바꾸는 것이다. 아래 예제에서 방금 배운 메서드들을 한 번에 조합해본다.

무슨 일이 일어나는가

  • .filter(u => u.age >= 19)로 성인만 남긴다.
  • .map() 안에서 구조분해로 name만 꺼내고, u.address?.city ?? '미상'로 안전하게 도시를 읽는다.
  • .reduce()로 도시별 인원수를 객체로 집계한다.

§9모듈 시스템

ESM: import/export

ESM(ES Modules)은 파일 하나를 독립된 모듈로 취급하고, export로 공개할 것을 정하고 import로 가져다 쓰는 표준 문법이다[18]. 각 모듈은 자기만의 스코프를 가지므로, 전역 변수 충돌 걱정 없이 파일을 나눠 개발할 수 있다.

named export vs default export

한 파일에서 export는 여러 개(named) 붙일 수 있고, export default는 파일당 하나만 붙일 수 있다. named export는 가져올 때 { }로 정확한 이름을 맞춰야 하고, default export는 아무 이름으로나 받을 수 있다.

src/utils/format.js
export function formatDate(date) {
  return new Intl.DateTimeFormat("ko-KR").format(date);
}

export const DEFAULT_LOCALE = "ko-KR";

export default function formatCurrency(value) {
  return new Intl.NumberFormat(DEFAULT_LOCALE, {
    style: "currency",
    currency: "KRW"
  }).format(value);
}
src/App.js
import formatCurrency, { formatDate, DEFAULT_LOCALE } from "./utils/format.js";

console.log(formatCurrency(15000));
console.log(formatDate(new Date()));
console.log(DEFAULT_LOCALE);

CommonJS와의 차이

Node.js는 오랫동안 CommonJS(CJS)를 기본 모듈 시스템으로 써왔다. 가장 큰 차이는 로딩 방식이다 — CJS의 require()는 실행 중에 동기적으로 파일을 읽어 들이지만, ESM의 import는 실행 전에 정적으로 의존 관계를 분석한다(정적 분석 가능). 이 차이 때문에 ESM에서만 다음 절의 트리셰이킹이 가능하다.

CommonJS 비교
// module.js (CommonJS)
function add(a, b) {
  return a + b;
}
module.exports = { add };

// main.js (CommonJS)
const { add } = require("./module.js");
console.log(add(1, 2));
참고 ESM은 브라우저와 최신 Node.js 모두에서 표준으로 지원되고, Vite 같은 번들러도 ESM을 기본 전제로 동작한다. 서로 다른 파일이 서로를 import하는 순환 의존(circular dependency)이 생기면 ESM은 "아직 초기화되지 않은 바인딩"을 참조할 수 있어 예상치 못한 undefined가 나올 수 있다 — 파일 간 의존 방향을 한쪽으로만 흐르게 설계하는 것이 근본적인 해법이다.

트리셰이킹과의 관계

트리셰이킹(tree shaking)은 번들러가 실제로 import되지 않는 export를 최종 번들에서 잘라내는 최적화다. ESM의 import/export가 실행 전에 정적으로 분석 가능하기 때문에 가능한 최적화이고, 동적으로 모듈을 로드하는 CommonJS에서는 이 분석이 훨씬 어렵다. Vite/Rollup이 이 최적화를 어떻게 수행하는지는 ch07 빌드 도구 & 패키지 매니저에서 다룬다.

스펙 노트 브라우저는 <script type="module">로 ESM을 네이티브 실행할 수 있다. 이때 스크립트는 자동으로 defer와 동일한 순서 보장을 갖는다[1] — §1에서 다룬 파싱/실행 순서 원리가 여기서도 그대로 적용된다.

라이브로 확인: 모듈은 왜 서로의 변수를 침범하지 못하나

실제 import/export는 이 플레이그라운드(UMD 환경)에서 쓸 수 없지만, §4에서 배운 클로저(IIFE)로 "파일마다 독립된 스코프를 갖는다"는 ESM의 핵심 성질을 그대로 재현할 수 있다. 아래에서 두 모듈이 같은 이름의 변수를 각자 가지고 있어도 서로 충돌하지 않는 것을 확인한다.

무슨 일이 일어나는가

  • moduleA와 moduleB는 각자의 IIFE 스코프 안에 독립된 count를 갖는다.
  • 전역에서는 count라는 변수 자체가 보이지 않는다 — export한 것만 노출되는 것과 같은 효과다.
  • 실제 ESM에서는 이 격리가 번들러/브라우저가 파일 단위로 자동으로 해준다.

동적 import()와 코드 스플리팅 예고

import 문은 파일 맨 위에서만 쓸 수 있지만, 함수 형태의 import()는 코드 어디서나 호출할 수 있고 그 모듈을 담은 Promise를 반환한다. 페이지가 처음 열릴 때 필요 없는 모듈(예: 특정 버튼을 눌러야만 쓰는 무거운 라이브러리)을 이렇게 나중에 불러오면, 초기 번들 크기를 줄일 수 있다. 이 기법을 번들러 레벨에서 자동화한 것이 "코드 스플리팅"이며, ch07 빌드 도구 & 패키지 매니저에서 Vite 기준으로 이어서 다룬다.

dynamic-import.js
button.addEventListener("click", async () => {
  const { formatCurrency } = await import("./utils/format.js");
  console.log(formatCurrency(15000));
});

§10이해도 점검

아래 항목을 스스로 설명할 수 있으면 이 챕터를 넘어가도 좋다. 체크 상태는 브라우저에 저장된다.

  • 브라우저가 script/defer/async 태그를 만났을 때 각각 언제 다운로드하고 언제 실행하는지 설명할 수 있다
  • 원시 타입 7가지를 말할 수 있다
  • 값 복사와 참조 복사의 차이를, 왜 "복사했는데 원본이 바뀌는지"로 설명할 수 있다
  • ===와 == 차이, NaN을 비교하는 올바른 방법을 안다
  • 얕은 복사와 깊은 복사의 차이, structuredClone의 용도를 안다
  • var/let/const의 스코프·재선언·재할당 차이와 TDZ를 설명할 수 있다
  • 호이스팅이 무엇인지, var와 let/const에서 왜 다르게 동작하는지 안다
  • 클로저의 정의와 실전 활용 사례(모듈 패턴, 디바운스 등)를 2개 이상 말할 수 있다
  • 반복문에서 var로 인한 클로저 함정을 재현하고 let으로 고칠 수 있다
  • this가 호출 방식에 따라 어떻게 달라지는지, 화살표 함수가 왜 예외인지 설명할 수 있다
  • call/apply/bind의 차이를 안다
  • 콜 스택, 마이크로태스크 큐, 태스크 큐의 실행 우선순위를 안다
  • setTimeout(0)과 Promise.then 중 무엇이 먼저 실행되는지, 그 이유를 안다
  • Promise.all / allSettled / race / any의 차이를 안다
  • 병렬 await와 직렬 await의 성능 차이를 설명할 수 있다
  • 옵셔널 체이닝(?.)과 nullish 병합(??)을 실무 코드에 쓸 수 있다
  • ESM named/default export의 차이, CommonJS와의 차이를 안다
  • falsy 값 8가지를 말할 수 있고, + 연산자의 타입 변환 규칙을 안다
  • array.sort()가 원본을 변경한다는 것을 알고, 복사 후 정렬하는 습관이 있다
