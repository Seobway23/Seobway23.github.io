CHAPTER 04

React Hooks 심화 & 렌더링 최적화

훅은 "함수 안에 상태를 저장하는 규칙"이다. 이 챕터는 그 규칙이 왜 그렇게 생겼는지부터, useState/useReducer/useRef/useEffect/useContext의 내부 동작, 리렌더링이 실제로 언제 일어나는지, useMemo·useCallback·React.memo가 언제 효과가 있고 언제 없는지, useTransition 같은 동시성 훅, 그리고 React 19의 새 훅까지 다룬다. 끝나면 "이 컴포넌트가 왜 다시 렌더됐는가"를 스스로 추적할 수 있다.

이 챕터가 끝나면 답할 수 있는 질문들: 훅은 왜 조건문 안에서 호출하면 안 되는가? useState와 useReducer 중 언제 무엇을 골라야 하는가? useEffect의 의존성 배열은 정확히 무엇을 비교하는가? 컴포넌트가 리렌더링되는 진짜 조건은 무엇이고, useMemo는 그중 무엇을 막아주는가? useTransition은 무거운 렌더링에서 실제로 무엇을 바꾸는가?

§1훅이란 무엇인가

훅(Hook)은 함수형 컴포넌트 안에서 상태나 생명주기 같은 React 기능을 사용하게 해주는 특별한 함수다. 이름이 전부 use로 시작하는 것은 우연이 아니라 규칙이다 — React가 훅 호출을 정적으로 분석하고, 린터가 규칙 위반을 잡아내려면 이름으로 구분할 수 있어야 한다.

훅의 두 가지 규칙

1. 최상위에서만 호출한다

반복문, 조건문, 중첩 함수 안에서 훅을 호출하지 않는다. 컴포넌트가 렌더링될 때마다 훅은 항상 같은 순서로 호출되어야 한다.

2. React 함수 안에서만 호출한다

일반 JavaScript 함수가 아니라 함수형 컴포넌트, 또는 다른 커스텀 훅 안에서만 호출한다.

왜 호출 순서가 중요한가

React는 각 컴포넌트 인스턴스마다 훅들의 상태를 배열(연결 리스트) 형태로 저장한다. 훅을 호출할 때마다 "몇 번째 훅인지"라는 인덱스로 그 저장소를 찾아간다. 훅에는 이름이 없다 — useState("a")든 useState("b")든 React 입장에서는 그냥 "이번 렌더의 3번째 훅 호출"일 뿐이다. 그래서 조건문으로 훅 호출을 건너뛰면, 다음 렌더에서 인덱스가 밀리면서 완전히 엉뚱한 상태를 읽어오게 된다[1].

무슨 일이 일어나는가

왼쪽 코드는 규칙을 어긴 예제다. if (name) 조건 안에 useState를 넣었다. 이름을 입력하는 순간 훅 호출 순서가 바뀌면서 상태가 뒤섞인다. 콘솔에 오류가 찍히는 것을 직접 확인해라.

  • useState — 조건부로 호출하면 React가 "Rendered more hooks than during the previous render" 류의 오류를 던진다.
  • 고치는 법은 간단하다 — 훅은 항상 최상위에 두고, 조건은 훅 안쪽 로직에서 처리한다.
흔한 실수 if, for, 이벤트 핸들러, 조기 return 이후에 훅을 호출하는 것 — 전부 같은 문제를 일으킨다. ESLint의 eslint-plugin-react-hooks가 이런 실수를 빌드 전에 잡아준다[2].

§2상태 훅 — useState와 useReducer

useState 심화

ch03에서 다룬 기본 useState 위에 세 가지를 더 알아야 실무에서 흔들리지 않는다: 지연 초기화(lazy initializer), 함수형 업데이트, 그리고 상태 배치(batching)다.

무슨 일이 일어나는가

세 버튼을 비교한다. "일반 초기화"는 expensiveCompute()가 렌더될 때마다 호출된다 — 결과가 버려지더라도 계산 자체는 실행된다. "지연 초기화"는 함수를 넘겨서 최초 1회만 계산한다.

  • useState(expensiveCompute()) — 매 렌더마다 함수를 실행하고 결과만 버림. 낭비.
  • useState(() => expensiveCompute()) — React가 최초 렌더에서만 이 함수를 호출.
  • setCount(c => c + 1) — 세 번 연속 호출해도 "이전 값 + 1"을 정확히 세 번 누적한다.
배치(batching) React 18부터는 이벤트 핸들러뿐 아니라 setTimeout, Promise, 네이티브 이벤트 안에서도 여러 setState 호출이 자동으로 하나의 리렌더로 묶인다[3]. React 17까지는 이벤트 핸들러 안에서만 배치됐다.

useReducer — 언제 useState 대신 쓰는가

useReducer는 상태 업데이트 로직이 복잡해지고, 다음 상태가 이전 상태와 액션(action)에 의해 결정되는 패턴일 때 쓴다. useState 여러 개가 서로 연관되어 함께 바뀌어야 한다면 신호다[12].

기준useStateuseReducer
상태 개수독립적인 값 1~2개서로 연관된 여러 필드
업데이트 로직단순 대입이전 상태 기반의 복잡한 분기
다음 상태 결정 방식호출부에서 직접 계산reducer 함수 한곳에 집중
테스트컴포넌트와 얽힘reducer만 순수 함수로 단위 테스트 가능
디버깅어디서 바뀌었는지 추적 어려움action 로그로 추적 쉬움

무슨 일이 일어나는가

장바구니 상태를 useReducer로 관리한다. reducer 함수 하나가 "무엇이 상태를 바꿀 수 있는가"를 전부 정의한다. 컴포넌트는 dispatch({ type: ... })만 호출할 뿐, 상태를 어떻게 바꿀지는 몰라도 된다.

  • reducer(state, action) — 순수 함수. 같은 입력이면 항상 같은 출력.
  • dispatch — "무엇을 하고 싶다"는 의도(action)만 보낸다.
  • switch (action.type) — 상태 변경 로직이 이 함수 하나에 모여있다.

§3참조 훅 — useRef와 DOM 접근

useRef가 반환하는 객체는 딱 하나, { current: 값 } 형태다. 핵심은 이것 하나다 — ref의 값을 바꿔도 컴포넌트는 리렌더링되지 않는다. useState는 "화면에 보여줄 값"을, useRef는 "화면과 상관없이 기억만 하고 싶은 값"을 담는다[13].

두 가지 용도

1. 값 보관 (리렌더 유발 안 함)

이전 값 기억, 타이머 ID 저장, 렌더 횟수 카운트처럼 "화면에 반영될 필요는 없지만 함수 재실행 사이에 유지돼야 하는 값".

2. DOM 요소 참조

<input ref={inputRef}>처럼 JSX 태그에 넘기면, 렌더링 후 inputRef.current가 실제 DOM 노드를 가리킨다. .focus() 같은 명령형 조작에 쓴다.

무슨 일이 일어나는가

같은 화면 안에서 useState 카운터와 useRef 카운터를 나란히 비교한다. state 카운터는 버튼을 누를 때마다 화면 숫자가 바뀌지만, ref 카운터는 .current만 올라가고 화면은 "리렌더 버튼"을 눌러야 갱신된다 — ref 변경 자체는 리렌더를 유발하지 않기 때문이다.

  • renderCount.current++ — 값은 바뀌지만 화면 갱신은 없다.
  • inputRef.current.focus() — 실제 DOM 메서드를 직접 호출.
  • 리렌더 버튼을 눌러야 렌더 카운트 숫자가 화면에 나타난다 — ref는 "조용히" 값을 들고 있을 뿐이다.

forwardRef와 React 19의 ref-as-prop

함수형 컴포넌트는 기본적으로 ref를 받지 못한다 — ref는 React가 예약한 특수 prop이라 props.ref로 전달되지 않는다. React 18까지는 자식 컴포넌트가 부모의 ref를 전달받으려면 React.forwardRef로 감싸야 했다. React 19부터는 함수형 컴포넌트가 ref를 일반 prop처럼 직접 받을 수 있다 — forwardRef 없이도 두 번째 인자 대신 props.ref로 받는다[4].

components/FancyInput.tsx (React 19)
// React 19: forwardRef 없이 ref를 일반 prop처럼 받는다.
function FancyInput({ placeholder, ref }: { placeholder: string; ref: React.Ref<HTMLInputElement> }) {
  return <input placeholder={placeholder} ref={ref} className="fancy" />;
}

// 사용하는 쪽
function Parent() {
  const ref = useRef<HTMLInputElement>(null);
  return <FancyInput placeholder="이름" ref={ref} />;
}
components/FancyInput.legacy.tsx (React 18 이하)
// React 18까지는 forwardRef로 감싸야 ref를 전달받을 수 있었다.
const FancyInput = React.forwardRef<HTMLInputElement, { placeholder: string }>(
  function FancyInput({ placeholder }, ref) {
    return <input placeholder={placeholder} ref={ref} className="fancy" />;
  }
);

useImperativeHandle

useImperativeHandle은 부모 컴포넌트가 ref를 통해 자식의 DOM 전체가 아니라 정해준 메서드만 쓰게 하고 싶을 때 쓴다. 예를 들어 커스텀 모달 컴포넌트가 open(), close()만 노출하고 내부 DOM 구조는 숨기는 식이다. 남용하면 명령형 코드가 늘어나므로, 정말 명령형 제어가 필요한 경우(포커스 이동, 스크롤 위치, 애니메이션 트리거)로 제한한다[5].

§4useEffect 완전 정복

언제 필요하고, 언제 필요 없는가

useEffect는 "렌더링 이후에 외부 시스템과 동기화"하기 위한 훅이다. React 공식 문서는 useEffect를 과용하지 말라고 명시한다 — props나 state로부터 값을 계산할 수 있다면 그건 Effect가 아니라 렌더링 중 계산이어야 한다[6].

Effect가 필요 없는 경우
  • props/state로부터 파생되는 값 → 렌더링 중 그냥 계산한다.
  • 사용자 이벤트에 대한 반응 → 이벤트 핸들러에서 처리한다.
  • props가 바뀔 때 state를 "리셋"하는 것 → key prop을 바꾸는 게 낫다.
Effect가 필요한 경우
  • DOM을 직접 조작해야 할 때 (React가 관리 안 하는 위젯 연동)
  • 서버 연결, 구독(subscription) 설정
  • 컴포넌트가 화면에 나타났을 때 로깅/분석 전송

의존성 배열의 의미

두 번째 인자로 넘기는 배열은 "이 값들 중 하나라도 이전 렌더와 달라졌으면(Object.is 비교) 이 effect를 다시 실행하라"는 뜻이다. 배열을 생략하면 매 렌더마다 실행, 빈 배열이면 마운트 시 1회만 실행된다.

클린업 함수

effect 함수가 함수를 return하면, React는 그것을 클린업 함수로 취급한다. 이 함수는 (1) effect가 재실행되기 직전, (2) 컴포넌트가 사라지기 직전 두 시점에 호출된다. 타이머, 이벤트 리스너, 구독을 정리하지 않으면 컴포넌트가 사라진 뒤에도 계속 실행되는 메모리 누수가 생긴다.

무슨 일이 일어나는가

1초마다 증가하는 타이머를 useEffect로 구현했다. 컴포넌트를 "끄기" 버튼으로 언마운트하면, 클린업 함수가 clearInterval을 호출해 타이머를 멈춘다. 콘솔에서 "타이머 시작"과 "타이머 정리" 로그 쌍을 확인해라.

  • setInterval — effect 안에서 타이머를 시작.
  • return () => clearInterval(id) — 클린업. 언마운트되거나 의존성이 바뀌면 호출.
  • 의존성 배열 [] — 마운트 시 1회만 타이머를 만든다.

StrictMode의 이중 실행

개발 모드에서 <React.StrictMode>는 컴포넌트를 마운트한 직후 즉시 언마운트하고 다시 마운트한다 — effect를 "실행 → 정리 → 실행"으로 한 번 더 돌려본다. 이는 버그가 아니라 의도된 개발 전용 동작으로, 클린업을 제대로 안 짜면 어떤 문제가 생기는지 미리 드러내기 위함이다[7]. 위 예제의 플레이그라운드도 내부적으로 StrictMode로 마운트되므로, 콘솔에서 "타이머 시작/정리"가 한 쌍 더 찍히는 것을 볼 수 있다.

무한 루프의 4가지 원인

원인증상해결
의존성 배열 누락매 렌더마다 effect 재실행실제로 쓰는 값만 배열에 명시
effect 안에서 의존성으로 쓰는 state를 그대로 setStateeffect → state 변경 → 리렌더 → effect… 반복함수형 업데이트(setX(prev => ...))로 의존성에서 제외
객체/배열/함수를 매 렌더마다 새로 만들어 의존성으로 사용참조가 매번 달라져 effect가 계속 재실행useMemo/useCallback으로 참조 고정, 또는 원시값만 의존성에 사용
effect 안에서 부모로부터 받은 콜백을 호출해 부모 state를 변경 → 그 결과가 다시 자식 props로 내려와 effect 재실행부모-자식 사이 무한 핑퐁실제로 동기화가 필요한지 재검토, 이벤트 핸들러로 옮길 수 있는지 확인

무슨 일이 일어나는가

버그 버전과 수정 버전을 비교한다. "버그" 탭 코드는 { name: query } 객체를 매 렌더마다 새로 만들어 의존성 배열에 넣는다 — 객체는 매번 다른 참조이므로 effect가 끝없이 재실행된다. "수정" 버튼을 눌러 원시값(query 문자열)만 의존성으로 쓰는 버전으로 바꿔볼 수 있다.

  • { name: query } — 렌더마다 새 객체. Object.is 비교에서 항상 "다름".
  • 의존성을 query(문자열)로 바꾸면 값이 실제로 같을 때 effect가 재실행되지 않는다.
  • 실행 횟수 카운터로 무한 루프 여부를 눈으로 확인한다.

§5컨텍스트 — useContext

Context는 "props를 여러 단계 아래로 계속 전달하는 것(prop drilling)"을 피하기 위한 기능이다. createContext로 만들고, <Context.Provider value={...}>로 값을 공급하며, 하위 컴포넌트는 useContext(Context)로 구독한다[14].

Context가 리렌더링을 퍼뜨리는 방식

Provider의 value가 바뀌면, 그 Context를 useContext로 구독하는 모든 하위 컴포넌트가 리렌더링된다 — 트리 구조나 memo 여부와 무관하다. value에 매 렌더마다 새로 만들어지는 객체({ user, setUser })를 넘기면, Provider를 감싼 컴포넌트가 렌더될 때마다 구독자 전체가 리렌더링된다.

state/dispatch 분리 패턴

Context 하나에 상태와 setter를 같이 담으면, 값을 "읽기만" 하는 컴포넌트도 상태가 바뀔 때마다 리렌더링된다. state Context와 dispatch(또는 setter) Context를 둘로 나누면, dispatch만 쓰는 컴포넌트(예: 버튼)는 state가 바뀌어도 리렌더링되지 않는다 — dispatch 함수 자체는 useReducer가 렌더 사이에 동일한 참조를 유지해주기 때문이다.

무슨 일이 일어나는가

state 전용 Context와 dispatch 전용 Context를 나눴다. DisplayCount는 state Context만 구독하고, IncrementButton은 dispatch Context만 구독한다. 렌더 카운터로 두 컴포넌트의 리렌더 횟수를 비교해라 — 버튼을 눌러도 IncrementButton 자신은 다시 렌더되지 않는다.

  • CountContext — 현재 값만 담당. 바뀌면 이 값을 읽는 컴포넌트만 리렌더.
  • DispatchContext — dispatch 함수는 리렌더 사이에도 항상 같은 참조.
  • 렌더 카운터(useRef)로 각 컴포넌트가 몇 번 렌더됐는지 표시.

§6성능 훅 — useMemo / useCallback / React.memo

참조 동일성이라는 전제

참조 동일성을 이해해야 세 훅이 왜 필요한지 이해할 수 있다. {} === {}는 항상 false다 — 내용이 같아도 서로 다른 객체이기 때문이다. 함수도 마찬가지다. 컴포넌트가 렌더될 때마다 그 안에서 정의한 객체/배열/함수는 매번 새로 생성된다. 

flowchart LR
  R1["렌더 1: const obj = {a:1}"] -->|"메모리 주소 0x001"| M1["obj"]
  R2["렌더 2: const obj = {a:1}"] -->|"메모리 주소 0x002"| M2["obj"]
  M1 -.->|"내용은 같지만"| EQ["obj1 === obj2 → false"]
  M2 -.-> EQ
그림 3. 내용이 같은 객체라도 렌더마다 새로 만들어지면 참조가 다르다. useMemo/useCallback은 이 참조를 렌더 사이에 고정하는 도구다.

useMemo — 계산 결과 캐시

useMemo는 "무거운 계산"을 캐시한다. 의존성이 바뀌지 않으면 계산을 건너뛰고 이전 결과(참조까지 동일한)를 그대로 돌려준다.

무슨 일이 일어나는가

입력창에 글자를 입력할 때마다 리스트를 필터링한다. useMemo 없이는 관련 없는 state(theme)가 바뀔 때도 필터링이 재실행된다. useMemo로 감싸면 items나 filter가 실제로 바뀔 때만 재계산한다.

  • useMemo(() => ..., [items, filter]) — 이 두 값이 바뀔 때만 재계산.
  • "테마 전환" 버튼을 눌러보면 필터링 로그가 안 찍히는 것을 확인할 수 있다.
  • 계산 자체가 가벼우면 useMemo의 비교 비용이 오히려 손해일 수 있다 — 무거운 계산에만 쓴다.

useCallback — 함수 참조 고정

useCallback은 함수의 참조를 고정한다. 함수 자체는 가볍게 재생성돼도 상관없지만, 그 함수를 React.memo로 감싼 자식에게 props로 넘기거나, useEffect의 의존성으로 쓸 때 참조가 계속 바뀌면 의미가 없어진다[15].

React.memo — props가 같으면 리렌더 생략

React.memo는 컴포넌트를 감싸서, props가 (얕은 비교로) 이전과 같으면 리렌더를 건너뛴다. 단, props로 넘기는 함수/객체가 매 렌더마다 새로 만들어지면 memo는 무용지물이다 — 그래서 useCallback/useMemo와 짝을 이룬다[16].

무슨 일이 일어나는가 — 효과 있는 경우 vs 없는 경우

같은 Child 컴포넌트(React.memo로 감쌈)를 두 부모가 각각 렌더링한다. "일반 콜백" 부모는 매 렌더마다 새 함수를 만들어 넘기므로 memo가 무력화된다. "useCallback 콜백" 부모는 참조를 고정해 자식 렌더를 실제로 건너뛴다. 렌더 카운터 숫자 차이를 직접 확인해라.

  • React.memo(Child) — props 얕은 비교로 리렌더 여부 결정.
  • 일반 함수 () => {} — 렌더마다 새 참조 → memo 무력화 → 자식도 매번 렌더.
  • useCallback(() => {}, []) — 참조 고정 → memo가 실제로 렌더를 막음.
판단 기준 useMemo/useCallback은 공짜가 아니다 — 의존성 비교 자체에도 비용이 든다. "무거운 계산"이거나 "memo로 감싼 자식에게 넘기는 props"일 때만 쓴다. 가벼운 계산에 습관적으로 씌우면 오히려 코드만 복잡해지고 성능 이득은 없다[8].

§7리렌더링의 원리

언제 리렌더링되는가

1. 상태 변경

setState(또는 dispatch)를 호출하면 그 컴포넌트가 리렌더링된다.

2. 부모가 렌더됨

부모 컴포넌트가 리렌더링되면, 기본적으로 모든 자식도 리렌더링된다 — 자식의 props가 하나도 안 바뀌었어도.

3. 컨텍스트 값 변경

구독 중인 Context의 value가 바뀌면 리렌더링된다 (§5 참고).

4. 훅 자체의 재실행

커스텀 훅 내부에서 useState가 바뀌어도 그 훅을 사용하는 컴포넌트가 리렌더링된다.

"부모가 렌더되면 자식도 렌더된다"의 진짜 의미

여기서 "렌더된다"는 것은 "화면이 실제로 다시 그려진다(DOM이 바뀐다)"는 뜻이 아니다. React가 그 컴포넌트 함수를 다시 호출하고, 이전 결과와 비교(재조정, reconciliation)해서 실제 DOM 변경이 필요한 부분만 반영한다는 뜻이다. 함수가 다시 호출되는 것 자체는 비용이지만, 실제 DOM 변경은 최소화된다.

children prop으로 렌더 차단하기

부모가 리렌더링될 때 자식까지 함께 리렌더링되는 것을 막는 흔한 패턴은, 자식을 children prop으로 미리 만들어서 넘기는 것이다. React는 children으로 전달된 React 엘리먼트가 이전 렌더와 같은 참조라면, 부모가 리렌더링돼도 그 부분은 다시 계산하지 않는다.

무슨 일이 일어나는가

ExpensiveChild를 두 가지 방식으로 렌더링한다. "직접 중첩"은 Counter 내부에서 <ExpensiveChild />를 직접 쓰므로, Counter가 리렌더될 때마다 같이 렌더된다. "children으로 전달"은 App이 이미 만들어둔 엘리먼트를 Counter가 props.children으로 그대로 통과시키므로, Counter의 리렌더와 무관하게 렌더 횟수가 그대로다.

  • <Counter><ExpensiveChild /></Counter> — App 레벨에서 미리 만든 엘리먼트.
  • Counter는 {children}을 그대로 렌더링만 할 뿐, 새로 만들지 않는다.
  • 두 렌더 카운터를 비교해 direct 방식만 계속 증가하는 것을 확인.

§8동시성 훅 — useTransition / useDeferredValue

동시성 기능은 "느린 렌더링" 자체를 없애주지 않는다. 대신 급하지 않은 렌더링을 낮은 우선순위로 표시해서, 사용자 입력 같은 급한 업데이트가 먼저 반영되도록 순서를 조정한다.

그림 4. 일반 업데이트는 순서대로 처리되어 무거운 렌더링이 입력을 막지만, startTransition으로 감싸면 급한 업데이트가 먼저 처리되고 무거운 렌더링은 낮은 우선순위로 밀린다. 출처: react.dev

useTransition

useTransition은 특정 상태 업데이트를 "긴급하지 않음(transition)"으로 표시한다. isPending으로 그 업데이트가 아직 처리 중인지 알 수 있다[17].

useDeferredValue

useDeferredValue는 startTransition을 직접 호출할 수 없는 상황(예: 이미 부모가 내려준 값)에서, 그 값의 "지연된 사본"을 만들어 같은 효과를 낸다[18].

무슨 일이 일어나는가 — 입력 반응성 체감

일부러 무거운 리스트(2,000개 항목, 각 항목마다 인위적 지연 계산)를 필터링한다. "일반 필터링" 탭에서는 타이핑할 때마다 화면 전체가 멈칫거린다(입력창 반영이 늦다). "useTransition 적용" 탭은 입력창 자체는 즉시 반응하고, 무거운 리스트 갱신만 isPending 표시와 함께 살짝 늦게 따라온다.

  • startTransition(() => setFilter(v)) — 리스트 갱신을 낮은 우선순위로.
  • isPending — transition이 진행 중임을 화면에 표시.
  • 입력 필드의 value는 별도 state로 즉시 갱신 — 이것이 핵심이다.
startTransition 단독 사용 useTransition이 반환하는 isPending이 필요 없다면, 훅이 아닌 startTransition 함수를 react에서 직접 import해서 컴포넌트 밖에서도 쓸 수 있다[9].

§9React 19 신규 훅

아래 네 가지는 React 19에서 새로 추가됐다. 플레이그라운드가 React 18 UMD로 동작하는 관계로 여기서는 정적 코드로 개요만 소개한다 — 실제 프로젝트(React 19 + 번들러 환경)에서 확인해라.

use

use는 Promise를 "언래핑"하거나 Context를 읽는 함수다. 다른 훅과 달리 조건부로 호출 가능하다는 점이 특이하다 — 훅이 아니라 특수 함수로 분류된다[10].

components/Comments.tsx (React 19, 개념 예시)
import { use } from "react";

function Comments({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  // use는 Promise가 처리(resolve)될 때까지 컴포넌트를 Suspense로 일시 중단시킨다.
  const comments = use(commentsPromise);
  return <ul>{comments.map((c) => <li key={c.id}>{c.text}</li>)}</ul>;
}

useOptimistic

useOptimistic은 서버 요청이 끝나기 전에 예상되는 결과를 먼저 보여준다 — "좋아요" 버튼을 누르면 응답을 기다리지 않고 즉시 하트가 채워지는 UX가 대표적이다[10].

components/LikeButton.tsx (React 19, 개념 예시)
import { useOptimistic } from "react";

function LikeButton({ likes, onLike }: { likes: number; onLike: () => Promise<void> }) {
  const [optimisticLikes, addOptimisticLike] = useOptimistic(
    likes,
    (current) => current + 1
  );

  async function handleClick() {
    addOptimisticLike(); // 서버 응답 전에 즉시 +1 표시
    await onLike();      // 실패 시 React가 이전 값으로 자동 되돌림
  }

  return <button onClick={handleClick}>좋아요 {optimisticLikes}</button>;
}

useActionState

useActionState는 폼 제출 같은 "action 함수"의 결과 상태와 진행 여부를 함께 관리한다[10].

components/SignupForm.tsx (React 19, 개념 예시)
import { useActionState } from "react";

async function signupAction(prevState: { error: string | null }, formData: FormData) {
  const email = formData.get("email") as string;
  if (!email.includes("@")) return { error: "이메일 형식이 아닙니다" };
  await fetch("/api/signup", { method: "POST", body: formData });
  return { error: null };
}

function SignupForm() {
  const [state, formAction, isPending] = useActionState(signupAction, { error: null });
  return (
    <form action={formAction}>
      <input name="email" />
      <button disabled={isPending}>가입</button>
      {state.error && <p>{state.error}</p>}
    </form>
  );
}

useFormStatus

useFormStatus는 상위 <form>의 제출 상태를, props로 내려받지 않고 자식 컴포넌트에서 직접 읽는다. 재사용 가능한 "제출 버튼" 컴포넌트를 만들 때 유용하다[10].

components/SubmitButton.tsx (React 19, 개념 예시)
import { useFormStatus } from "react-dom";

// form 내부에서만 의미가 있다 — form 밖에서는 pending이 항상 false.
function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "제출 중…" : "제출"}</button>;
}

§10커스텀 훅 만들기

커스텀 훅은 "여러 컴포넌트에서 반복되는, 훅을 사용하는 로직"을 함수로 뽑아낸 것이다. 이름이 use로 시작해야 React가 훅 규칙을 적용한다. 기준은 단순하다 — 같은 상태/effect 조합을 두 번째로 복사-붙여넣기 하려는 순간이 커스텀 훅으로 뽑을 신호다.

useToggle

무슨 일이 일어나는가

불리언 상태를 뒤집는 로직을 훅으로 뽑았다. toggle()과 명시적으로 값을 지정하는 setValue()를 둘 다 제공한다.

  • useToggle(initial) — [value, toggle, setValue] 반환.
  • 모달, 아코디언, 다크모드 스위치 등에서 반복되는 패턴을 하나로 통합.

useDebounce

무슨 일이 일어나는가

입력값이 바뀔 때마다 즉시가 아니라, 타이핑이 멈춘 뒤 일정 시간이 지나야 반영되는 값을 만든다. 검색어 자동완성처럼 매 타이핑마다 API를 호출하고 싶지 않을 때 쓴다.

  • useDebounce(value, delay) — 내부에서 useEffect + setTimeout + 클린업을 사용.
  • 타이핑을 멈추지 않으면 이전 타이머가 계속 클린업되고 새로 설정된다.

useLocalStorage

무슨 일이 일어나는가

useState와 똑같이 쓰지만, 값이 localStorage에도 함께 저장된다. 새로고침해도 값이 유지된다(이 페이지를 실제로 새로고침해서 확인해도 좋다).

  • useLocalStorage(key, initial) — 지연 초기화로 최초 1회만 localStorage를 읽는다.
  • 값이 바뀔 때마다 useEffect가 localStorage.setItem을 호출.

useFetch

무슨 일이 일어나는가

네트워크 요청의 로딩/에러/데이터 상태를 하나로 관리한다. 실제 서비스에서는 TanStack Query가 캐싱까지 포함해 이 역할을 대신하지만, 원리를 보기 위해 fetch 기반으로 20줄 내외로 직접 구현한다. 여기서는 외부 API 대신 타이머로 흉내낸 가짜 요청을 쓴다.

  • AbortController — 컴포넌트가 사라지거나 url이 바뀌면 이전 요청을 취소해 레이스 컨디션을 막는다.
  • cancelled 플래그 — 클린업 이후 도착한 응답을 상태에 반영하지 않도록 방어.

§11React Compiler

React Compiler는 빌드 단계에서 컴포넌트와 훅 코드를 분석해, 값이 실제로 바뀌지 않으면 재계산을 건너뛰도록 자동으로 메모이제이션 코드를 삽입한다. React 규칙(§1의 두 규칙, 순수 함수로서의 컴포넌트)을 지키는 코드를 전제로 동작한다[11].

무엇을 자동화하는가

자동화되는 것

§6에서 손으로 작성한 useMemo/useCallback/React.memo 패턴을 컴파일러가 정적 분석으로 유추해 자동 삽입한다.

여전히 손으로 써야 하는 것

§4의 useEffect(외부 시스템 동기화), §8의 useTransition/useDeferredValue(렌더 우선순위 제어)는 컴파일러의 대상이 아니다 — "무엇을, 언제" 실행할지는 여전히 개발자가 결정한다.

사실 확인 React Compiler는 규칙을 위반하는 코드(순수하지 않은 렌더, 조건부 훅 호출)를 감지하면 해당 컴포넌트에는 최적화를 적용하지 않고 건너뛴다. 즉 §1의 훅 규칙을 지키는 것이 컴파일러 최적화의 전제 조건이다[11]. 이 챕터 작성 시점 기준 공식 문서가 안정적으로 배포되는 최신 상태를 따랐으며, 세부 옵션명은 프로젝트 도입 시 공식 문서로 재확인해라.

§12이해도 점검

  • 훅이 "호출 순서"로 식별된다는 것을 설명하고, 왜 조건문 안에서 호출하면 안 되는지 말할 수 있다.
  • useState의 지연 초기화와 함수형 업데이트를 언제 써야 하는지 안다.
  • useState와 useReducer 중 어느 것을 쓸지 표(§2)의 기준으로 판단할 수 있다.
  • useRef가 리렌더링을 유발하지 않는 이유와, DOM 참조 용도를 구분해 설명할 수 있다.
  • React 19의 ref-as-prop과 forwardRef의 차이를 안다.
  • useEffect가 필요 없는 상황(react.dev 기준)을 최소 2가지 말할 수 있다.
  • 클린업 함수가 호출되는 두 시점을 안다.
  • 무한 루프의 4가지 원인 중 최소 2가지를 원인-해결 짝으로 설명할 수 있다.
  • Context 값이 바뀌면 어떤 컴포넌트가 리렌더링되는지, 그리고 state/dispatch 분리가 왜 도움이 되는지 안다.
  • 참조 동일성 개념으로 useMemo/useCallback/React.memo가 왜 필요한지 설명할 수 있다.
  • "부모가 렌더되면 자식도 렌더된다"가 DOM 변경이 아니라 함수 재호출을 의미한다는 것을 안다.
  • children prop으로 렌더를 차단하는 패턴을 이해했다.
  • useTransition이 실제로 무엇의 우선순위를 조정하는지 설명할 수 있다.
  • React 19의 use, useOptimistic, useActionState, useFormStatus를 언제 쓰는지 개요를 안다.
  • React Compiler가 자동화하는 범위와, 여전히 손으로 판단해야 하는 부분을 구분할 수 있다.
