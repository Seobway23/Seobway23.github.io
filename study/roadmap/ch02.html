CHAPTER 02

TypeScript 타입 시스템

TypeScript는 JavaScript 문법 위에 타입 검사기를 얹은 언어다. 이 챕터에서는 기본 타입부터 제네릭, 유틸리티 타입, React와의 결합, 실전 tsconfig까지 실무에서 매일 마주치는 순서로 다룬다.

Narrowing Generic Utility Types tsconfig React + TS

이 챕터는 다음 질문에 답한다. JavaScript 대신 TypeScript를 쓰면 정확히 무엇이 달라지는가? any, unknown, never는 왜 서로 다른 타입인가? 유니온 타입으로 분기할 때 TypeScript는 어떻게 타입을 좁혀나가는가? 제네릭은 왜 필요하고 useState<T>는 내부에서 어떻게 동작하는가? 마지막으로 tsconfig.json의 strict 계열 옵션들은 각각 무엇을 막아주는가?

§1왜 타입인가

JavaScript는 동적 타입 언어다. 변수 x가 지금 문자열인지 숫자인지 객체인지는 그 줄이 실행되는 순간에야 정해진다. 그래서 user.address.city처럼 중첩된 값을 읽다가 address가 undefined이면, 코드를 작성할 때는 아무 문제 없어 보이다가 사용자가 그 버튼을 누르는 순간 화면이 하얗게 멈추는 식의 런타임 에러가 발생한다.

TypeScript는 JavaScript 문법을 그대로 쓰면서, 코드를 실행하기 전 단계인 컴파일 타임에 정적 타입 검사를 수행하는 검사기를 하나 더 붙인 것이다. user.address.city를 쓰기 전에 이미 에디터가 빨간 줄로 "address는 undefined일 수 있다"고 알려준다. 버그를 찾는 시점이 "사용자가 발견"에서 "개발자가 타이핑하는 순간"으로 앞당겨지는 것, 이것이 타입을 쓰는 근본적인 이유다[1].

그림 1. 같은 버그라도 JavaScript는 실행 후(런타임)에, TypeScript는 실행 전(컴파일 타임)에 드러난다. 출처: TypeScript Handbook — The Basics

타입은 컴파일 후 사라진다 (Type Erasure)

여기서 흔히 오해하는 지점이 있다. TypeScript의 타입은 브라우저나 Node.js가 실행하는 최종 코드에는 존재하지 않는다. 컴파일 과정에서 타입 주석과 interface 같은 타입 전용 문법은 전부 걷어내지고, 순수한 JavaScript만 남는다. 이 현상을 타입 소거(type erasure)라고 부른다[1].

그림 2. 타입은 컴파일 시점의 도구일 뿐, 실행 시점의 JavaScript에는 남지 않는다. 출처: TypeScript Handbook — The Basics

무슨 일이 일어나는가

오른쪽 코드는 interface User와 타입 주석을 쓴 정상적인 TypeScript다. 이 플레이그라운드는 Babel로 타입만 지우고 실행하기 때문에, 타입을 어긴 bad 값을 넣어도 컴파일 에러 없이 그대로 돈다 — 실제 프로젝트의 에디터/tsc라면 bad 줄에 빨간 줄이 떴을 것이다[15].

  • interface User — 객체의 형태를 이름 붙여 정의한다.
  • function greet(user: User) — 매개변수가 반드시 User 형태여야 한다고 선언.
  • const bad: any = ... — any는 타입 검사를 끄는 탈출구다 (§2에서 다룬다).
흔한 실수 타입을 "런타임에 값을 검증해주는 기능"으로 착각하는 것. TypeScript는 컴파일 타임 도구다. 외부 API 응답처럼 실제로 런타임에 형태를 확인해야 하는 값은 zod 같은 런타임 검증 라이브러리나 수동 검증 함수가 따로 필요하다.
요약 TypeScript는 JavaScript + 정적 타입 검사기다. 버그를 실행 후가 아니라 작성 중에 잡아준다. 단, 타입은 컴파일 후 사라지므로(type erasure) 런타임 값 검증과는 별개다.

§2기본 타입

Primitive 타입

JavaScript의 원시값 타입은 TypeScript에서도 그대로 소문자로 쓴다: string, number, boolean, null, undefined, symbol, bigint[2]. 변수 선언 뒤 : 타입을 붙이는 것을 타입 주석이라 하는데, 초기값만으로 타입을 알 수 있으면 TypeScript가 스스로 알아내는 타입 추론(type inference)이 동작하므로 매번 타입을 적을 필요는 없다.

primitives.ts
let id: number = 1;
let name: string = "지수";
let done: boolean = false;

// 초기값이 있으면 타입 추론이 동작한다 — 아래 세 줄은 주석이 없어도 타입이 고정된다.
let inferredId = 1;        // number로 추론
let inferredName = "지수";  // string으로 추론

배열과 튜플

같은 타입이 여러 개 들어가는 배열은 string[] 또는 Array<string>로 쓴다. 길이와 각 자리의 타입이 고정된 배열은 튜플(tuple)이라 부르고 [string, number]처럼 쓴다. React의 useState가 [값, setter] 형태의 배열을 반환하는 것이 대표적인 튜플 사용 예다[17].

any · unknown · never · void

이 네 타입은 이름이 비슷해 보이지만 역할이 완전히 다르다. 표로 정리한다.

타입의미다른 값 대입바로 프로퍼티/메서드 사용언제 쓰나
any타입 검사를 완전히 끈다가능 (아무 타입이나)가능 (검사 안 함, 위험)가급적 쓰지 않는다. 외부 라이브러리 타입이 아예 없을 때 최후 수단
unknown"안전한 any" — 뭐든 담을 수 있지만 사용 전 확인 필요가능불가 (narrowing 후에만)외부 입력값(API 응답, JSON.parse 결과)의 초기 타입
never절대 발생할 수 없는 값의 타입불가 (대입할 값 자체가 없음)해당 없음무한 루프/항상 예외 던지는 함수, switch의 exhaustive check
void함수가 의미 있는 값을 반환하지 않음undefined만 사실상 가능해당 없음콜백/이벤트 핸들러처럼 "실행만 하고 끝"인 함수의 반환 타입
unknown-vs-any.ts
function handleAny(v: any) {
  v.toUpperCase(); // 컴파일 통과 — 하지만 v가 숫자면 런타임에 터진다.
}

function handleUnknown(v: unknown) {
  // v.toUpperCase(); // 컴파일 에러: unknown은 바로 메서드를 쓸 수 없다.
  if (typeof v === "string") {
    v.toUpperCase(); // 좁혀졌으므로(narrowing) 이제 안전하다.
  }
}

리터럴 타입과 as const

string보다 더 좁게, 정확한 값 하나를 타입으로 쓸 수도 있다. 이를 리터럴 타입(literal type)이라 하고, 보통 유니온으로 묶어 "가능한 값의 목록"을 표현한다. as const는 배열/객체 리터럴을 "그 값 그대로" 고정해서, 넓은 타입(string[])이 아니라 좁은 리터럴 튜플 타입으로 추론되게 만든다.

무슨 일이 일어나는가

오른쪽 코드는 튜플, 리터럴 유니온, as const를 한 번에 보여준다.

  • type Pair = [string, number] — useState 반환값과 같은 형태의 튜플.
  • type Direction = "up" | "down" | ... — 이 네 문자열 외에는 컴파일 에러.
  • as const — 배열을 string[]이 아니라 readonly ["up","down",...]로 고정한다.
흔한 실수 as const가 붙은 배열/객체는 읽기 전용이 된다. DIRECTIONS.push(...)나 DIRECTIONS[0] = "x"는 컴파일 에러다. 값을 바꿀 배열이라면 as const를 쓰면 안 된다.
요약 any는 검사를 끈다(위험), unknown은 안전한 미확인 값이다, never는 발생 불가능한 값, void는 "반환값 없음"이다. 리터럴 타입 + as const로 정확한 값 목록을 타입으로 표현할 수 있다.

§3객체 타입

interface vs type

객체 형태를 이름 붙여 정의하는 방법은 두 가지다: interface와 type alias. 기능이 많이 겹치지만 차이가 있다.

관점interfacetype
선언 병합(declaration merging)가능 — 같은 이름을 여러 번 선언하면 자동 병합불가 — 같은 이름 재선언은 에러
확장interface B extends A교차 타입 type B = A & {...}
유니온 · 튜플 표현불가가능 (type T = A | B)
객체 형태 표현적합, 에러 메시지가 더 읽기 쉬움적합
일반적 관례공개 API, React 컴포넌트 props유니온, 매핑드 타입, 함수 시그니처

둘 중 하나가 "정답"은 아니다[4]. 팀 컨벤션을 따르되, 유니온이 필요한 순간에는 type이 필수다.

선택적 프로퍼티와 readonly

프로퍼티 이름 뒤에 ?를 붙이면 있어도 되고 없어도 되는 선택적 프로퍼티가 된다. readonly는 객체가 생성된 뒤 해당 프로퍼티를 재할당하지 못하게 막는다 (컴파일 타임 한정).

인덱스 시그니처

객체의 키를 미리 다 알 수 없을 때(예: 색상 팔레트, 다국어 메시지 맵) 쓰는 인덱스 시그니처(index signature)는 [key: string]: T 형태로 쓴다. 키가 정해져 있다면 인덱스 시그니처보다 Record<Key, T>(§6)가 더 안전하다.

함수 타입

함수도 하나의 타입으로 표현할 수 있다[6]. 콜백 prop의 타입을 지정할 때 특히 자주 쓴다.

function-type.ts
type BinaryOp = (a: number, b: number) => number;

const add: BinaryOp = (a, b) => a + b;
const multiply: BinaryOp = (a, b) => a * b;

무슨 일이 일어나는가

선택적 프로퍼티(discount?), readonly, 인덱스 시그니처를 한 예제에서 확인한다.

  • readonly id — 생성 후 item.id = 2는 컴파일 에러 (아래 주석 참고).
  • discount?: number — 없어도 되는 값이라 p.discount ?로 먼저 확인한다.
  • [key: string]: string — 어떤 문자열 키가 와도 값은 문자열이어야 한다.
흔한 실수 인덱스 시그니처는 존재하지 않는 키에 접근해도 타입 상으로는 값이 있다고 가정한다. colors["존재안함"]은 string으로 추론되지만 실제로는 undefined다. §9의 noUncheckedIndexedAccess 옵션이 이 문제를 막아준다.
요약 interface는 선언 병합이 되고 확장이 쉬워 공개 API/props에 적합, type은 유니온·매핑드 타입까지 표현 가능해 더 범용적이다. ?는 선택적, readonly는 재할당 금지, 인덱스 시그니처는 동적인 키를 표현한다.

§4유니온 · 교차 · 타입 좁히기

유니온 타입(union type)은 "이거 아니면 저거"(A | B), 교차 타입(intersection type)은 "이것도 저것도 전부"(A & B)를 뜻한다. 실무에서는 유니온을 압도적으로 더 자주 쓴다 — API 응답이 성공/실패 중 하나이거나, prop이 문자열이거나 함수이거나 하는 식이다.

문제는 string | number 타입의 값에 .toUpperCase()를 바로 부를 수 없다는 것이다 (number에는 그 메서드가 없으므로). 조건문으로 "지금 이 값은 확실히 string이다"를 증명해야 하는데, 이 과정을 타입 좁히기(narrowing)라고 부른다[3].

typeof · in · instanceof

가장 많이 쓰는 세 가지 좁히기 방법이다.

연산자무엇을 검사하나주로 쓰는 상황
typeof v === "string"primitive 타입 구분string | number | boolean 좁히기[20]
"key" in v객체에 특정 프로퍼티가 있는지공통 필드가 없는 객체 유니온 좁히기[18]
v instanceof Klass특정 클래스의 인스턴스인지Error 하위 클래스 구분, DOM 요소 구분[19]

커스텀 타입 가드 함수

위 세 연산자로 표현이 안 되는 복잡한 조건은 직접 타입 가드(type guard) 함수를 만들 수 있다. 반환 타입을 value is Foo로 적으면, 이 함수가 true를 반환한 분기에서 TypeScript가 자동으로 타입을 좁혀준다.

무슨 일이 일어나는가

  • typeof id === "string" — 그 블록 안에서 id는 string으로 확정.
  • "meow" in animal — Cat 전용 필드 존재 여부로 Cat | Dog를 나눈다.
  • e instanceof ApiError — 클래스 상속 관계로 에러 종류를 구분한다.
  • function isCat(a): a is Cat — 커스텀 타입 가드. 호출부에서 if (isCat(a))로 쓰면 좁혀진다.
flowchart TD
  V["값의 타입: string | number | Cat | Dog"] --> Q1{"typeof v === 'string'?"}
  Q1 -- "예" --> R1["v: string으로 좁혀짐"]
  Q1 -- "아니오" --> Q2{"'meow' in v?"}
  Q2 -- "예" --> R2["v: Cat으로 좁혀짐"]
  Q2 -- "아니오" --> R3["v: number | Dog로 좁혀짐"]
그림 3. narrowing은 조건문을 통과할 때마다 유니온에서 가능성을 하나씩 제거해 나가는 과정이다. 출처: TypeScript Handbook — Narrowing

판별 유니온으로 API 응답 모델링

실무에서 가장 유용한 패턴은 판별 유니온(discriminated union)이다. API 요청 상태를 loading / success / error 세 가지 형태의 객체로 표현하고, 공통 필드 status의 값으로 나머지 필드가 무엇인지 컴파일러가 스스로 추론하게 만든다. 아래는 이 패턴으로 만든 살아있는 예제다 — 버튼을 눌러 상태를 바꿔보면 화면이 그에 맞춰 바뀐다. 

stateDiagram-v2
  [*] --> loading
  loading --> success: 데이터 도착
  loading --> error: 요청 실패
  success --> loading: 재요청
  error --> loading: 재시도
그림 4. ApiState는 status 필드로 구분되는 세 형태를 오간다. 각 상태에서만 존재하는 필드(data, message)는 그 상태일 때만 접근 가능하다. 출처: TypeScript Handbook — Narrowing

무슨 일이 일어나는가

  • ApiState<T> — status가 "success"일 때만 data 필드가 존재한다는 것을 타입으로 강제한다.
  • switch (state.status) — 각 case 블록 안에서 state는 해당 케이스 타입으로 좁혀진다.
  • default의 never — 모든 케이스를 다 처리했다면 여기 도달할 값이 없어야 한다. 새 상태를 추가하고 처리를 빼먹으면 여기서 컴파일 에러가 난다 (exhaustive check).
흔한 실수 판별 필드 없이 { data?: T; message?: string } 처럼 옵셔널 필드로만 상태를 표현하면 "data도 message도 없는" 애매한 상태가 타입으로 허용된다. 반드시 status 같은 리터럴 판별 필드를 둔다.
요약 유니온은 narrowing 없이는 좁은 메서드를 못 쓴다. typeof/in/instanceof/커스텀 타입 가드로 좁히고, 여러 형태의 상태를 다룰 땐 공통 리터럴 필드를 둔 판별 유니온 + switch + never exhaustive check가 정석이다.

§5제네릭

왜 필요한가

"숫자 상자"와 "문자열 상자"를 각각의 interface로 만들면 코드가 중복되고, any로 퉁치면 상자 안에 뭐가 들었는지 타입 정보가 사라진다. 제네릭(generic)은 "지금은 어떤 타입인지 모르지만, 넣는 타입과 나오는 타입이 항상 같다"를 표현하는 도구다. 함수의 매개변수가 값을 받는 것처럼, 제네릭의 타입 파라미터(type parameter)는 타입을 받는다[5].

extends 제약과 기본값

<T extends { id: number }>처럼 extends를 쓰면 "아무 타입이나"가 아니라 "적어도 이 형태는 갖춘 타입"으로 제약을 걸 수 있다. <T = string>처럼 기본값도 지정할 수 있어, 타입 인자를 생략하면 string이 쓰인다. 

flowchart TB
  T["제네릭 정의: Box(T)"] --> S["호출: Box(string)"]
  T --> N["호출: Box(number)"]
  T --> U["호출: Box(User)"]
그림 5. 하나의 제네릭 정의가 호출 시점에 넣는 타입에 따라 여러 구체 타입으로 구체화된다. 출처: TypeScript Handbook — Generics

무슨 일이 일어나는가

  • identity<T>(value: T): T — 넣은 타입 그대로 돌려준다는 것을 타입으로 보장.
  • findById<T extends { id: number }> — id 필드가 있는 타입만 허용.
  • useMiniState<T> — React의 useState가 실제로 하는 일을 축소 구현한 것. 초기값의 타입 T가 값과 setter의 타입을 동시에 고정한다.
흔한 실수 .tsx 파일에서 화살표 함수로 제네릭 컴포넌트를 선언할 때 const Box = <T>(props: ...) => ...는 JSX 태그로 오인되어 파싱 에러가 난다. <T,>처럼 콤마를 붙이거나 <T extends unknown>로 우회한다.
요약 제네릭은 타입 중복 없이 "입력 타입과 출력 타입의 관계"를 표현한다. extends로 제약을 걸고 기본값을 줄 수 있으며, React의 useState<T>()도 결국 이 메커니즘으로 값과 setter 타입을 함께 고정한다.

§6유틸리티 타입

유틸리티 타입(utility type)은 기존 타입을 변형해 새 타입을 만드는 내장 도구다. 매번 직접 매핑드 타입을 작성하지 않아도 된다[7].

유틸리티하는 일실무에서 언제 쓰나
Partial<T>모든 프로퍼티를 선택적으로수정 폼(PATCH) — 일부 필드만 보낼 때
Required<T>모든 프로퍼티를 필수로기본값 병합 후 "이제 전부 채워졌다"를 표현할 때
Readonly<T>모든 프로퍼티를 readonly로state, 설정 객체처럼 불변으로 다루고 싶은 값
Pick<T, K>지정한 키만 뽑기큰 엔티티에서 화면에 필요한 필드만 추릴 때
Omit<T, K>지정한 키만 제외비밀번호처럼 민감한 필드를 API 응답 타입에서 뺄 때
Record<K, T>키 집합 K, 값 타입 T인 객체role → label처럼 고정된 키의 맵을 만들 때
ReturnType<F>함수의 반환 타입 추출타입을 따로 안 적어도 함수 시그니처에서 파생시킬 때
Parameters<F>함수의 매개변수 타입들을 튜플로 추출래퍼 함수를 만들 때 원본과 동일한 인자 타입을 재사용
Awaited<P>Promise<T>에서 T만 추출async 함수의 실제 반환값 타입을 알고 싶을 때
NonNullable<T>null/undefined 제거narrowing 이후 값이 확실히 있다고 확정할 때

무슨 일이 일어나는가

  • Omit<User, "password"> — API로 내려보낼 안전한 사용자 타입.
  • Partial<Pick<User, "name"|"email">> — 유틸리티는 이렇게 조합해서 쓸 수 있다.
  • Record<Role, string> — role 3종에 대한 라벨 맵, 키를 빠뜨리면 컴파일 에러.
  • ReturnType<typeof f> / Parameters<typeof f> — 값이 아니라 함수의 타입에서 추출하므로 typeof가 필요하다.
흔한 실수 ReturnType<createUser>처럼 함수 값을 그대로 넣는 것. 유틸리티 타입은 타입만 받으므로 반드시 ReturnType<typeof createUser>처럼 typeof로 먼저 값을 타입으로 바꿔야 한다.
요약 유틸리티 타입은 직접 매핑드 타입을 작성하지 않고도 기존 타입을 변형한다. 조합도 가능하다(Partial<Pick<...>>). 함수의 타입을 다룰 때는 typeof가 짝으로 따라온다.

§7심화 타입 난이도: 심화

지금 몰라도 된다 이 절의 내용은 라이브러리 타입 정의나 고급 유틸리티 타입을 직접 만들 때 필요하다. 처음 학습한다면 "이런 게 있다" 정도만 알고 넘어가도 실무 코드를 작성하는 데 지장 없다. 필요할 때 다시 찾아오면 된다.

아래 여섯 가지는 "타입에서 새로운 타입을 뽑아내는" 도구들이다[10]. §6의 유틸리티 타입들도 내부적으로는 이 도구들의 조합으로 만들어져 있다.

문법하는 일
keyof T객체 타입 T의 키들을 리터럴 유니온으로 뽑는다[8]
typeof value변수/값으로부터 거꾸로 타입을 뽑는다 (타입 위치에서 사용)[9]
T["key"]인덱스드 액세스 — 특정 프로퍼티 하나의 타입만 꺼낸다
A extends B ? X : Y조건부 타입(conditional type)[11]
infer R조건부 타입 안에서 특정 위치의 타입을 변수처럼 뽑아 R로 이름 붙인다
{ [K in keyof T]: ... }매핑드 타입(mapped type) — 모든 키를 순회하며 새 타입을 만든다[12]
`on${Capitalize<E>}`템플릿 리터럴 타입(template literal type) — 문자열 패턴을 타입으로[13]
advanced-types.ts
interface User {
  id: number;
  name: string;
  email: string;
}

// keyof: 객체 타입의 키들을 유니온 리터럴 타입으로
type UserKey = keyof User; // "id" | "name" | "email"

// typeof: 값(변수)으로부터 타입을 역으로 추출
const config = { host: "localhost", port: 8787 };
type Config = typeof config; // { host: string; port: number }

// 인덱스드 액세스: 타입의 특정 프로퍼티 타입만 꺼내기
type UserName = User["name"]; // string

// 조건부 타입 + infer: 함수의 반환 타입을 조건부로 추출
type ReturnOf<F> = F extends (...args: any[]) => infer R ? R : never;
type Result = ReturnOf<() => number>; // number

// 매핑드 타입: 모든 프로퍼티를 optional + readonly로
type ReadonlyPartial<T> = { readonly [K in keyof T]?: T[K] };

// 템플릿 리터럴 타입: 문자열 패턴을 타입으로 검증
type EventName = `on${Capitalize<"click" | "change">}`; // "onClick" | "onChange"
요약 keyof/typeof/인덱스드 액세스는 "기존 타입에서 조각을 뽑아내고", 조건부 타입 + infer는 "조건에 따라 다른 타입을 고르고", 매핑드 타입은 "모든 프로퍼티를 규칙대로 변환"하고, 템플릿 리터럴 타입은 "문자열 패턴 자체를 타입으로" 만든다.

§8React와 TypeScript

props 타입

함수 컴포넌트의 props는 보통 컴포넌트 이름 뒤에 Props를 붙인 interface로 정의하고, 구조 분해 매개변수에 바로 타입을 붙인다.

children과 ReactNode

JSX로 감싼 자식 요소를 받는 prop은 children이고, 타입은 React.ReactNode다. 문자열, 숫자, JSX, 배열, null까지 렌더링 가능한 모든 값을 포괄한다[16].

이벤트 타입

React의 이벤트 핸들러는 브라우저 네이티브 이벤트가 아니라 React가 감싼 합성 이벤트를 받는다. 자주 쓰는 조합을 표로 정리한다.

이벤트타입예시
onClickReact.MouseEvent<HTMLButtonElement>버튼 클릭 핸들러
onChange (input)React.ChangeEvent<HTMLInputElement>e.target.value로 입력값 읽기
onSubmitReact.FormEvent<HTMLFormElement>e.preventDefault() 후 제출 처리
onKeyDownReact.KeyboardEvent<HTMLInputElement>e.key === "Enter" 분기
onChange (select)React.ChangeEvent<HTMLSelectElement>드롭다운 선택값 읽기

useRef 타입

DOM 요소를 참조하는 useRef는 useRef<HTMLInputElement>(null)처럼 제네릭으로 요소 타입을 지정한다. 초기값이 null이므로 current는 HTMLInputElement | null 타입이 되고, 사용할 때 옵셔널 체이닝(?.)이 필요하다.

제네릭 컴포넌트

리스트 컴포넌트처럼 "어떤 타입의 배열이든 받는" 컴포넌트는 컴포넌트 자체를 제네릭으로 만든다. 단, .tsx 파일에서는 §5에서 언급한 <T,> 콤마 규칙을 지켜야 JSX와 구분된다.

무슨 일이 일어나는가

  • CardProps — children: React.ReactNode로 어떤 JSX든 감쌀 수 있게 한다.
  • handleChange(e: React.ChangeEvent<HTMLInputElement>) — e.target.value가 string으로 타입 검사된다.
  • useRef<HTMLInputElement>(null) — inputRef.current?.focus()로 안전하게 접근.
  • handleSubmit(e: React.FormEvent<HTMLFormElement>) — e.preventDefault()로 새로고침 방지.
GenericList.tsx
interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

// .tsx 파일에서는 <T,> 처럼 콤마를 붙여야 JSX 태그와 구분된다.
function List<T,>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map((item, i) => <li key={i}>{renderItem(item)}</li>)}</ul>;
}

// 사용하는 쪽에서 T가 User로 자동 추론된다.
<List items={users} renderItem={(u) => u.name} />
흔한 실수 onChange 핸들러의 이벤트 타입을 Event로 적는 것. React의 이벤트는 브라우저 네이티브 Event가 아니라 React.ChangeEvent<T> 같은 합성 이벤트 타입이며, 요소 타입 T를 빠뜨리면 e.target.value에서 타입 에러가 난다.
요약 props는 interface + 구조 분해, children은 React.ReactNode, 이벤트는 요소 타입을 포함한 React.XxxEvent<Element>, DOM 참조는 useRef<Element>(null) 패턴을 따른다.

§9tsconfig.json 실전

tsconfig.json은 타입 검사의 엄격도와 모듈 해석 방식을 결정한다. Vite 기반 React 프로젝트에서 실제로 자주 켜는 옵션 위주로 정리한다[14].

옵션효과권장값
strictnoImplicitAny, strictNullChecks 등 엄격 검사 묶음을 한 번에 켠다true
noUncheckedIndexedAccessobj[key] 같은 인덱스 접근 결과 타입에 자동으로 | undefined를 더한다true
moduleResolution: "bundler"Vite 같은 번들러가 실제로 모듈을 찾는 방식과 TS의 타입 해석 방식을 일치시킨다"bundler"
paths@/* 같은 임포트 별칭을 TS가 인식하게 한다 (런타임 별칭은 Vite 설정에서 별도로 맞춰야 함)프로젝트 구조에 맞게
isolatedModules파일 하나만 보고도 안전하게 변환 가능한 문법만 허용한다 (Babel/esbuild처럼 파일 단위로 동작하는 도구와의 호환)true
verbatimModuleSyntaximport/export를 쓴 그대로 남기고, 타입만 가져올 때는 import type을 강제한다true
tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",

    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,

    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,

    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  },
  "include": ["src"]
}
흔한 실수 paths에 별칭을 등록하고 vite.config.ts의 resolve.alias를 빠뜨리는 것. tsconfig.json의 paths는 타입 검사와 에디터 자동완성에만 쓰이고, 실제 빌드 시 경로 치환은 번들러(Vite)가 따로 해야 한다.
요약 strict는 기본으로 켠다. noUncheckedIndexedAccess는 인덱스 접근의 숨은 undefined를 잡아준다. moduleResolution: "bundler"는 Vite와의 해석 방식 불일치를 없앤다. isolatedModules + verbatimModuleSyntax는 Babel/esbuild 같은 파일 단위 트랜스파일러와 안전하게 맞물리게 한다.

§10이해도 점검

다음 항목을 스스로 설명할 수 있으면 이 챕터를 이해한 것이다.

  • 타입이 "컴파일 타임 도구"이고 런타임에는 사라진다는 것(type erasure)을 예를 들어 설명할 수 있다.
  • any, unknown, never, void의 차이를 표 없이도 말할 수 있다.
  • as const가 배열/객체의 타입을 어떻게 좁히는지 설명할 수 있다.
  • interface와 type을 언제 각각 선택해야 하는지 근거를 댈 수 있다.
  • 인덱스 시그니처의 위험(존재하지 않는 키도 타입상 값이 있다고 나옴)을 설명할 수 있다.
  • typeof/in/instanceof로 유니온 타입을 좁히는 코드를 직접 쓸 수 있다.
  • 판별 유니온 + switch + never exhaustive check 패턴을 직접 구현할 수 있다.
  • 제네릭 함수를 하나 직접 만들고 extends 제약을 걸 수 있다.
  • 언제 Pick, Omit, Partial, Record를 쓸지 실무 상황과 연결지어 말할 수 있다.
  • ReturnType/Parameters를 쓸 때 typeof가 왜 필요한지 설명할 수 있다.
  • React props에서 children: React.ReactNode가 무엇을 의미하는지 안다.
  • 이벤트 핸들러 타입을 요소 종류에 맞게 (React.ChangeEvent<HTMLInputElement> 등) 고를 수 있다.
  • strict, noUncheckedIndexedAccess, moduleResolution: "bundler"가 각각 무엇을 막아주는지 설명할 수 있다.
