CHAPTER 03

React 기초 — 컴포넌트와 상태

React는 "화면을 상태의 함수로 그린다"는 하나의 아이디어를 지킨다. 이 챕터는 왜 DOM을 직접 조작하는 대신 그렇게 하는지부터, JSX가 실제로 무엇으로 바뀌는지, 함수 컴포넌트와 props, useState로 상태를 다루는 법, 이벤트 처리, 리스트 렌더링과 key가 왜 필요한지(실제 버그 재현 포함), 폼을 다루는 법, 상태를 어디에 둘지 결정하는 기준까지 다룬다. 끝나면 할 일 목록(Todo) 앱을 처음부터 설명할 수 있다.

JSX Component props useState key Controlled Component React 19

이 챕터가 끝나면 답할 수 있는 질문들: document.createElement로 다 되는데 왜 React를 쓰는가? JSX는 실제로 브라우저에서 어떻게 실행되는가? props와 state는 무엇이 다르고, 왜 props는 함수 안에서 바꾸면 안 되는가? setCount(count + 1)을 세 번 불러도 왜 한 번만 반영되는가? 리스트를 렌더링할 때 key에 배열 인덱스를 쓰면 정확히 어떤 버그가 생기는가? 상태는 컴포넌트 트리의 어디에 둬야 하는가?

§1React를 왜 쓰나

DOM을 다루는 가장 원초적인 방법은 document.createElement로 요소를 직접 만들고, appendChild로 붙이고, innerHTML이나 textContent로 내용을 바꾸는 것이다. 이 방식 자체에는 문제가 없다 — 실제로 브라우저가 화면을 그리는 유일한 방법이고, React도 결국 내부에서는 이 API들을 호출한다. 문제는 화면에 표시할 상태가 여러 곳에 흩어져 있고, 그 상태가 바뀔 때마다 어떤 DOM 노드를 어떻게 고쳐야 하는지 사람이 일일이 기억해야 한다는 데 있다.

바닐라 DOM 조작의 문제

아래는 "항목 추가 / 전체 삭제" 기능을 document.createElement[19]와 innerHTML[20]만으로 구현한 예제다. 버튼을 눌러 직접 동작을 확인해라. 코드 자체는 짧지만, 화면에 보여줄 목록이 하나 더 생기거나 항목마다 삭제 버튼이 붙는 순간 "어느 노드를 언제 갱신할지"를 관리하는 코드가 기하급수적으로 늘어난다.

무슨 일이 일어나는가

버튼의 onclick 속성 안에 직접 DOM API를 호출하는 코드를 넣었다. 실무에서는 이렇게 쓰지 않지만, "React 없이 화면을 갱신하려면 정확히 무엇을 해야 하는가"를 가장 적나라하게 보여준다.

  • document.createElement("div") — 새 DOM 노드를 메모리에 만든다. 아직 화면에는 없다.
  • list.appendChild(item) — 만든 노드를 실제 트리에 붙여야 비로소 화면에 보인다.
  • list.innerHTML = "" — 문자열을 통째로 다시 파싱시켜 자식 노드를 전부 지운다.
  • 새 항목이 몇 번째인지, 몇 개가 있는지 사람이 직접 계산해야 한다(list.children.length).

React 버전 — 상태를 선언하면 화면은 알아서 따라온다

같은 기능을 React로 옮기면 코드가 짧아지는 게 핵심이 아니다. 핵심은 "몇 번째 항목을 어떻게 그릴지"를 더 이상 계산하지 않는다는 점이다. 상태(state)인 배열 items만 갖고 있으면, "이 배열을 화면에 어떻게 그릴지"는 items.map(...) 한 줄로 항상 선언한다. 배열이 바뀌면 React가 알아서 실제 DOM의 차이만 계산해 반영한다.

무슨 일이 일어나는가

버튼을 누르면 items 배열만 바꾼다. "어떤 DOM 노드를 추가할지"는 한 줄도 쓰지 않았다 — items.map이 항상 배열 전체를 기준으로 화면을 다시 "선언"하고, React가 실제로 바뀐 부분만 DOM에 반영한다.

  • useState([]) — 빈 배열로 시작하는 상태 하나.
  • setItems(prev => [...prev, ...]) — 기존 배열을 복사해 새 항목을 뒤에 붙인 새 배열을 만든다(원본을 직접 수정하지 않는다 — §4에서 이유를 다룬다).
  • items.map(...) — "이 배열이 곧 이 화면이다"를 코드로 그대로 옮긴 것.
이 예제에서 key로 index를 써도 괜찮은 이유 여기서는 배열 끝에만 추가하고, 지울 땐 전부 지운다 — 항목의 순서가 절대 바뀌지 않는다. index를 key로 써도 안전한 경우다. 중간 삽입·삭제·정렬이 있는 리스트에서 index를 쓰면 실제로 버그가 생긴다. §6에서 그 버그를 직접 재현한다.

§1 요약 — 바닐라 DOM 조작은 "무엇을 어떻게 바꿀지"를 매번 계산해야 하지만, React는 상태만 선언하면 화면 갱신을 대신 계산해준다. 다음 절부터는 그 선언에 쓰는 문법(JSX)과 단위(컴포넌트)를 하나씩 다룬다.

§2JSX

JSX는 새로운 언어가 아니다. Babel 같은 컴파일러가 빌드 시점에 React.createElement 함수 호출로 바꿔주는 문법일 뿐이다. 브라우저는 JSX를 절대 직접 실행하지 않는다 — 항상 변환된 JavaScript를 실행한다[14].

JSX가 React.createElement로 변환되는 과정

아래 두 코드는 같은 것이다. 위는 사람이 쓰는 JSX, 아래는 Babel이 실제로 만들어내는 코드다. <h1 className="title">처럼 생긴 태그는 사실 React.createElement("h1", { className: "title" }, ...)라는 함수 호출의 문법적 설탕(syntactic sugar)이다.

JSX (작성한 코드)
function Greeting({ name }) {
  return (
    <h1 className="title">
      안녕, {name}
    </h1>
  );
}
컴파일 결과 (Babel 변환 후)
function Greeting({ name }) {
  return React.createElement(
    "h1",
    { className: "title" },
    "안녕, ",
    name
  );
}
참고 Vite처럼 최신 빌드 도구는 실제로는 React.createElement 대신 react/jsx-runtime의 jsx() 함수를 자동으로 사용하는 "automatic JSX runtime"을 쓴다. 결과물의 세부 형태만 다를 뿐, "JSX는 함수 호출로 변환된다"는 핵심 개념은 동일하다.

className/htmlFor, 중괄호 표현식

JSX는 HTML과 똑같아 보이지만 결국 JavaScript이기 때문에, JavaScript 예약어와 충돌하는 HTML 속성 이름은 바꿔 써야 한다. class는 JS 예약어라 className을, for는 htmlFor를 쓴다. 중괄호 { } 안에는 어떤 JavaScript 표현식이든 넣을 수 있다 — 변수, 함수 호출, 삼항 연산자, 심지어 다른 JSX까지[15].

HTMLJSX이유
class="box"className="box"class는 JS 예약어
for="email"htmlFor="email"for는 JS 예약어(for문)
onclick="..."onClick={fn}문자열이 아니라 함수 참조를 전달
style="color:red"style={{ color: "red" }}객체로 전달(카멜케이스 속성명)

무슨 일이 일어나는가

중괄호 안에 변수(name), 함수 호출(score.toFixed(1)), 삼항 연산자를 그대로 썼다. JSX 텍스트 자리에 { }를 열면 그 안은 다시 JavaScript다.

  • className={isPass ? "ok" : "fail"} — 조건에 따라 클래스 이름을 바꾼다.
  • {score.toFixed(1)} — 함수 호출 결과를 그대로 화면에 꽂는다.
  • 중괄호 안에 if문이나 for문은 못 넣는다 — 표현식(expression)만 가능하다(문(statement)은 안 된다).

조건부 렌더링 — &&와 삼항 연산자

JSX 안에서 if문을 직접 쓸 수 없기 때문에, 조건에 따라 다른 내용을 그리려면 표현식으로 된 조건부 문법을 쓴다. 참/거짓 둘 중 하나만 보여줄 땐 삼항 연산자(? :), "조건이 참일 때만 보여주고 거짓이면 아무것도 안 보여준다"는 &&를 쓴다[13].

흔한 실수 {count && <p>...</p>}처럼 쓰면 count가 0일 때 false가 아니라 숫자 0이 그대로 화면에 찍힌다. && 왼쪽은 반드시 boolean으로 만들어라 — {count > 0 && <p>...</p>}처럼.

Fragment

컴포넌트는 값 하나만 반환할 수 있어서, 형제 요소 여러 개를 감쌀 부모 태그가 필요할 때가 많다. 그런데 불필요한 <div>를 추가하면 CSS 레이아웃이 깨지거나 의미 없는 DOM 노드가 늘어난다. Fragment는 실제 DOM에는 아무 흔적도 남기지 않으면서 여러 요소를 하나로 묶어준다[17].

무슨 일이 일어나는가

로그인 여부(state)에 따라 버튼 텍스트, &&로 조건부 문단, 삼항 연산자로 두 문단 중 하나를 보여준다. 최상위를 <>...</>(Fragment 축약 문법)로 감싸 불필요한 <div> 없이 여러 요소를 반환한다.

  • <> ... </> — React.Fragment의 축약형. 실제 DOM에 남지 않는다.
  • {loggedIn && <p>...</p>} — 참일 때만 렌더링.
  • {loggedIn ? <p>A</p> : <p>B</p>} — 둘 중 하나만 렌더링.

§2 요약 — JSX는 React.createElement 호출로 변환되는 문법일 뿐이다. className/htmlFor 같은 이름 변경, 중괄호 표현식, &&/삼항 조건부 렌더링, Fragment는 모두 "JSX도 결국 JavaScript"라는 사실에서 나온다.

§3컴포넌트와 props

함수 컴포넌트

React 19에서 컴포넌트를 만드는 방법은 사실상 함수 컴포넌트 하나뿐이다. 이름이 대문자로 시작하는 함수를 만들고, JSX를 반환하면 그게 컴포넌트다. React는 소문자로 시작하는 태그(<div>)는 HTML 요소로, 대문자로 시작하는 태그(<Card>)는 직접 만든 컴포넌트로 구분한다 — 이 대소문자 규칙은 강제 사항이다.

props 전달과 구조분해

props는 컴포넌트에 넘기는 매개변수다. <Avatar name="서지수" />처럼 속성으로 넘기면, Avatar 함수는 { name: "서지수" }라는 객체 하나를 첫 번째 인자로 받는다. 매번 props.name이라고 쓰는 대신, 구조분해할당으로 function Avatar({ name })처럼 바로 꺼내 쓰는 게 관례다.

children

컴포넌트 태그 사이에 넣은 내용은 children이라는 특별한 prop으로 자동으로 전달된다. <Card>여기 내용</Card>라고 쓰면, Card 함수는 props.children으로 "여기 내용"을 받는다. children이 있어야 "이 컴포넌트로 다른 걸 감쌀 수 있는" 구조가 만들어진다.

props는 읽기 전용

규칙 컴포넌트는 자신이 받은 props를 절대 수정하면 안 된다. props.name = "다른 이름" 같은 코드는 React의 단방향 데이터 흐름을 깨고, 부모가 모르는 사이 자식이 값을 바꾸는 예측 불가능한 버그로 이어진다. props를 기반으로 새 값이 필요하면 부모에게 "이렇게 바꿔줘"라고 요청하는 함수(콜백)를 prop으로 받아 호출해라. §8에서 이 패턴을 다룬다.

컴포넌트 합성(composition) vs 상속

React에는 클래스 상속으로 컴포넌트 기능을 확장하는 방법이 없다. 대신 합성(composition) — 작은 컴포넌트를 조합해 큰 화면을 만드는 방식만 쓴다. "Card라는 틀을 상속받아 ProfileCard를 만든다"가 아니라, "Card 컴포넌트 안에 Avatar 컴포넌트를 끼워 넣는다"는 식이다.

합성 (React 방식)

<Card><Avatar /></Card> — Card는 Avatar가 뭔지 몰라도 된다. children 자리에 뭐가 들어오든 감싸기만 한다. 재사용성이 높고 관계가 단순하다.

상속 (React에서 쓰지 않음)

class ProfileCard extends Card — 부모 클래스의 내부 구현을 자식이 알아야 하고, 계층이 깊어질수록 어떤 메서드가 어디서 오는지 추적하기 어려워진다. React 공식 문서도 상속 대신 합성을 권장한다[1].

무슨 일이 일어나는가

Card는 title과 children을 받아 틀만 그린다. 내용이 무엇인지는 전혀 모른다 — 그래서 Avatar를 넣을 수도, 그냥 문단을 넣을 수도 있다. 이게 합성이다.

  • function Card({ title, children }) — props를 즉시 구조분해.
  • <Card title="프로필">...내용...</Card> — 태그 사이 내용이 children이 된다.
  • props는 읽기만 한다 — Card 내부 어디에서도 title을 재할당하지 않는다.

§3 요약 — 컴포넌트는 props를 입력으로 받는 함수다. props는 구조분해로 꺼내 쓰고, 절대 수정하지 않는다. children과 합성(composition)으로 컴포넌트를 조합하며, 상속은 쓰지 않는다.

§4state와 useState

왜 그냥 변수는 안 되나

컴포넌트 함수 안에 let count = 0;을 두고 count++를 해도 코드는 실행된다. 하지만 화면은 바뀌지 않는다. 이유는 단순하다 — React는 함수 안의 지역 변수가 바뀐 것을 알 방법이 없다. 화면을 다시 그리려면(리렌더링) React가 "이 컴포넌트를 다시 실행해야 한다"는 사실을 알아야 하는데, 그 신호를 주는 유일한 방법이 useState가 돌려주는 setter 함수를 호출하는 것이다. useState는 값을 "React가 추적하는 저장소"에 넣어주고, 그 값을 바꾸는 공식 통로(setter)를 함께 준다[16][18].

무슨 일이 일어나는가

왼쪽 카운터는 일반 변수를 증가시킨다. 콘솔에 값은 제대로 찍히지만 화면 숫자는 그대로다 — 리렌더링이 일어나지 않았기 때문이다. 오른쪽은 useState를 써서 즉시 화면이 갱신된다.

  • let plainCount = 0 — 컴포넌트가 처음 실행될 때 딱 한 번만 0으로 초기화된다.
  • 버튼을 눌러도 리렌더링이 일어나지 않으니, 이 변수는 계속 초기화된 상태로 "보인다"(실제로는 클로저에 값이 남지만 화면엔 반영 안 됨).
  • useState(0) — [stateCount, setStateCount] 쌍을 돌려준다. setStateCount를 호출해야만 리렌더링이 예약된다.

상태 갱신은 비동기적으로 배치된다

setState를 호출한다고 그 자리에서 즉시 값이 바뀌고 화면이 다시 그려지는 게 아니다. React는 이벤트 핸들러 안에서 일어난 여러 번의 상태 갱신을 모아 한 번에 처리하는 배치(batching)를 수행한다[2]. 그래서 한 핸들러 안에서 setCount(count + 1)를 세 번 불러도, count는 그 핸들러가 시작될 때의 "스냅샷" 값을 계속 참조하기 때문에 결과적으로 +1만 반영된다[3].

함수형 업데이트

"이전 상태를 기준으로 다음 상태를 계산"하고 싶다면 setCount(count + 1) 대신 setCount(c => c + 1) 형태의 함수형 업데이트를 써라. React는 큐에 쌓인 업데이트 함수들을 순서대로 실행하며 항상 "직전 갱신까지 반영된 최신 값"을 넘겨주기 때문에, 몇 번을 호출하든 정확히 그 횟수만큼 반영된다.

무슨 일이 일어나는가

두 버튼 모두 "3번 더하기"를 시도한다. 직접 계산 버전은 클릭 한 번에 count가 1만 증가하고, 함수형 업데이트 버전은 3이 증가한다. 왜 다른지 아래 노트를 읽어라.

  • setCount(count + 1) — count는 이 핸들러가 시작된 시점의 값에 고정된 스냅샷이다. 세 줄 다 "0 + 1"을 계산해 큐에 넣는다.
  • setCount(c => c + 1) — "이전 값에 1을 더하라"는 지시를 큐에 넣는다. React가 순서대로 실행하며 매번 최신 값을 넘긴다.

객체/배열 상태는 불변으로 갱신한다

상태가 객체나 배열이면 state.age = 21이나 state.push(x)처럼 직접 수정(mutate)하면 안 된다. React는 리렌더링 여부를 판단할 때 "이전 상태와 새 상태가 서로 다른 객체(참조)인지"를 비교한다. 원본을 직접 고치면 참조가 그대로라서 React가 변화를 감지하지 못해 화면이 갱신되지 않을 수 있다. 그래서 스프레드 문법(...)으로 항상 새 객체·새 배열을 만들어 불변성을 지킨다[4][5].

무슨 일이 일어나는가

생일 버튼은 객체를 통째로 새로 만들면서 age만 바꾼다({ ...prev, age: prev.age + 1 }). 태그 추가/삭제는 배열을 slice/스프레드로 다시 만든다. 원본 profile, tags 객체는 어디서도 직접 수정하지 않는다.

  • { ...prev, age: prev.age + 1 } — prev의 모든 속성을 복사한 새 객체를 만들고 age만 덮어쓴다.
  • [...prev, `태그${prev.length + 1}`] — prev 배열의 모든 원소를 복사한 새 배열 뒤에 하나를 더한다.
  • prev.slice(1) — 원본을 건드리지 않고 첫 원소를 뺀 새 배열을 반환한다.
흔한 실수 — 배열 메서드가 원본을 바꾸는지 항상 확인해라 JavaScript 배열 메서드 중 일부는 원본 배열을 직접 변형(mutate)한다. 상태로 쓰는 배열에는 절대 이 메서드들을 직접 호출하면 안 된다[5].
피해야 할 것 (원본 변형)대신 쓸 것 (새 배열 반환)

arr.pop(), arr.shift()arr.slice(0, -1), arr.slice(1)

§4 요약 — 화면을 갱신하려면 반드시 useState의 setter를 호출해야 한다. 한 핸들러 안의 여러 setState는 배치되므로, 이전 값을 기준으로 갱신할 땐 함수형 업데이트를 쓴다. 객체/배열 상태는 항상 새로 만들어서 교체한다.

§5이벤트 처리

React의 onClick, onChange, onSubmit 같은 속성은 실제 DOM 이벤트 이름(onclick)과 비슷하지만 카멜케이스로 쓰고, 문자열이 아니라 함수를 전달한다는 점이 다르다. 핸들러가 받는 이벤트 객체는 브라우저 고유의 이벤트가 아니라 React가 감싼 합성 이벤트(SyntheticEvent)다[6]. preventDefault(), target 같은 익숙한 속성/메서드는 그대로 쓸 수 있다.

이벤트 객체와 preventDefault

폼의 기본 동작(제출 시 페이지 새로고침)을 막으려면 onSubmit 핸들러에서 e.preventDefault()를 호출한다. 이걸 빼먹으면 SPA(Single Page Application)에서 폼을 제출할 때마다 페이지 전체가 새로고침된다.

핸들러에 인자 넘기기

onClick={handleClick}처럼 함수 참조를 그대로 넘기면 인자를 넘길 수 없다. 특정 값을 함께 넘기려면 화살표 함수로 한 번 감싸서 onClick={() => handleClick(id)} 형태로 쓴다. 이렇게 하면 클릭이 일어날 때만 handleClick(id)가 실행되고, 렌더링 시점에 곧바로 실행되는 실수(onClick={handleClick(id)})를 피할 수 있다.

무슨 일이 일어나는가

과일 버튼마다 () => setPicked(f)로 감싸 각기 다른 값을 넘긴다. 제출 버튼은 e.preventDefault()로 실제 폼 제출(페이지 새로고침)을 막는다.

  • onClick={() => setPicked(f)} — 클릭 시점에만 f 값으로 호출된다.
  • function handleSubmit(e) { e.preventDefault(); ... } — 합성 이벤트의 preventDefault.
  • onSubmit={handleSubmit} — 폼 자체의 제출 이벤트에 연결.

§5 요약 — React 이벤트 핸들러는 합성 이벤트를 받는다. 기본 동작을 막으려면 e.preventDefault(), 인자를 넘기려면 화살표 함수로 감싸 호출한다.

§6리스트 렌더링과 key

map으로 렌더링

배열을 화면에 그릴 때는 {items.map(item => <div>...</div>)} 형태로 각 원소를 JSX로 변환한다. 이때 React는 배열의 각 항목에 key라는 특별한 prop을 요구한다. key는 화면에 보이지 않지만, React가 리스트의 항목을 식별하는 유일한 단서다[12].

key가 없거나 index를 쓰면 생기는 버그

key를 안 주면 콘솔에 경고가 뜨고, React는 어쩔 수 없이 배열 인덱스를 key로 대신 쓴다. 문제는 항목이 리스트 중간에 삽입·삭제되거나 순서가 바뀌는 경우다. index는 항목의 정체성이 아니라 "몇 번째 자리인가"일 뿐이라, 같은 인덱스라도 그 자리에 있던 실제 항목은 렌더링마다 달라질 수 있다. 아래 예제로 직접 재현해라.

실습 방법 각 입력창에 아무 글자나 입력한 뒤 "맨 앞에 새 항목 추가"를 눌러라. "key로 index 사용" 체크박스가 켜진 상태에서는 방금 입력한 글자가 엉뚱한 행으로 옮겨간 것처럼 보인다 — 실제로는 글자가 옮겨간 게 아니라, React가 기존 <input> DOM 노드를 "같은 key(같은 인덱스)"로 착각해 재사용하면서 라벨만 바뀐 것이다. 체크박스를 끄고(=id를 key로 사용) 같은 동작을 해보면 입력값이 원래 행에 그대로 남는다.

무슨 일이 일어나는가

<input>에는 value를 주지 않았다(비제어 상태) — 그래서 입력값은 오직 실제 DOM 노드 안에만 존재한다. key가 index면, 맨 앞에 새 행이 생겨도 React는 "0번 슬롯, 1번 슬롯..."의 기존 DOM을 그대로 재사용하고 라벨 텍스트만 새로 써넣는다. 그 결과 입력 내용이 담긴 DOM 노드가 다른 라벨 아래로 밀려난다.

  • key={useIndex ? i : row.id} — 체크박스로 두 key 전략을 즉시 비교.
  • id는 데이터가 생성될 때 부여된 고유하고 안정적인 값이라, 항목이 이동해도 항상 같은 항목을 가리킨다.
  • index는 배열 안에서의 위치일 뿐이라, 앞에 뭔가 삽입되면 기존 항목들의 index가 전부 밀린다.

재조정(reconciliation)

React가 이전 렌더링 결과와 새 렌더링 결과를 비교해 실제 DOM에 최소한의 변경만 적용하는 과정을 재조정(reconciliation)이라고 부른다[7]. 리스트를 비교할 때 React는 "같은 key를 가진 항목은 같은 항목"이라고 가정하고 DOM 노드를 재사용한다. key가 안정적이지 않으면(index처럼 위치에 따라 바뀌면) 이 가정이 깨지면서 위 예제 같은 버그가 생긴다.

React가 리스트를 비교하는 절차를 단순화하면 다음과 같다. 이전 렌더의 자식들과 새 렌더의 자식들을 key 기준으로 짝짓는다. 같은 key를 가진 자식이 있으면 "같은 컴포넌트 인스턴스"로 간주해 기존 DOM 노드와 내부 state를 그대로 재사용하고, 바뀐 props만 갱신한다. 짝이 없는 새 key는 새 DOM 노드를 만들고, 이전에 있었지만 새 렌더에 없는 key는 DOM에서 제거한다. 이 과정 전체가 "몇 번째 자리인가"가 아니라 "어떤 key인가"를 기준으로 이루어지기 때문에, key 선택이 곧 "이 항목의 정체성을 무엇으로 정의할 것인가"를 결정하는 것과 같다.

§6 요약 — key는 React가 리스트 항목의 정체성을 추적하는 유일한 단서다. 순서가 바뀔 수 있는 리스트에는 반드시 데이터에 이미 있는 안정적인 id를 key로 쓰고, index는 순서가 절대 바뀌지 않을 때만 쓴다.

§7폼과 제어 컴포넌트

controlled vs uncontrolled

제어 컴포넌트는 <input value={state} onChange={...} />처럼 값을 항상 state에서 가져오고, 사용자가 입력할 때마다 state를 갱신해 "지금 화면에 보이는 값 = state 값"을 강제하는 방식이다. 반대로 비제어 컴포넌트는 value를 지정하지 않아 입력값이 DOM 안에만 존재한다(§6의 key 버그 예제가 비제어 input을 썼다). 폼 검증이나 실시간 반응이 필요하면 대부분 제어 컴포넌트를 쓴다[8].

제어 컴포넌트비제어 컴포넌트
값의 위치React stateDOM 노드 내부

다른 입력값과 연동쉽다 — 같은 state 객체로 관리번거롭다

여러 입력을 한 핸들러로 처리

입력창마다 별도 핸들러를 만드는 대신, <input name="email" />처럼 name 속성을 붙이고 e.target.name, e.target.value를 이용해 하나의 handleChange 함수로 여러 필드를 처리할 수 있다. 객체 상태를 계산된 속성 이름([name]: value)으로 갱신하는 패턴이다.

유효성 검사 기초

가장 단순한 검증은 렌더링 중에 조건식(정규식, 길이 비교 등)을 계산해두고, 조건에 맞지 않을 때만 에러 메시지를 조건부 렌더링하는 것이다. "제출을 한 번이라도 시도했는지(touched)"를 별도 state로 두면, 사용자가 아직 아무것도 안 쳤을 때부터 에러가 보이는 걸 막을 수 있다.

무슨 일이 일어나는가

이메일/닉네임 두 입력창이 하나의 handleChange를 공유한다. form.email, form.nickname은 항상 화면에 보이는 값과 동일하다(제어 컴포넌트). 제출을 시도해야만 에러 문구가 나타난다.

  • const { name, value } = e.target; — 어떤 입력창에서 발생했는지, 무슨 값인지 한 번에 꺼낸다.
  • { ...prev, [name]: value } — name이 "email"이면 email 속성만, "nickname"이면 nickname 속성만 갱신.
  • 정규식(/^[^\s@]+@[^\s@]+\.[^\s@]+$/)으로 이메일 형식을 대략적으로 검사한다(완벽한 검증은 서버에서도 반드시 해야 한다).

§7 요약 — 제어 컴포넌트는 값을 state에서 가져오고 onChange로 갱신해, "지금 보이는 값 = state"를 강제한다. name 속성과 계산된 속성 이름을 쓰면 여러 입력을 하나의 핸들러로 처리할 수 있다.

§8상태 끌어올리기와 컴포넌트 트리 설계

어디에 상태를 둘지 결정하는 기준

상태 끌어올리기(lifting state up)는 새로운 API가 아니라 "상태를 어디에 선언할지"에 대한 설계 원칙이다[9]. 기준은 단순하다.

상황상태 위치
이 상태를 쓰는 컴포넌트가 하나뿐이다그 컴포넌트 내부에 useState로 둔다
형제 컴포넌트 여러 개가 같은 값을 공유·동기화해야 한다가장 가까운 공통 부모로 끌어올린다
트리 전체 여러 계층에서 필요하고, props로 계속 넘기기(prop drilling)가 번거롭다Context나 전역 상태 관리 라이브러리 고려(§5, ch04)

상태를 상위로 끌어올릴수록, 그 상태를 쓰지 않는 중간 컴포넌트들도 단지 전달만을 위해 props를 받아야 하는 경우가 생긴다. 계층이 두세 단계면 괜찮지만, 다섯 단계 이상 내려가면 코드를 읽기 어려워진다 — 이 문제는 ch04의 Context나 별도의 상태 관리 도구로 해결한다. 지금 단계에서 기억할 것은 하나다: 상태는 필요한 가장 좁은 범위에 두고, 정말 공유가 필요할 때만 위로 옮긴다. 처음부터 최상위에 모든 상태를 두는 것은 좋은 설계가 아니다.

단방향 데이터 흐름

React는 데이터가 항상 부모 → 자식으로만 props를 통해 흐르고, 자식이 부모에게 뭔가 알리고 싶으면 부모가 자식에게 넘겨준 콜백 함수를 호출하는 식으로만 거슬러 올라간다. 이 "단방향 데이터 흐름"이 지켜지면, 어떤 값이 왜 바뀌었는지 항상 "그 값을 소유한 컴포넌트의 setter 호출"까지 역추적할 수 있다.

무슨 일이 일어나는가

color 상태는 App 하나에만 있다. Swatches와 Preview는 형제 관계라 서로 직접 통신할 수 없다 — 대신 공통 부모인 App이 상태를 갖고, Swatches가 고른 값을 onSelect 콜백으로 올려보내면 App이 Preview에 그 값을 다시 props로 내려준다.

  • <Swatches ... onSelect={setColor} /> — 자식이 부를 콜백으로 setter를 그대로 넘겼다.
  • <Preview color={color} /> — 같은 상태를 다른 자식에게 props로 전달.
  • 두 자식은 서로의 존재를 모른다 — 오직 App을 통해서만 동기화된다.

§8 요약 — 상태는 필요한 가장 좁은 범위에 두다가, 형제 컴포넌트가 공유해야 하는 순간 공통 부모로 끌어올린다. 값은 항상 props로 내려가고, 변경 요청은 항상 콜백 호출로 올라간다.

포털이 하는 일 Modal이 컴포넌트 트리상 깊은 곳(예: 어떤 카드 내부)에 있어도, createPortal의 두 번째 인자로 지정한 실제 DOM 노드(#modal-root, 보통 <body> 바로 아래) 밑에 렌더링된다. React 이벤트 버블링은 DOM 위치가 아니라 컴포넌트 트리 위치를 따라가므로, 이벤트 처리는 트리 구조 그대로 동작한다[10].

React 규칙 — 순수 컴포넌트, 렌더 중 부수효과 금지

React가 예측 가능하게 동작하려면 컴포넌트 함수가 순수 함수여야 한다[11]. 렌더링 도중에는 다음을 하면 안 된다.

  • props나 state를 직접 수정하는 것 (§3, §4에서 이미 다룬 규칙)
  • 같은 props/state로 호출됐는데 매번 다른 결과를 반환하는 것 (예: 렌더링 중 Math.random()이나 new Date()를 그대로 화면에 쓰는 것)
  • 네트워크 요청, localStorage 쓰기, DOM 직접 조작 같은 부수효과(side effect)를 렌더링 함수 본문에서 실행하는 것

이 규칙이 중요한 이유는 React가 최적화를 위해 컴포넌트 함수를 여러 번, 또는 예상치 못한 순서로 호출할 수 있기 때문이다(예: Strict Mode는 개발 환경에서 컴포넌트를 의도적으로 두 번 렌더링해 부수효과를 조기에 드러낸다). 렌더링 함수가 순수하지 않으면 "몇 번 호출됐는가"에 따라 결과가 달라지는 버그가 생긴다.

그럼 부수효과는 어디서? 부수효과는 이벤트 핸들러(사용자가 뭔가 했을 때) 또는 useEffect(렌더링 이후, 화면이 그려지고 나서) 안에서 실행한다. "렌더링 = 화면을 계산하는 순수한 단계", "이펙트/핸들러 = 바깥 세상과 상호작용하는 단계"로 나누는 것이 React의 핵심 규칙이다.

§9 요약 — 조건부 렌더링·Fragment·포털은 모두 "화면 어딘가에 이걸 보여줄지 말지, 어디에 보여줄지"를 선언하는 도구다. 렌더링 함수는 항상 순수해야 하며, 부수효과는 이벤트 핸들러나 useEffect로 분리한다.

§10미니 실습 — 할 일 목록(Todo) 앱

지금까지 배운 개념 — useState, 불변 갱신, 이벤트 처리, 리스트와 key, 제어 컴포넌트, 조건부 렌더링 — 을 전부 사용해 추가·삭제·토글·필터가 모두 동작하는 Todo 앱을 완성한다. 오른쪽에서 직접 실행하고, 왼쪽 해설로 각 줄의 역할을 확인해라.

코드 줄별 해설

  • useState([...]) — 할 일 배열. 각 항목은 { id, text, done } 객체.
  • useState("") — 입력창의 현재 값(text). 입력창은 제어 컴포넌트다.
  • useState("all") — 현재 필터("all"/"active"/"done").
  • addTodo(e) — e.preventDefault()로 새로고침 방지 → 빈 문자열이면 무시(trim() 후 길이 체크) → [...prev, 새항목]으로 불변 추가 → 입력창 비우기.
  • toggleTodo(id) — prev.map으로 배열 전체를 순회하되, id가 일치하는 항목만 { ...t, done: !t.done }로 새로 만들고 나머지는 그대로 둔다. 배열 자체도 map이 새 배열을 반환하므로 통째로 불변이다.
  • removeTodo(id) — prev.filter로 해당 id만 뺀 새 배열.
  • visible — 원본 todos는 그대로 두고, 화면에 보여줄 목록만 filter로 파생시킨다. 필터용 state를 따로 두지 않고 매 렌더마다 계산하는 것이 핵심이다 — "필터링된 목록"이라는 별도 state를 만들면 todos와 동기화를 직접 관리해야 해서 버그가 생기기 쉽다.
  • <input type="checkbox" checked={t.done} onChange={...} /> — 체크박스도 제어 컴포넌트다.
  • key={t.id} — 삭제/필터로 순서와 개수가 바뀌는 리스트이므로, §6에서 다룬 대로 반드시 안정적인 id를 key로 쓴다.

§11이해도 점검

  • DOM을 직접 조작하는 방식과 React 방식의 근본적인 차이("무엇을 할지" vs "어떤 상태인지")를 설명할 수 있다.
  • JSX가 React.createElement 호출로 변환된다는 것을 알고, 왜 className/htmlFor를 쓰는지 설명할 수 있다.
  • &&와 삼항 연산자로 조건부 렌더링을 할 수 있고, &&의 0 함정을 안다.
  • props는 구조분해로 받고, 절대 함수 내부에서 수정하지 않는다는 규칙을 안다.
  • 합성(composition)이 상속을 대신하는 방식이라는 걸 설명할 수 있다.
  • 일반 변수 대신 useState를 써야 화면이 갱신되는 이유를 설명할 수 있다.
  • setCount(count + 1)을 여러 번 부르는 것과 setCount(c => c + 1)을 여러 번 부르는 것의 차이를 안다.
  • 객체/배열 상태를 스프레드로 불변 갱신할 수 있다.
  • 이벤트 핸들러에 인자를 넘기는 방법(화살표 함수로 감싸기)을 안다.
  • 리스트에 key로 index를 쓰면 어떤 상황에서 어떤 버그가 생기는지 직접 재현해서 설명할 수 있다.
  • 제어 컴포넌트와 비제어 컴포넌트의 차이를 안다.
  • 상태를 어디에 둘지 판단하는 기준(사용처가 하나인가, 공통 부모가 있는가)을 안다.
  • 렌더링 중에 부수효과를 실행하면 안 되는 이유와, 대신 어디서 실행해야 하는지 안다.
  • push/splice/sort처럼 배열을 직접 변형하는 메서드와, 그 대신 쓸 수 있는 불변 버전을 최소 3쌍 말할 수 있다.
  • prop drilling이 무엇이고, 계층이 깊어질 때 어떤 대안이 있는지 안다.
  • Todo 앱의 추가/토글/삭제/필터 로직을 코드 없이 말로 설명할 수 있다.
