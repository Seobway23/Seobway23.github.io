§1CSS 기본기

CSS는 "어떤 요소에 어떤 스타일을 적용할지"를 선택자(selector)로 지정하는 규칙의 나열이다. 문제는 같은 요소에 서로 다른 값을 주는 규칙이 동시에 걸릴 때다. 이때 브라우저는 정해진 순서대로 승자를 가린다.

선택자 종류

선택자는 조합해서 쓸 수 있고, 조합할수록 더 구체적인 요소를 가리킨다.

명시도 계산 규칙

같은 출처(origin)에서 온 규칙끼리는 명시도로 승부를 가린다. 명시도는 4자리 숫자 (a, b, c, d)로 표현하고, 왼쪽 자리가 더 무겁다[1].

자리포함 항목예시
a인라인 스타일 (style="...")+1
bid 선택자#header → +1
c클래스, 속성, 가상 클래스.card, [type], :hover → 각 +1
d타입 선택자, 가상 요소div, ::before → 각 +1

전역 선택자(*)와 결합자(>, +, 공백)는 명시도에 영향을 주지 않는다. 예를 들어 p.note#target은 (0, 1, 1, 1) — id 1개, 클래스 1개, 태그 1개다. (0,1,0,0)인 #target보다 이 값이 더 크므로 이긴다. !important는 명시도 계산 자체를 건너뛰고 별도로 최우선 취급되는데, 남용하면 나중에 그 무엇으로도 못 이기는 규칙이 쌓여 유지보수가 힘들어진다.

  B -- "같다" --> D{"명시도가 다른가?"}
  D -- "다르다" --> E["명시도 높은 규칙이 이긴다"]
  D -- "같다" --> F["소스 코드에서 나중에 나온 규칙이 이긴다"]
그림 1. 캐스케이드(cascade) 결정 순서 — 출처와 중요도, 명시도, 소스 순서 순으로 승자를 가린다[20]. 출처: W3C CSS Cascading and Inheritance

무슨 일이 일어나는가

같은 문단에 명시도가 다른 4개의 규칙이 걸려 있다. 코드를 고쳐서 어떤 규칙이 이기는지 직접 확인해보자.

  • p — 명시도 (0,0,0,1), 가장 약함
  • .note — (0,0,1,0)
  • #target — (0,1,0,0), id라서 클래스보다 강함
  • p.note#target — (0,1,1,1), 셋을 다 합쳐서 가장 강함
  • 버튼을 누르면 getComputedStyle로 실제 적용된 색을 읽어온다

상속과 캐스케이드

모든 속성이 상속되지는 않는다. color, font-family, font-size, line-height 같은 텍스트 관련 속성은 기본적으로 상속되고, margin, padding, border, width 같은 박스 관련 속성은 상속되지 않는다. 강제로 상속시키려면 값에 inherit을, 반대로 브라우저 기본값으로 되돌리려면 initial을, 상속된 값을 명시적으로 지우려면 unset을 쓴다.

흔한 실수 명시도를 이기려고 !important를 계속 추가하는 것. 근본 원인은 대개 선택자 설계가 너무 강하거나(id 남용), CSS 로딩 순서가 꼬여 있는 것이다. 구조를 고치는 게 먼저다.

§2박스 모델과 단위

브라우저는 모든 요소를 사각형 상자로 취급한다. 이 상자를 박스 모델(box model)이라고 부른다[2]. 액자에 비유하면 그림(content) 주변에 여백(padding), 액자 틀(border), 벽과의 간격(margin)이 순서대로 감싸는 구조다.

box-sizing — content-box vs border-box

기본값 content-box에서는 width: 200px에 padding: 16px, border: 4px를 더하면 실제 렌더링 너비는 240px가 된다[3]. 레이아웃 계산이 매번 덧셈이 되는 게 번거로워서, 실무에서는 거의 항상 아래처럼 전역으로 border-box를 켠다.

reset.css
*, *::before, *::after {
  box-sizing: border-box; /* width에 padding·border가 이미 포함됨 */
}

마진 상쇄

  • 인접한 형제 블록 요소의 위/아래 마진은 합이 아니라 더 큰 값 하나로 합쳐진다[4].
  • 부모·자식 사이에도 부모에 border/padding/inline 콘텐츠가 없으면 마진이 부모 밖으로 새어 나가며 합쳐진다.
  • Flex/Grid 컨테이너의 자식 사이에서는 마진 상쇄가 일어나지 않는다. 이 차이 때문에 레이아웃을 Flex/Grid로 바꾸면 간격이 달라 보이는 경우가 흔하다.

단위 — px / rem / em / % / vh·vw / ch / clamp()

단위기준주로 쓰는 곳
px절대값(고정 픽셀)테두리 두께처럼 확대해도 안 커져야 하는 값
rem루트(html)의 font-size 기준 (보통 16px)폰트 크기, 간격 — 사용자 브라우저 설정을 존중해야 할 때
em자기 자신(또는 부모)의 font-size 기준글자에 종속적인 간격(아이콘 크기 등), 중첩 시 값이 누적되니 주의
%부모 요소의 해당 값 기준부모에 맞춰 늘어나야 하는 너비
vh / vw뷰포트(viewport) 높이/너비의 1%전체 화면을 채우는 히어로 섹션
ch현재 폰트의 숫자 "0" 한 글자 너비가독성 좋은 본문 줄 길이 제한(max-width: 65ch)

clamp()는 최소·선호·최대 세 값을 받아 뷰포트 크기에 따라 유동적으로 값을 계산한다[5]. font-size: clamp(1rem, 0.8rem + 1vw, 1.8rem)처럼 쓰면 미디어 쿼리 없이도 화면 크기에 비례해 커지는 타이포그래피를 만들 수 있다. §5에서 라이브로 다룬다.

무슨 일이 일어나는가

같은 width: 200px; padding: 16px; border: 4px solid를 가진 두 박스를 box-sizing만 다르게 렌더링한다.

  • 왼쪽(content-box) — 실제 너비 200+32+8=240px
  • 오른쪽(border-box) — 실제 너비 그대로 200px
  • JS로 getBoundingClientRect().width를 읽어 실측값을 보여준다

§3레이아웃 — Flexbox & Grid

Flexbox

Flexbox는 컨테이너에 display: flex를 주는 순간, 그 안의 자식들이 한 줄(또는 한 열)로 배치되는 1차원 레이아웃이다[6]. 자식이 나열되는 방향을 주축(main axis), 그에 수직인 방향을 교차축(cross axis)이라 부른다. 정렬 속성은 어느 축을 조정하는지에 따라 이름이 다르다.

그림 3. flex-direction: row일 때 주축은 가로, 교차축은 세로. column이면 정반대가 된다. 출처: MDN Flexbox

gap아이템 사이 간격 (margin과 달리 상쇄되지 않고, 바깥 여백에는 영향 없음)

orderDOM 순서와 무관하게 시각적 배치 순서를 바꿈 (기본 0)

무슨 일이 일어나는가

셀렉트 박스를 바꾸면 JS가 컨테이너의 style.justifyContent/alignItems/flexDirection을 직접 갱신한다. 세 번째 아이템만 높이를 다르게 줘서 교차축 정렬 차이가 잘 보이게 했다.

  • flex-direction: column으로 바꾸면 주축/교차축이 서로 뒤바뀌는 것도 확인해보자

Grid

Grid는 grid-template-columns/grid-template-rows로 행과 열의 "트랙"을 먼저 정의하고, 그 위에 아이템을 배치하는 2차원 레이아웃이다[7]. 정식 스펙은 W3C의 CSS Flexible Box Layout[8]과 CSS Grid Layout Module Level 2[9]다.

표현의미
grid-template-columns: repeat(3, 1fr)1fr 너비 열을 3개 반복 생성
repeat(auto-fit, minmax(160px, 1fr))최소 160px, 남으면 균등 확장(1fr)하는 열을 컨테이너 너비가 허용하는 만큼 자동 생성
grid-template-areas문자열로 레이아웃 이름을 그려서 지정
grid-area: nav해당 아이템을 nav라는 이름의 영역에 배치
auto-fit vs auto-fillauto-fit은 남는 빈 트랙을 접어서 콘텐츠가 있는 열을 늘리고, auto-fill은 빈 트랙도 자리를 유지한다. 카드 갤러리처럼 아이템 개수가 적을 때 화면 전체로 늘어나길 원하면 auto-fit을 쓴다.

위쪽 그리드는 repeat(auto-fit, minmax(120px, 1fr)) — 브라우저 창을 좁혀보면 열 개수가 자동으로 줄어든다. 아래쪽은 grid-template-areas로 그림 4와 동일한 레이아웃을 코드로 재현한 것이다.

§4포지셔닝과 쌓임 맥락

position 값

값기준(top/left 등)문서 흐름
static없음(기본값)흐름 유지, top/z-index 무시됨
relative자기 자신의 원래 위치흐름 유지(원래 자리를 계속 차지), 시각적으로만 이동

실무에서 가장 많이 하는 실수는 absolute 자식의 기준이 될 부모에 position: relative를 깜빡하는 것이다[10]. 그러면 기준점이 조상을 타고 올라가 문서 전체(<html>) 기준으로 배치되어 버린다.

z-index와 쌓임 맥락(stacking context)

z-index는 아무 요소에나 적용되지 않는다. position이 static이 아니어야 값이 의미를 가진다. 그리고 그 비교는 전역이 아니라 "같은 쌓임 맥락 안"에서만 이루어진다[11].

쌓임 맥락이 새로 생기는 조건
  • 문서의 root 요소(<html>)
  • position: fixed 또는 sticky
  • position: absolute/relative + z-index가 auto가 아님
  • opacity 값이 1 미만
  • transform, filter, perspective, clip-path, mask 중 하나라도 none이 아님
  • 해당 속성을 예고하는 will-change
  • isolation: isolate
  • mix-blend-mode가 normal이 아님
  • flex/grid 아이템이면서 z-index가 auto가 아님

부모가 새 쌓임 맥락을 만들면, 그 자식이 아무리 z-index: 9999를 줘도 부모 바깥의 형제 요소를 절대 넘어설 수 없다 — 자식은 부모가 만든 "그룹 안"에 갇힌다.

그림 5. 왼쪽 박스의 z-index: 9999는 자기 부모(쌓임 맥락 A) 안에서만 유효하다. 바깥의 z-index: 2짜리 형제를 절대 덮지 못한다. 출처: MDN Stacking Context

무슨 일이 일어나는가

position: sticky 헤더는 스크롤해도 컨테이너 안에서 상단에 붙어있다. 두 카드 위의 배지는 position: absolute이고, z-index가 다르게 겹치도록 만들었다.

§5반응형

미디어 쿼리와 모바일 퍼스트

@media는 뷰포트 조건에 따라 다른 스타일을 적용한다[12]. 실무 관례는 모바일 퍼스트 — 기본 CSS는 가장 작은 화면을 가정하고, min-width 쿼리로 화면이 커질 때마다 스타일을 "추가"한다. 반대로 max-width로 큰 화면을 기본으로 잡고 깎아나가면 미디어 쿼리 우선순위가 꼬이기 쉽다.

responsive.css
.card { display: block; } /* 기본값: 모바일 */

@media (min-width: 640px) {
  .card { display: flex; } /* 태블릿 이상부터 가로 배치 */
}

@media (min-width: 1024px) {
  .card { gap: 24px; } /* 데스크톱에서 간격 확대 */
}

컨테이너 쿼리 (@container)

미디어 쿼리는 뷰포트 전체 크기만 본다. 그런데 같은 카드 컴포넌트가 넓은 본문에도, 좁은 사이드바에도 들어갈 수 있다면 뷰포트 크기만으로는 판단할 수 없다. 컨테이너 쿼리는 부모에 container-type: inline-size를 선언해두면, 자식이 그 부모의 실제 너비를 기준으로 스타일을 바꿀 수 있게 한다[13].

card.css
.card-wrap { container-type: inline-size; }

@container (min-width: 420px) {
  .card { flex-direction: row; } /* 부모가 420px 넘으면 가로 배치 */
}

무슨 일이 일어나는가

박스 우측 하단 모서리를 드래그해서 너비를 늘려보자(resize: horizontal). 부모 너비가 420px를 넘는 순간 @container 쿼리가 발동해 세로 배치가 가로 배치로 바뀐다. 제목 글자 크기는 clamp()로 뷰포트 너비에 비례해 유동적으로 변한다.

clamp()로 유동 타이포그래피

clamp(최소, 선호, 최대)의 선호값에 vw를 섞으면(clamp(1rem, 0.8rem + 1vw, 2rem)) 미디어 쿼리 여러 개 없이도 화면 크기와 함께 부드럽게 변하는 값을 만들 수 있다. 위 놀이터의 .fluid-title이 그 예시다.

§6모던 CSS

네이티브 CSS 중첩

Sass 같은 전처리기 없이도 &로 부모 선택자를 참조하며 중첩할 수 있다[14].

nesting.css
.card {
  padding: 16px;
  border: 1px solid #e2e6f0;

  &:hover {
    border-color: #3b5bdb;
  }

  & .title {
    font-weight: 700;
  }

  @media (min-width: 768px) {
    padding: 24px;
  }
}

커스텀 프로퍼티(CSS 변수)와 다크모드

--이름: 값으로 선언하고 var(--이름)으로 쓴다. Sass 변수와 달리 브라우저가 런타임에 값을 들고 있어서, data-theme 속성 하나만 바꿔도 그 속성을 참조하는 모든 요소가 즉시 재계산된다 — 이 페이지 우상단 테마 버튼도 정확히 이 방식으로 동작한다.

무슨 일이 일어나는가

:root에 라이트 모드 변수를, [data-theme="dark"]에 다크 모드 변수를 다시 선언해뒀다. 버튼을 누르면 JS가 <html>의 data-theme 속성만 토글하고, CSS는 그 값을 보고 자동으로 다시 그린다.

  • document.documentElement.setAttribute('data-theme', ...) 한 줄이 전부다
  • 색을 계산하는 JS 로직은 없다 — 브라우저가 var() 참조를 알아서 다시 푼다

:has() / :is() · :where()

:has()는 자식(또는 형제)의 상태를 보고 조상 스타일을 바꿀 수 있게 한다 — CSS에 없던 "부모 선택자"다[15]. :is()와 :where()는 여러 선택자를 하나로 묶어 반복을 줄인다[16]. 둘의 차이는 명시도뿐이다 — :is()는 괄호 안에서 가장 강한 선택자의 명시도를 그대로 가져가고, :where()는 명시도가 항상 0이라 나중에 덮어쓰기 쉽다.

selectors.css
/* h2, h3, h4를 매번 나열하지 않아도 됨 */
:is(h2, h3, h4) { font-weight: 800; }

/* 명시도 0 — 나중에 컴포넌트 스타일이 쉽게 덮어씀 */
:where(article) p { line-height: 1.7; }

color-mix()와 light-dark()

colors.css
/* 파란색에 흰색을 15% 섞은 연한 파랑 계산 */
.selected { background: color-mix(in srgb, #3b5bdb 15%, white); }

/* color-scheme이 dark면 두 번째 값, light면 첫 번째 값 자동 선택 */
:root {
  color-scheme: light dark;
  --fg: light-dark(#171a21, #e6e9f0);
}

color-mix()[17]는 hover/선택 상태처럼 원색에서 살짝 변형된 색이 필요할 때 별도 색상값을 하드코딩하지 않아도 되게 해준다. light-dark()[18]는 [data-theme] 토글 없이 OS 설정만으로 다크모드를 지원할 때 코드량을 줄여준다.

무슨 일이 일어나는가

체크박스를 누르면 :has(input:checked)가 부모 <li>의 배경을 color-mix()로 계산한 연한 파랑으로 바꾼다. 자바스크립트 코드는 단 한 줄도 없다 — 순수 CSS 선택자만으로 동작한다.

@layer, aspect-ratio, gap

@layer는 CSS 규칙을 이름 있는 "층"으로 묶어, 명시도와 무관하게 층 선언 순서로 우선순위를 정한다[19]. reset → base → components → utilities 순으로 층을 쌓아두면, 나중에 로드된 유틸리티 클래스가 명시도 계산 없이도 항상 이긴다 — Tailwind가 내부적으로 쓰는 방식이기도 하다.

layers.css
@layer reset, base, components, utilities;

@layer reset {
  * { margin: 0; padding: 0; }
}
@layer utilities {
  .text-center { text-align: center; } /* 명시도가 낮아도 항상 이김 */
}

aspect-ratio: 16 / 9는 padding-top 트릭 없이 요소의 가로세로 비율을 고정한다. gap은 이미 §3에서 다뤘듯 Flex/Grid 모두에서 아이템 사이 간격을 마진 상쇄 없이 지정한다.

§7애니메이션

transition과 transform

transition은 속성값이 바뀔 때(예: :hover 진입) 그 변화를 지정한 시간에 걸쳐 부드럽게 보간한다. transform은 요소를 이동/확대/회전시키는데, top/left/width를 직접 바꾸는 것과 시각적 결과는 비슷해도 성능이 다르다 — 아래에서 이유를 설명한다.

@keyframes

시작~끝 사이 중간 지점들을 퍼센트로 지정해서 반복 재생 가능한 애니메이션을 만든다.

spin.css
@keyframes spin {
  to { transform: rotate(360deg); }
}
.spinner {
  animation: spin 1s linear infinite;
}

왜 transform/opacity만 애니메이션해야 하는가

브라우저는 화면을 그릴 때 레이아웃(layout) → 페인트(paint) → 합성(compositing) 3단계를 거친다. width, top, margin 같은 속성을 바꾸면 레이아웃부터 다시 계산해야 하지만, transform과 opacity는 별도의 합성 레이어에서 GPU가 처리해 레이아웃·페인트를 건너뛴다[23]. 그래서 60fps를 유지하려면 애니메이션 대상은 최대한 transform/opacity로 제한해야 한다.

will-change: transform은 브라우저에게 "이 요소는 곧 움직일 것"이라 미리 알려 합성 레이어를 미리 준비시킨다[21]. 다만 남용하면 메모리를 불필요하게 점유하므로, 실제로 애니메이션 직전에만 붙였다가 끝나면 제거하는 게 정석이다.

접근성prefers-reduced-motion: reduce는 OS에서 "동작 줄이기"를 켠 사용자를 위한 미디어 쿼리다[22]. 전정기관(vestibular) 문제가 있는 사용자에게 큰 움직임은 어지러움을 유발할 수 있으므로, 장식용 애니메이션은 이 쿼리 안에서 꺼주는 게 좋다. 포커스 링·대비 등 접근성 스타일링 전반은 ch09에서 이어서 다룬다.

무슨 일이 일어나는가

카드는 transform과 box-shadow만 transition시킨다(레이아웃에 영향 없음). 스피너는 @keyframes로 무한 회전한다. @media (prefers-reduced-motion: reduce) 블록이 두 애니메이션을 모두 끄는 패턴도 포함했다.

§8Tailwind CSS

유틸리티 퍼스트 철학

Tailwind CSS는 .card 같은 의미 있는 클래스명을 새로 만드는 대신, p-4/flex/text-lg처럼 한 가지 CSS 속성만 담당하는 저수준 클래스를 마크업에 직접 조합하는 유틸리티 퍼스트 프레임워크다[25].

장점

클래스명을 새로 짓는 고민이 사라진다. CSS 파일과 마크업을 오가며 컨텍스트를 전환할 필요가 없다. 설정 파일의 디자인 토큰(spacing/color 스케일)만 따르면 임의의 값 남발을 막아 자연스럽게 일관성이 생긴다. 실제 쓰이는 클래스만 스캔해서 CSS를 생성하므로 번들에 죽은 CSS가 쌓이지 않는다.

단점

마크업의 className이 매우 길어져 가독성이 떨어질 수 있다. 유틸리티 이름 자체를 외워야 하는 학습 비용이 있다. 디자인 시스템에서 크게 벗어나는 완전히 독특한 스타일은 결국 커스텀 CSS로 빠져나가야 한다.

설치 (Vite 기준, Tailwind v4)

v4부터는 tailwind.config.js 없이 CSS 파일 안에서 바로 설정하는 방식이 기본이다[24].

터미널
yarn add -D tailwindcss @tailwindcss/vite
vite.config.ts
import { defineConfig } from 'vite';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({
  plugins: [tailwindcss()],
});
src/index.css
@import "tailwindcss";

@theme {
  --color-brand: #3b5bdb; /* 커스텀 토큰 → 자동으로 bg-brand, text-brand 클래스 생성 */
}

무슨 일이 일어나는가

이 놀이터는 Tailwind CDN을 쓸 수 없어서, 순수 CSS로 같은 결과를 재현했다. 아래 코드블록에 실제로 쓰였을 Tailwind 클래스를 병기했으니 대응 관계를 비교해보자.

  • rounded-xl border p-6 shadow-sm → border-radius, border, padding, box-shadow 각각의 유틸리티 조합
  • flex flex-col gap-3 → display:flex; flex-direction:column; gap:12px

@apply 남용 경고

@apply는 유틸리티 클래스 여러 개를 커스텀 CSS 클래스 하나로 묶어준다.

button.css
.btn-primary {
  @apply inline-flex items-center gap-2 rounded-lg bg-blue-500 px-4 py-2 text-white;
}
함정 @apply[26]를 여기저기 남용하면 결국 "긴 유틸리티 조합을 클래스명 뒤에 숨긴" 옛날 방식 CSS로 되돌아간다 — Tailwind가 애초에 피하려던 문제(클래스명 짓기, CSS 파일과 마크업 사이 컨텍스트 전환)가 그대로 재발한다. 반복되는 조합은 @apply보다 React 컴포넌트(<Button>)로 추출하는 편이 대부분 더 낫다.

clsx / tailwind-merge 패턴

조건부로 클래스를 조합하다 보면 두 가지 문제가 생긴다. 첫째, isActive && 'bg-blue-500' 같은 표현식을 문자열로 안전하게 이어 붙이는 게 번거롭다(clsx가 해결). 둘째, 기본 클래스에 px-2가 있는데 prop으로 px-4를 덮어쓰려 하면, 클래스 문자열에 둘 다 남아 CSS 소스 순서에 따라 승자가 정해져버린다(tailwind-merge가 해결).

무슨 일이 일어나는가

clsx와 tailwind-merge를 각각 20~30줄로 원리만 재구현했다. 콘솔에서 실제 라이브러리와 같은 방식의 출력을 확인할 수 있다.

  • clsx 미니 구현 — 문자열/배열/객체를 받아 true인 값만 이어 붙인다
  • twMerge 미니 구현 — 같은 접두사(px- 등)를 가진 클래스가 뒤에 또 나오면 앞의 것을 제거한다(실제 라이브러리는 Tailwind의 전체 클래스 규칙을 인식하는 훨씬 정교한 버전)

실제로는 두 라이브러리를 합쳐 cn() 헬퍼 하나로 쓰는 게 shadcn/ui를 포함한 실무 표준 패턴이다.

src/lib/utils.ts
import { clsx, type ClassValue } from 'clsx';
import { twMerge } from 'tailwind-merge';

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

// 사용: cn('px-2', isWide && 'px-4') → 'px-4' (충돌 자동 해결)

§9컴포넌트 시스템

shadcn/ui — "설치"가 아니라 "복사"

일반적인 UI 라이브러리는 npm install로 node_modules에 들어가는 블랙박스다. 커스터마이징은 라이브러리가 제공하는 props나 테마 API 범위 안에서만 가능하다. shadcn/ui는 다르게 동작한다 — npx shadcn add button을 실행하면 Button 컴포넌트의 소스 코드 자체가 components/ui/button.tsx로 복사되어 들어온다[27]. 그 순간부터 그 코드는 라이브러리 코드가 아니라 내 코드다. 자유롭게 고칠 수 있고, 버전 업그레이드에 깨질 걱정도 없다 — 애초에 의존성으로 물려있지 않기 때문이다. 대신 업스트림 버그 수정이나 개선을 자동으로 받지는 못하므로, 그 책임도 내가 진다. 

flowchart LR
  subgraph npm["일반 UI 라이브러리"]
    A1["npm install"] --> A2["node_modules 안의 블랙박스"]
    A2 --> A3["props/테마 API 범위 안에서만 커스터마이징"]
  end
  subgraph shadcn["shadcn/ui"]
    B1["npx shadcn add button"] --> B2["소스 코드가 내 저장소로 복사됨"]
    B2 --> B3["components/ui/button.tsx — 내 코드처럼 자유롭게 수정"]
  end
그림 6. npm 설치형 라이브러리와 shadcn/ui의 근본적인 차이 — 의존성이냐 소유권이냐. 출처: ui.shadcn.com

Radix UI와 headless 컴포넌트

shadcn/ui가 복사해오는 코드 상당수는 내부적으로 Radix UI 원시(primitive) 컴포넌트를 감싼다. Radix는 headless — 드롭다운의 포커스 트랩, 다이얼로그의 ESC 닫기, 콤보박스의 키보드 화살표 탐색 같은 "접근성 로직"만 제공하고 시각적 스타일은 한 줄도 강요하지 않는다. 스타일은 100% Tailwind 클래스로 shadcn 쪽에서 입힌다. 즉 "어떻게 동작해야 하는가"는 Radix가, "어떻게 보여야 하는가"는 내가(또는 shadcn 템플릿이) 책임지는 분업이다.

CVA (class-variance-authority) 패턴

버튼 하나에도 variant(primary/secondary/danger/ghost)와 size(sm/md/lg) 같은 여러 축의 변형이 필요하다. CVA는 이 조합을 선언적으로 정의하고, props만 넘기면 알맞은 클래스 문자열을 계산해준다.

무슨 일이 일어나는가

class-variance-authority 패키지를 import할 수 없으므로, 그 핵심 아이디어만 20여 줄의 cva() 함수로 재구현했다. base 클래스 + variants 맵 + defaultVariants를 받아 클래스 문자열을 조합하는 게 전부다.

  • 위쪽 버튼들로 variant를 바꾸고, 아래쪽 버튼들로 size를 바꾼다
  • Button 컴포넌트는 실제 렌더링 로직만 담당하고, 클래스 계산은 전부 buttonVariants()에 위임한다

실제 shadcn/ui가 복사해주는 button.tsx는 이 원리를 그대로 쓰되, 진짜 cva 패키지와 Radix의 Slot(자식 요소에 props를 그대로 전달하는 패턴)을 함께 쓴다.

components/ui/button.tsx (발췌)
import { cva, type VariantProps } from 'class-variance-authority';

const buttonVariants = cva(
  'inline-flex items-center justify-center rounded-md font-medium transition-colors',
  {
    variants: {
      variant: {
        default: 'bg-primary text-primary-foreground hover:bg-primary/90',
        destructive: 'bg-destructive text-white hover:bg-destructive/90',
        outline: 'border bg-background hover:bg-accent',
        ghost: 'hover:bg-accent hover:text-accent-foreground',
      },
      size: {
        default: 'h-9 px-4 py-2',
        sm: 'h-8 px-3',
        lg: 'h-10 px-6',
      },
    },
    defaultVariants: { variant: 'default', size: 'default' },
  }
);

export interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement>,
    VariantProps<typeof buttonVariants> {}

export function Button({ className, variant, size, ...props }: ButtonProps) {
  return (
    <button className={cn(buttonVariants({ variant, size }), className)} {...props} />
  );
}

§10디자인 토큰과 일관성

색 · 간격 · 타이포 스케일

디자인 토큰은 색상·간격·폰트 크기 같은 값을 하드코딩하지 않고 이름 붙은 상수로 관리하는 것이다. 간격은 보통 8pt 그리드 — 4, 8, 12, 16, 24, 32, 48, 64px처럼 8(또는 4)의 배수만 후보로 남겨 임의의 여백 값이 화면 곳곳에 흩어지는 걸 막는다. 실제로 이 학습서의 style.css도 --radius, 헤더 높이 등에서 같은 원칙을 쓴다.

스케일값
간격 (8pt)4 · 8 · 12 · 16 · 24 · 32 · 48 · 64px
타이포12 · 14 · 16 · 18 · 20 · 24 · 30 · 36 · 48px
모서리 반경4 · 8 · 12 · 16 · 9999px(pill)

시맨틱 토큰 vs 프리미티브 토큰

--gray-100 같은 이름은 프리미티브(원시) 토큰 — "이 색이 어디에 쓰이는지"는 말하지 않는다. --color-bg 같은 시맨틱 토큰은 "용도"를 이름에 담고, 실제 값은 프리미티브 토큰을 참조한다. 컴포넌트는 항상 시맨틱 토큰만 참조해야 다크모드 전환 시 프리미티브 값의 매핑만 바꾸면 되고, 컴포넌트 코드는 한 줄도 안 건드려도 된다 — §6의 다크모드 놀이터가 바로 이 패턴이다.

프리미티브 토큰시맨틱 토큰용도
--gray-900--color-fg기본 텍스트 색
--gray-50--color-bg배경색
--blue-500--color-accent강조·링크·버튼
--gray-200--color-border구분선·테두리
tokens.css
:root {
  /* 1. 프리미티브: 값 그 자체 */
  --gray-50: #f8fafc;
  --gray-900: #171a21;
  --blue-500: #3b5bdb;

  /* 2. 시맨틱: 용도를 이름에 담고 프리미티브를 참조 */
  --color-bg: var(--gray-50);
  --color-fg: var(--gray-900);
  --color-accent: var(--blue-500);
}

[data-theme="dark"] {
  /* 다크모드에서는 시맨틱 토큰의 참조 대상만 바꾼다 */
  --color-bg: var(--gray-900);
  --color-fg: var(--gray-50);
}

.card { background: var(--color-bg); color: var(--color-fg); } /* 절대 --gray-* 직접 참조 금지 */

무슨 일이 일어나는가

JS로 getComputedStyle(document.documentElement).getPropertyValue('--space-4')처럼 CSS 변수값을 직접 읽어와서, 8pt 간격 스케일과 회색 스케일을 화면에 시각화했다.

§11이해도 점검

  • 명시도 (a,b,c,d) 네 자리가 각각 무엇을 세는지 설명할 수 있다
  • box-sizing: border-box가 content-box와 실제 렌더링 너비를 어떻게 다르게 만드는지 설명할 수 있다
  • 마진 상쇄가 언제 일어나고, Flex/Grid 아이템 사이에서는 왜 안 일어나는지 설명할 수 있다
  • Flexbox의 주축/교차축과 justify-content/align-items의 대응 관계를 설명할 수 있다
  • repeat(auto-fit, minmax(...))이 하는 일을 설명할 수 있다
  • Flexbox와 Grid 중 언제 무엇을 쓸지 스스로 판단할 수 있다
  • position: absolute의 기준이 어떻게 정해지는지 설명할 수 있다
  • 쌓임 맥락이 새로 생기는 조건을 3개 이상 말할 수 있다
  • 모바일 퍼스트 미디어 쿼리와 컨테이너 쿼리의 차이를 설명할 수 있다
  • CSS 변수 하나로 다크모드를 전환하는 원리를 직접 구현할 수 있다
  • transform/opacity만 애니메이션해야 하는 성능상의 이유를 설명할 수 있다
  • Tailwind의 장단점을 최소 하나씩 스스로 설명할 수 있다
  • shadcn/ui가 npm 라이브러리와 근본적으로 다른 점을 설명할 수 있다
  • 프리미티브 토큰과 시맨틱 토큰의 차이와, 왜 컴포넌트는 시맨틱 토큰만 참조해야 하는지 설명할 수 있다
