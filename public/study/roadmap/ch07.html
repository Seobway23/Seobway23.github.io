CHAPTER 07

빌드 도구 & 패키지 매니저

브라우저는 TypeScript도, JSX도, node_modules 경로도 모른다. 소스 코드가 브라우저가 실행 가능한 파일로 바뀌는 전체 파이프라인(트랜스파일 · 번들 · 미니파이 · 코드 스플리팅)을 이해하고, Vite가 왜 빠른지, 그리고 Yarn Berry(PnP · Zero-Install · Workspaces)가 기존 node_modules 방식과 근본적으로 무엇이 다른지를 원리부터 파본다.

Vite ESM Yarn Berry PnP Zero-Install Workspaces

이 챕터는 다음 질문에 답한다. 브라우저가 못 읽는 코드를 왜 쓰는가, 그리고 그걸 누가 어떻게 바꿔주는가? 번들러는 수백 개 파일을 어떤 원리로 하나(또는 몇 개)로 합치는가? Vite의 개발 서버는 왜 프로젝트 크기와 무관하게 즉시 뜨는가? package.json의 ^1.2.3은 정확히 어떤 버전까지 허용한다는 뜻인가? 그리고 Yarn Berry는 왜 node_modules 폴더 자체를 없애버렸는가?

§1왜 빌드가 필요한가

브라우저가 실제로 이해하는 것

브라우저의 JS 엔진(V8, SpiderMonkey 등)이 실행할 수 있는 건 딱 하나, 표준 JavaScript(ECMAScript)다[1]. 그런데 실무에서는 이런 걸 쓴다.

  • TypeScript — interface, : string 같은 타입 문법은 JS 문법이 아니다. 브라우저에 그대로 주면 문법 에러.
  • JSX — <div>Hi</div>는 HTML이 아니라 React.createElement("div", null, "Hi")로 바뀌어야 실행된다.
  • 최신 문법 — 옵셔널 체이닝(?.), 널 병합(??) 같은 최신 ES 문법은 오래된 브라우저 엔진에는 없다.
  • node_modules 경로 — import { useState } from "react" 라고 쓰면, 브라우저는 react라는 이름이 실제로 어느 파일(node_modules/react/index.js)을 가리키는지 알 방법이 없다. 이런 이름을 bare specifier(베어 스펙파이어)라고 부른다.

즉 "소스 코드"와 "브라우저가 실행 가능한 코드" 사이에는 간극이 있고, 그 간극을 메우는 작업 전체를 보통 빌드(build)라고 부른다. 빌드는 한 가지 작업이 아니라 여러 단계의 파이프라인이다.

트랜스파일(transpile)

문법을 바꾼다. TS → JS, JSX → createElement 호출, 최신 ES → 구버전 ES. §4에서 자세히.

번들(bundle)

수백 개의 import로 얽힌 파일들을 하나(또는 몇 개) 파일로 합친다. §3에서 자세히.

미니파이(minify)

변수명을 a, b로 줄이고 공백·주석을 지워 파일 크기를 줄인다. 로직은 그대로 유지된다.

코드 스플리팅(code splitting)

모든 걸 한 파일에 담지 않고, 필요한 시점에만 불러올 청크로 쪼갠다. §3에서 자세히.

흔한 오해 "번들러 = 웹팩" 이라고 생각하기 쉽지만, 번들링은 하나의 작업이고 웹팩·Rollup·esbuild·Vite는 그 작업을 수행하는 여러 도구 중 일부다. 이 챕터에서는 원리를 먼저 잡고, 실무 표준으로 자리 잡은 Vite를 깊게 다룬다.

§2모듈의 역사

"모듈"이란 코드를 파일 단위로 쪼개고, 필요한 부분만 다른 파일에서 가져다 쓰는 단위를 말한다. 지금은 import/export가 당연해 보이지만, 여기까지 오는 데 15년 넘게 걸렸다. 각 단계가 무엇을 해결하려다 다음 문제를 만들었는지 순서대로 본다.

전역 스크립트와 IIFE

가장 원시적인 방식은 <script src="a.js"><script src="b.js">를 순서대로 나열하는 것이다. 문제는 a.js에서 선언한 변수가 전부 전역 객체(window)에 붙는다는 것이다. b.js가 실수로 같은 이름의 변수를 선언하면 a.js의 값을 덮어써 버린다. 파일이 10개만 넘어가도 이름 충돌을 사람이 손으로 관리해야 했다.

이를 해결하려고 나온 패턴이 IIFE다.

iife-pattern.js
// 함수로 감싸서 즉시 실행 — 내부 변수가 전역으로 새지 않는다
var MyModule = (function () {
  var privateCount = 0; // 밖에서 절대 접근 불가

  function increment() {
    privateCount += 1;
    return privateCount;
  }

  // 외부에 노출할 것만 골라서 return
  return { increment: increment };
})();

MyModule.increment(); // 1
// privateCount는 여기서 보이지 않는다

IIFE는 스코프 오염은 막았지만, 여전히 "무엇이 무엇에 의존하는지"는 <script> 태그를 쓰는 순서로만 표현됐다. 의존성이 늘어날수록 순서를 맞추는 게 곧 지옥이 됐다.

CommonJS와 AMD — 같은 문제, 다른 환경

2009년 Node.js가 등장하면서 서버 환경에서는 CommonJS가 표준이 됐다[14]. require()로 모듈을 동기적으로 불러오고 module.exports로 내보낸다. 파일 시스템에서 즉시 읽을 수 있는 서버 환경에는 동기 로딩이 자연스러웠다.

math.cjs (CommonJS)
// math.cjs
function add(a, b) { return a + b; }
module.exports = { add };

// app.cjs
const { add } = require("./math.cjs");
console.log(add(1, 2)); // 3

문제는 브라우저였다. 브라우저는 파일을 네트워크로 비동기로 받아온다. require()가 동기 함수라는 전제 자체가 브라우저 환경과 맞지 않았다. 그래서 브라우저 전용으로 AMD(Asynchronous Module Definition)가 나왔다 — RequireJS가 대표 구현체다. 콜백 기반으로 의존성을 미리 선언해서 비동기로 로드했다.

amd-example.js
// AMD: 의존성을 배열로 먼저 선언하고, 콜백에서 사용
define(["./math"], function (math) {
  return { run: function () { return math.add(1, 2); } };
});

결과적으로 서버는 CommonJS, 브라우저는 AMD(또는 UMD로 둘 다 지원)를 따로 관리해야 하는 상황이 됐다. 같은 언어인데 모듈 시스템이 환경마다 다른 건 명백히 비정상적이었다.

ESM — 언어 표준으로 수렴

2015년 ES2015(ES6)에서 ESM(ECMAScript Modules)이 언어 명세에 정식으로 포함됐다[2]. CommonJS/AMD는 라이브러리 차원의 관례였지만, ESM은 JS 엔진 자체가 이해하는 문법이다.

esm-example.js
// math.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;

// app.js
import { add, PI } from "./math.js";
console.log(add(1, 2), PI);

ESM이 CommonJS보다 우월한 지점은 단순히 문법 통일이 아니다. import/export는 정적(static)이다 — 즉 코드를 실행하지 않고도 "이 파일이 무엇을 가져오고 무엇을 내보내는지"를 파일을 읽는 것만으로 100% 알 수 있다. require()는 함수 호출이라 if (cond) require("a")처럼 런타임에만 결정될 수 있어 정적 분석이 불가능하다. 이 차이가 트리셰이킹을 가능하게 만든 핵심 조건이다.

script type=module 실제 동작 확인

무슨 일이 일어나는가

브라우저는 이미 오래전부터 <script type="module">을 네이티브로 지원한다[3]. 일반 <script>와 다른 점 세 가지를 직접 확인한다.

  • 일반 스크립트의 최상위 변수는 window에 붙지만, 모듈 스크립트의 최상위 변수는 모듈 스코프에 갇힌다.
  • 모듈 스크립트는 항상 defer된 것처럼 동작한다 — 문서 파싱이 끝난 뒤에 실행된다.
  • 모듈 최상위는 항상 strict mode이고, 최상위 this는 undefined다.

오른쪽 콘솔에서 순서를 눈여겨봐라. 아래에 있는 일반 스크립트가 위의 모듈 스크립트보다 먼저 로그를 찍을 수도 있다 — 그게 바로 "모듈은 defer된다"는 증거다.

핵심 ESM은 브라우저와 Node.js 양쪽의 표준 모듈 시스템이지만, 실무에서는 여전히 트랜스파일과 번들이 필요하다. 이유는 (1) 구형 브라우저 지원, (2) 수백 개 파일을 각각 네트워크 요청하면 느리다는 성능 문제, (3) TS/JSX처럼 ESM 문법이 아닌 것도 함께 처리해야 하기 때문이다.

§3번들러의 원리

엔트리와 의존성 그래프

번들러는 사람이 "이 파일부터 시작해"라고 지정한 엔트리(entry) 파일 하나에서 출발한다. 그 파일의 import문을 전부 읽어서 연결된 파일을 찾고, 그 파일들의 import도 또 읽는다. 이 과정을 재귀적으로 반복하면 프로젝트 전체가 하나의 의존성 그래프(dependency graph)로 그려진다. 

flowchart TD
  Entry["entry: main.tsx"] --> App["App.tsx"]
  App --> Header["Header.tsx"]
  App --> Router["Router.tsx"]
  Router --> Home["Home.tsx"]
  Router -->|"동적 import()"| Settings["Settings.tsx
별도 청크로 분리"]
  Header --> Fmt["utils/format.ts"]
  Home --> Fmt
그림 3. 엔트리에서 시작해 정적 import를 따라가며 만들어지는 의존성 그래프. 정적으로 연결된 노드는 같은 청크에, 동적 import()로 연결된 노드는 별도 청크가 된다.

그래프가 완성되면 번들러는 이걸 하나 이상의 출력 파일(청크)로 "평평하게" 펼친다. 이때 그래프 구조를 알고 있기 때문에 "이 파일이 실제로 쓰이는가"를 판단할 수 있고, 그게 다음 절의 트리셰이킹이다.

트리셰이킹이 되는 조건

트리셰이킹(tree shaking)[4]은 "엔트리에서 도달 가능한 export만 남기고 나머지는 버리는" 최적화다. 아래 미니 시뮬레이터로 원리를 직접 확인한다 — 실제 번들러(Rollup/esbuild)도 결국 이 "도달 가능성 분석(reachability analysis)"을 훨씬 정교하게 수행한다.

무슨 일이 일어나는가

  • moduleGraph — 어떤 export가 어떤 export를 참조하는지 기록한 표. 실제 번들러 내부의 그래프를 단순화한 것.
  • treeShake() — 엔트리(app.js:entry)에서 시작해 참조를 재귀적으로 따라가며 Set에 도달한 것만 쌓는다.
  • 결과적으로 subtract, multiplyUnused는 어디서도 참조되지 않으므로 reachable에 들어가지 않는다 — 이게 곧 "제거 대상"이라는 뜻.

트리셰이킹이 실제로 동작하려면 두 조건이 맞아야 한다.

조건이유
ESM 문법 사용 import/export는 정적이라 실행 없이 분석 가능하다. require()로 작성된 CommonJS 코드는 동적 호출이라 분석이 어렵다.
sideEffects 필드 package.json의 "sideEffects": false는 "이 패키지의 모듈은 import만 해도 부작용(전역 변수 설정, polyfill 등)이 없다"는 선언이다. 이게 있어야 번들러가 안심하고 미사용 export를 통째로 제거한다.
흔한 실수 import * as _ from "lodash"처럼 통째로 가져오면 트리셰이킹이 거의 불가능하다. import { debounce } from "lodash-es"처럼 named import를 쓰고, ESM 빌드(-es 접미사)를 제공하는 패키지를 골라야 한다.

코드 스플리팅과 동적 import

모든 페이지의 코드를 한 파일에 담으면, 사용자가 로그인 페이지만 볼 때도 관리자 대시보드 코드까지 다운로드해야 한다. 코드 스플리팅은 import() 함수 형태(동적 import)로 표시한 지점을 기준으로 번들을 여러 청크로 쪼갠다.

router.tsx
// 정적 import: 항상 초기 번들에 포함
import Home from "./pages/Home";

// 동적 import: 이 경로로 이동할 때만 별도 청크를 네트워크로 가져온다
const Settings = React.lazy(() => import("./pages/Settings"));

function App() {
  return (
    <Suspense fallback={<p>로딩 중...</p>}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}

번들러는 import()를 만나면 "여기가 청크 경계다"라고 판단하고, 그 시점부터 도달 가능한 모듈들을 별도 파일로 뽑아낸다. 성능 관점의 예산 잡기는 CH08 성능 최적화에서 더 다룬다.

청크와 해시 파일명

빌드 결과 파일명이 index-B3f8xk2A.js처럼 생긴 이유가 있다. 뒤의 무작위 문자열은 파일 내용의 해시다. 내용이 하나도 안 바뀌면 해시도 그대로라서, 브라우저는 캐시된 파일을 재사용한다. 내용이 1바이트라도 바뀌면 해시가 바뀌어 새 파일명이 되고, 브라우저는 새로 받는다. 이 방식 덕분에 "영구 캐시(Cache-Control: max-age=31536000, immutable)"를 걸어도 배포할 때마다 안전하게 캐시를 무효화할 수 있다.

§4트랜스파일 vs 폴리필

둘 다 "구형 환경 지원"을 위한 것이지만 layer가 다르다. 트랜스파일은 문법(syntax)을, 폴리필은 런타임 기능(API)을 다룬다. 화살표 함수(=>)는 문법이라 트랜스파일로 바꿀 수 있지만, Array.prototype.flat 같은 메서드는 문법이 아니라 런타임에 존재해야 하는 함수이므로 트랜스파일로는 만들어낼 수 없다 — 이건 폴리필의 일이다.

Babel / SWC / esbuild 역할 구분

도구구현 언어주 역할특징
Babel JavaScript 트랜스파일(문법 변환), 플러그인 기반 커스텀 변환 가장 오래됐고 가장 유연하다. 플러그인 생태계가 방대하지만 상대적으로 느리다. 이 학습서의 라이브 플레이그라운드도 Babel Standalone으로 동작한다.
SWC Rust 트랜스파일, 제한적 번들 Babel과 대부분 호환되는 변환을 훨씬 빠르게 수행한다. Next.js가 기본 컴파일러로 채택했다.
esbuild Go 트랜스파일 + 번들 + 미니파이 극단적으로 빠르다. Vite가 dev 서버의 의존성 사전 번들과 prod 빌드의 미니파이에 사용한다[5].

browserslist — "어디까지 지원할지"의 단일 진실 공급원

Babel, autoprefixer(CSS), core-js 같은 도구들이 "어떤 브라우저까지 지원해야 하는지"를 각자 따로 설정하면 기준이 어긋난다. package.json의 browserslist 필드(또는 .browserslistrc)에 쿼리를 한 번 적어두면, 이걸 지원하는 모든 도구가 같은 기준을 공유한다.

package.json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead",
    "not IE 11"
  ]
}

폴리필과 core-js

폴리필(polyfill)은 "이 함수가 없으면 내가 대신 구현해서 붙여준다"는 방식이다. core-js는 이런 폴리필을 모아둔 표준 라이브러리이고, Babel의 preset-env가 browserslist 기준을 보고 필요한 폴리필만 자동으로 골라 넣어준다.

무슨 일이 일어나는가

  • myFlat() — Array.prototype.flat이 없다고 가정하고 재귀로 직접 구현한 것. core-js가 내부적으로 하는 일과 원리는 같다.
  • if (!Array.prototype.flat) — 실제 폴리필들도 "이미 있으면 건드리지 않는다"는 방어 코드를 꼭 넣는다.
  • 중요한 점: 이 코드는 문법을 바꾸는 게 아니라 없는 메서드를 채워 넣는다 — 그래서 폴리필이다.

§5Vite

Vite는 "dev 서버"와 "prod 빌드"에서 서로 다른 전략을 쓰는 도구다[6]. 이걸 헷갈리면 "Vite가 빠르다"는 말의 절반만 이해하게 된다.

dev: 브라우저 네이티브 ESM + esbuild 사전번들

예전 방식(webpack dev server 등)은 개발 서버를 켤 때 프로젝트 전체를 한 번 번들링했다. 파일이 1000개면 서버가 뜨기 전에 1000개를 다 번들링해야 했다 — 프로젝트가 커질수록 dev 서버 기동 시간이 길어졌다.

Vite는 정반대로 접근한다. 브라우저가 이미 ESM을 네이티브로 지원한다는 점을 이용해서, 번들링을 거의 하지 않는다. 브라우저가 import "./Header.tsx"를 요청하면, 그 순간 Vite 서버가 그 파일 하나만 즉석에서 트랜스파일해서 응답한다. 즉 "요청받은 파일만 그때그때 변환"하는 온디맨드 방식이라 프로젝트 크기와 서버 기동 시간이 거의 무관하다.

단, node_modules의 라이브러리(예: lodash가 CommonJS로 수백 개 파일을 export하는 경우)는 예외다. 이런 건 브라우저가 요청할 때마다 수백 번 네트워크 요청을 하게 되므로, Vite는 시작 시점에 esbuild로 이런 의존성만 미리 하나의 ESM 파일로 사전 번들(pre-bundle)한다. esbuild는 Go로 만들어져 Babel/webpack보다 수십~수백 배 빠르기 때문에 이 사전 작업이 체감상 순식간에 끝난다.

build: Rollup

반면 프로덕션 빌드는 다르다. 네이티브 ESM을 그대로 배포하면 파일이 너무 많아 네트워크 요청 수가 폭발하고(HTTP/2라도 무시할 수 없는 오버헤드), 트리셰이킹·코드 스플리팅 같은 최적화도 못 받는다. 그래서 vite build는 Rollup을 사용해 실제로 번들링·트리셰이킹·미니파이를 수행한다[6]. 

flowchart TB
  subgraph DEV["개발 서버: vite dev"]
    direction LR
    Browser1["브라우저"] -->|"import 요청 (native ESM)"| DevServer["Vite Dev Server"]
    DevServer -->|"esbuild로 사전 번들 (1회)"| PreBundle["node_modules 의존성"]
    DevServer -->|"요청 시에만 온디맨드 변환"| SourceFiles["소스 파일 (.tsx 등)"]
  end
  subgraph BUILD["프로덕션 빌드: vite build"]
    direction LR
    Rollup["Rollup"] --> Chunks["해시된 청크 파일
.js / .css"]
    Chunks --> Browser2["브라우저"]
  end
그림 4. dev 서버는 번들링을 최소화하고 esbuild로 의존성만 사전 처리한다. prod 빌드는 Rollup으로 실제 번들·트리셰이킹·코드 스플리팅을 수행한다. 출처: vitejs.dev/guide/why
그래서 dev와 build가 "다른" 이유 dev의 목표는 "서버 기동 속도"와 "저장 즉시 반영"이고, build의 목표는 "최종 번들 크기와 캐시 효율"이다. 두 목표가 요구하는 최적화 전략이 근본적으로 다르기 때문에 Vite는 도구를 다르게 골랐다.

HMR(Hot Module Replacement) 원리

HMR은 파일을 저장했을 때 브라우저를 새로고침하지 않고 바뀐 모듈만 교체하는 기술이다. Vite는 파일 변경을 감지하면 WebSocket으로 브라우저에 "이 모듈이 바뀌었다"고 알리고, 브라우저는 해당 모듈만 다시 import해서 교체한다[7]. 

sequenceDiagram
  participant F as 파일시스템
  participant D as Vite Dev Server
  participant B as 브라우저

  F->>D: 파일 변경 감지 (watcher)
  D->>D: 변경된 모듈만 재컴파일
  D-->>B: WebSocket으로 업데이트 신호 전송
  B->>B: import.meta.hot.accept 콜백 실행
  B->>D: 새 모듈 코드 fetch (import)
  B->>B: DOM 갱신, 컴포넌트 상태(state)는 유지
그림 5. Vite HMR의 흐름. 페이지 전체를 새로고침하지 않으므로 입력값·스크롤 위치·컴포넌트 상태가 그대로 유지된다.

Vite는 import.meta.hot.accept(), import.meta.hot.dispose(), import.meta.hot.data 같은 API를 제공한다[7]. 아래는 그 개념을 직접 구현한 미니 시뮬레이터다 — "상태를 유지한 채 코드만 교체한다"는 핵심 아이디어를 확인할 수 있다.

무슨 일이 일어나는가

  • moduleRegistry — 모듈 id별로 exports와 state를 저장해두는 표. Vite 내부의 모듈 그래프를 단순화한 것.
  • defineModule() — 이전에 등록된 state가 있으면 그걸 이어받는다(prev ? prev.state : {}). 이게 "상태 유지"의 핵심.
  • hotUpdate() — 실제 파일 저장 시 Vite가 하는 일을 흉내낸 것. 새 factory로 다시 정의하되 state 객체는 그대로 넘긴다.

import.meta.env

Vite는 .env 파일의 값을 import.meta.env 객체로 클라이언트 코드에 주입한다[8]. 보안을 위해 기본적으로 VITE_ 접두사가 붙은 변수만 노출한다 — DB_PASSWORD 같은 서버 전용 값이 실수로 번들에 박혀버리는 걸 막기 위한 장치다.

.env
VITE_API_BASE=http://127.0.0.1:8787
DB_PASSWORD=secret   # VITE_ 접두사가 없으므로 클라이언트에 노출되지 않는다
src/api.ts
const apiBase = import.meta.env.VITE_API_BASE;
console.log(import.meta.env.MODE);  // "development" | "production"
console.log(import.meta.env.DEV);   // boolean
console.log(import.meta.env.PROD);  // boolean

정적 자산 처리

이미지·폰트 같은 정적 파일을 import하면 Vite는 개발 중엔 경로를 그대로 서빙하고, 빌드 시엔 해시가 붙은 파일명으로 dist/assets/에 복사한 뒤 그 최종 경로를 문자열로 돌려준다.

Logo.tsx
import logoUrl from "./logo.png"; // 문자열 URL로 import된다

function Logo() {
  return <img src={logoUrl} alt="logo" />;
}

React + TS + alias + proxy + 청크 분할

import react from "@vitejs/plugin-react";
import path from "node:path";

export default defineConfig({
  // React 컴포넌트를 트랜스파일하는 공식 플러그인 (내부적으로 Babel 또는 SWC 사용)
  plugins: [react()],

  resolve: {
    // import "@/components/Button" 처럼 상대경로 대신 별칭을 쓸 수 있게 한다
    alias: {
      "@": path.resolve(__dirname, "src"),
      "@components": path.resolve(__dirname, "src/components"),
    },
  },

  // dev 서버 전용 설정
  server: {
    port: 5174,
    // /api로 시작하는 요청을 백엔드로 우회(프록시)한다.
    // 프론트는 그냥 fetch("/api/...")만 호출하면 되고, CORS 설정 없이 8787로 전달된다.
    proxy: {
      "/api": {
        target: "http://127.0.0.1:8787",
        changeOrigin: true,
      },
    },
  },

  // import.meta.env로 노출할 환경변수 접두사. 기본값은 "VITE_"이며 배열로 확장 가능
  envPrefix: ["VITE_"],

  build: {
    rollupOptions: {
      output: {
        // 자주 안 바뀌는 라이브러리를 별도 청크로 묶어 캐시 적중률을 높인다
        manualChunks: {
          "react-vendor": ["react", "react-dom"],
          "query-vendor": ["@tanstack/react-query"],
        },
      },
    },
    // 청크 크기 경고 기준(KB). 넘으면 vite build가 경고를 출력한다
    chunkSizeWarningLimit: 600,
  },
});

필드별 설명

필드역할
plugins빌드 파이프라인에 훅을 거는 플러그인 배열. React, SVG 처리, PWA 등을 여기 추가한다.
resolve.aliasimport 경로 별칭. ../../../components 같은 상대경로 지옥을 없앤다.
server.proxydev 서버에서만 동작하는 요청 우회. 백엔드 CORS 설정을 프론트가 대신 회피한다.
build.rollupOptionsprod 빌드에 쓰이는 Rollup에 직접 옵션을 전달하는 통로. manualChunks로 청크 분할을 제어한다.
envPrefix클라이언트에 노출할 환경변수 접두사. 넓히면 노출 범위가 커지므로 신중히.
이 프로젝트 규칙 CH05에서 다루는 apiBase 하드코딩 금지 규칙은 바로 이 server.proxy 설정과 import.meta.env.VITE_API_BASE를 함께 쓰라는 뜻이다 — URL을 코드에 직접 박지 않는다.

semver: ^ ~ 정확한 버전

버전은 semver(MAJOR.MINOR.PATCH) 규칙을 따른다[13]. MAJOR가 바뀌면 호환이 깨질 수 있고, MINOR는 하위호환 기능 추가, PATCH는 버그 수정이다.

표기의미허용 범위 예시(1.2.3 기준)
^1.2.3가장 왼쪽 0이 아닌 자리를 고정, 그 이상은 자유1.2.3 ~ <2.0.0
~1.2.3MINOR까지 고정, PATCH만 자유1.2.3 ~ <1.3.0
1.2.3정확히 이 버전만1.2.3
^0.2.3MAJOR가 0일 땐 MINOR가 고정 자리가 된다(0.x는 아직 불안정하다는 semver 관례)0.2.3 ~ <0.3.0
* / latest아무 버전이나 허용 — lockfile 없이는 위험전체 범위

무슨 일이 일어나는가

  • satisfies() — 실제 npm/yarn이 내부적으로 하는 범위 판정을 단순화해서 직접 구현.
  • ^ 분기 — MAJOR가 0보다 크면 "MAJOR 고정, 나머지는 그 이상"으로 판정한다.
  • ~ 분기 — MAJOR·MINOR를 모두 고정하고 PATCH만 그 이상 허용한다.

lockfile이 존재하는 이유

package.json의 ^1.2.3은 "범위"이지 "정확한 값"이 아니다. 같은 package.json으로 오늘 설치한 사람과 한 달 뒤 설치한 사람이 서로 다른 PATCH 버전을 받을 수 있다. lockfile(yarn.lock, package-lock.json, pnpm-lock.yaml)은 실제로 설치된 정확한 버전과 의존성 트리 전체를 기록해서, 언제 누가 설치하든 완전히 동일한 결과를 보장한다. lockfile은 반드시 Git에 커밋해야 한다.

node_modules 호이스팅과 유령 의존성

npm/yarn classic은 중첩된 의존성을 최대한 평평하게(flat) 끌어올린다 — 이걸 호이스팅(hoisting)이라 한다. 예를 들어 내가 설치한 A가 내부적으로 B를 쓰면, B도 최상위 node_modules/에 끌어올려진다. 문제는 이렇게 되면 내가 package.json에 선언하지도 않은 B를 import "B"로 우연히 쓸 수 있게 된다는 것이다 — 이걸 유령 의존성(phantom dependency)이라 부른다[9]. 

flowchart TD
  App["my-app/package.json
dependencies: A"] --> A["A (직접 의존성)"]
  A --> B["B (A가 내부적으로 사용)"]
  Hoist["최상위 node_modules/"] -.-> A
  Hoist -.-> B
  App -.->|"import B (선언 안 했지만 우연히 동작)"| B
  style B stroke-dasharray: 5,5
그림 6. B는 package.json에 선언되지 않았지만, A의 의존성으로 호이스팅되어 최상위에 존재하기 때문에 import "B"가 우연히 성공한다. A가 나중에 B를 안 쓰게 바뀌면 이 import는 아무 경고 없이 깨진다.
왜 위험한가 유령 의존성은 로컬에서는 잘 동작하다가, 다른 사람의 환경(설치 순서·다른 패키지 버전 조합에 따라 호이스팅 결과가 달라짐)이나 CI에서 갑자기 "Cannot find module"로 깨진다. Yarn Berry의 PnP는 이 문제를 구조적으로 차단한다(§8).

§8Yarn Berry(Yarn 4) 심화

Plug'n'Play(PnP) — node_modules 없이 모듈을 찾는 법

Plug'n'Play(PnP)는 node_modules를 아예 만들지 않는다[11]. 대신 모든 패키지가 정확히 어디에 있는지(대부분 .yarn/cache/ 안의 zip 파일 내부 경로) 기록한 .pnp.cjs 파일 하나를 만들고, Node의 모듈 해석(require/resolve) 과정에 이 파일을 끼워 넣는다.

    W1 --> F1["파일 발견
(호이스팅으로 우연히 찾을 수도)"]
  end

    R2["require('react')"] --> M[".pnp.cjs 조회 맵

그림 7. node_modules 방식은 디스크를 탐색하며 우연히 유령 의존성을 찾아낼 수 있지만, PnP는 미리 계산된 맵을 한 번 조회할 뿐이라 더 빠르고, 선언 안 된 의존성은 구조적으로 접근이 막힌다.

PnP가 주는 세 가지 이점은 다음과 같다.

  • 설치 속도 — 디스크에 수만 개의 작은 파일을 복사/링크할 필요가 없다. zip 안의 내용을 그대로 둔 채 맵만 만든다.
  • 디스크 사용량 — 같은 버전의 패키지를 여러 프로젝트가 쓸 때 전역 캐시를 공유해서 중복 저장을 줄인다.
  • 엄격성 — 유령 의존성이 구조적으로 불가능하다. package.json에 선언하지 않은 패키지를 import하면 즉시 명확한 에러가 난다.

PnP가 차단하는 상황을 직접 시뮬레이션해본다 — 실제 Yarn PnP가 내는 에러 메시지 형식과 동일하다[11].

무슨 일이 일어나는가

  • pnpMap — .pnp.cjs가 실제로 갖고 있는 "패키지 이름 → zip 내부 경로" 맵을 단순화한 것.
  • dependencyTree — package.json에 실제 선언된 의존성만 기록.
  • pnpResolve() — 선언되지 않은 패키지를 요청하면 Yarn PnP와 동일한 형식의 에러를 던진다.

Zero-Install

Zero-Install은 .yarn/cache/ 안의 압축된 패키지 zip 파일들을 Git에 커밋하는 전략이다[12]. 이렇게 하면 저장소를 clone한 직후 yarn install을 아예 실행하지 않고도 바로 실행 가능한 상태가 된다 — CI에서도 설치 단계가 사실상 사라진다.

장점단점
Zero-Install clone 직후 즉시 실행, CI에서 설치 시간 제거, 오프라인에서도 동작 레포 용량 증가(zip 파일들이 Git 히스토리에 쌓임), PR diff에 바이너리 변경이 섞임
트레이드오프 레포 용량이 민감한 프로젝트라면 Zero-Install 없이 .yarn/cache/를 .gitignore하고 CI에서 yarn install --immutable만 돌리는 일반 구성도 충분히 합리적이다. 이 프로젝트는 후자를 기본으로 한다.

yarn dlx @yarnpkg/sdks vscode
5번을 꼭 해야 하는 이유 PnP를 쓰면 실제 typescript 패키지가 .yarn/cache/typescript-npm-...zip 안에 있다. VSCode의 내장 TS 서버는 이 경로를 모르기 때문에 "타입을 못 찾음" 오류를 낸다. yarn dlx @yarnpkg/sdks vscode는 .vscode/settings.json에 워크스페이스 전용 TS 버전 경로를 자동으로 등록해준다[17].

Workspaces(모노레포)

하나의 Git 레포 안에 여러 패키지(예: packages/ui, packages/api-client, apps/web)를 두고, 서로를 node_modules 재설치 없이 참조하게 하는 구조를 모노레포(monorepo)라 한다.

package.json (루트)
{
  "name": "my-workspace",
  "private": true,
  "workspaces": ["packages/*", "apps/*"]
}
apps/web/package.json
{
  "dependencies": {
    "@ops/ui": "workspace:*"
  }
}

workspace:* 프로토콜은 "이 의존성은 레지스트리에서 받지 말고, 같은 레포 안의 워크스페이스를 심볼릭 링크로 연결해라"는 뜻이다[18]. @ops/ui를 수정하면 apps/web에서 다시 설치할 필요 없이 즉시 반영된다.

terminal
# 모든 워크스페이스에서 순서대로(의존성 그래프 순서) build 스크립트 실행
yarn workspaces foreach --all run build

# 특정 워크스페이스에만 의존성 추가
yarn workspace @ops/ui add lodash-es

자주 만나는 에러와 해결

에러/증상원인해결
X tried to access Y, but it isn't declared in its dependencies 유령 의존성 — package.json에 선언 안 한 패키지를 import함 실제로 쓰는 패키지를 dependencies에 직접 추가한다.
ESLint/Prettier 플러그인이 에디터에서 "모듈을 찾을 수 없음" 에디터가 PnP의 .pnp.cjs 경로 해석 방식을 모름 yarn dlx @yarnpkg/sdks vscode 재실행, 또는 해당 에디터 확장의 PnP 지원 확인.
어떤 패키지가 잘못된(비공식) peer dependency를 요구해서 경고/에러 패키지 저자가 peerDependencies를 실제보다 좁게/느슨하게 선언함 .yarnrc.yml의 packageExtensions로 해당 패키지의 peer 선언을 보정한다.
.yarnrc.yml — packageExtensions 예시
packageExtensions:
  "some-legacy-package@*":
    peerDependencies:
      react: "*"   # 저자가 누락한 peer dependency를 직접 보정

§10빌드 결과 분석

vite build 출력 읽는 법

vite build를 실행하면 각 청크의 원본 크기와 gzip 압축 후 크기가 함께 출력된다. 실제 네트워크로 전송되는 크기는 gzip(또는 brotli) 쪽에 가깝다는 걸 기억해야 한다.

무슨 일이 일어나는가

  • buildOutput — vite build가 실제로 찍는 출력 형식을 흉내낸 문자열.
  • parseBuildOutput() — 정규식으로 파일명·원본 크기·gzip 크기를 뽑아낸다.
  • JS 합계가 예산(여기선 임의로 170KB)을 넘으면 "코드 스플리팅 검토" 경고를 낸다 — 실무에서 CI에 넣는 번들 크기 체크의 축소판.

rollup-plugin-visualizer

어떤 패키지가 번들 크기를 얼마나 차지하는지 트리맵으로 시각화하는 플러그인이다. vite build가 내부적으로 Rollup을 쓰기 때문에 Rollup 플러그인을 그대로 vite.config.ts의 plugins에 추가해서 쓸 수 있다.

vite.config.ts (분석용 부분)
import { visualizer } from "rollup-plugin-visualizer";

export default defineConfig({
  plugins: [
    react(),
    // build 후 stats.html이 생성되어, 각 패키지가 번들에서 차지하는 비중을 트리맵으로 보여준다
    visualizer({ filename: "stats.html", gzipSize: true }),
  ],
});

번들 크기 예산 잡기

"일단 만들고 나중에 최적화"는 번들 크기에서 특히 잘 안 통한다. 처음부터 청크별 gzip 크기 상한을 정해두고 build.chunkSizeWarningLimit(§6)로 경고를 받거나, CI에서 위 미니 분석기와 같은 로직으로 예산 초과를 자동 체크하는 걸 권장한다. Web Vitals와 연결된 실제 성능 영향은 CH08 성능 최적화에서 이어서 다룬다.

이해도 점검

  • 브라우저가 이해하지 못하는 것 4가지(TS 타입, JSX, 최신 문법, bare specifier)를 설명할 수 있다.
  • 전역 스크립트 → IIFE → CommonJS → AMD → ESM 순서와 각 단계가 해결한 문제를 설명할 수 있다.
  • <script type="module">이 defer되고, 최상위 변수가 window로 새지 않는다는 걸 실습으로 확인했다.
  • 트리셰이킹이 되려면 ESM 문법 + sideEffects 필드가 필요한 이유를 설명할 수 있다.
  • 코드 스플리팅과 청크 해시 파일명이 캐시 전략과 어떻게 연결되는지 안다.
  • Babel/SWC/esbuild의 역할 차이를 표 없이도 말할 수 있다.
  • 트랜스파일(문법)과 폴리필(런타임 기능)의 차이를 예시와 함께 설명할 수 있다.
  • Vite dev 서버가 esbuild 사전번들 + 네이티브 ESM으로 빠른 이유, build가 Rollup을 쓰는 이유를 안다.
  • Vite HMR이 WebSocket + import.meta.hot로 상태를 유지한 채 모듈만 교체하는 흐름을 안다.
  • vite.config.ts의 alias/proxy/rollupOptions/envPrefix가 각각 무슨 문제를 푸는지 안다.
  • ^와 ~의 허용 범위 차이를 예시 버전으로 계산할 수 있다.
  • 호이스팅이 만드는 유령 의존성 문제를 그림으로 설명할 수 있다.
  • Yarn PnP가 .pnp.cjs로 유령 의존성을 원천 차단하는 원리를 안다.
  • Zero-Install의 장단점(설치시간 제거 vs 레포 용량)을 설명할 수 있다.
  • nodeLinker 3종(pnp/node-modules/pnpm)의 선택 기준을 안다.
  • Yarn Berry 마이그레이션 절차(corepack enable → set version stable → install → sdks)를 순서대로 안다.
  • npm/pnpm/Yarn Berry를 언제 골라야 하는지 상황별로 말할 수 있다.
