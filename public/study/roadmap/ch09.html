CHAPTER 09

렌더링 전략 & 접근성

브라우저가 HTML을 화면으로 바꾸는 전체 과정부터, CSR·SSR·SSG·ISR·RSC 중 무엇을 언제 써야 하는지, 그리고 그 페이지를 스크린 리더 사용자와 키보드만 쓰는 사용자도 문제없이 쓸 수 있게 만드는 방법까지 다룬다.

시맨틱 HTML 렌더링 파이프라인 CSR / SSR / SSG / ISR Hydration RSC Suspense WCAG 2.2 ARIA

이 챕터는 다음 질문에 답한다. 브라우저는 HTML 한 줄을 받아서 어떤 단계를 거쳐 화면에 그리는가? CSR·SSR·SSG·ISR 중 내 페이지에는 무엇이 맞는가? 하이드레이션은 왜 필요하고 어디서 깨지는가? React Server Components는 무엇을 서버에만 남기고 무엇을 클라이언트로 보내는가? 스크린 리더 사용자는 내가 만든 페이지를 어떤 구조로 인식하며, WCAG를 지키려면 실무에서 정확히 무엇부터 고쳐야 하는가?

§1HTML 기초 다지기

모든 렌더링 전략과 접근성 이야기는 결국 하나의 질문에서 시작한다. "이 HTML이 무엇을 의미하는가?" 시맨틱(semantic) HTML은 태그 이름만으로 그 구획이 무엇인지 브라우저·검색엔진·스크린 리더에게 알려준다. div와 span은 의미가 없는 상자일 뿐이라, 똑같은 화면을 그리더라도 기계 입장에서는 아무 정보가 없다.

시맨틱 태그와 div 남용의 비용

HTML5는 문서 구조를 나타내는 랜드마크 태그를 제공한다. 이 태그들은 각각 암묵적 role을 가지고 있어서, 별도 설정 없이도 접근성 트리에 랜드마크로 등록된다.

태그암묵적 role용도
<header>banner(최상위일 때만)사이트/섹션 상단 영역
<nav>navigation내비게이션 링크 묶음
<main>main페이지의 핵심 콘텐츠. 문서당 1개만
<section>region(제목이 있을 때)주제별로 묶은 콘텐츠 구획
<article>article독립적으로 배포 가능한 콘텐츠(게시글, 카드)
<aside>complementary본문과 간접적으로 관련된 부가 콘텐츠
<footer>contentinfo(최상위일 때만)저작권, 연락처 등 하단 정보

div만으로 페이지를 짜면 겉보기엔 똑같이 보인다. 하지만 스크린 리더 사용자는 랜드마크 단위로 페이지를 건너뛰며 탐색하는데[1], div만 있는 문서에는 건너뛸 지점 자체가 없다. 검색엔진도 어디가 본문이고 어디가 내비게이션인지 구조적으로 판단하지 못해 SEO 신호가 약해진다. 아래에서 같은 내용을 div로만 짠 버전과 시맨틱 태그로 짠 버전을 직접 비교해본다.

무슨 일이 일어나는가

오른쪽은 동일한 내용을 두 가지 방식으로 렌더링한 뒤, querySelectorAll로 실제 랜드마크 태그 개수를 세어 보여준다.

  • div 버전 — header/nav/main/footer 자리에 전부 <div>만 사용. 시각적으로는 동일.
  • 시맨틱 버전 — 같은 자리에 <header>, <nav>, <main>, <footer> 사용.
  • 버튼을 눌러 전환하면 "브라우저가 인식한 랜드마크" 목록이 실시간으로 바뀐다.
핵심 div가 나쁜 게 아니라 "의미 없는 순수 레이아웃 상자"일 때만 div를 쓴다는 게 규칙이다. 의미가 있는 구획이라면 항상 시맨틱 태그가 우선이다.

§2브라우저가 페이지를 그리는 전체 과정

서버에 요청을 보내고 화면이 뜨기까지, 브라우저는 정해진 순서를 밟는다. 이 순서를 알아야 "왜 CSS가 렌더링을 막는지", "왜 script 태그 위치가 중요한지"를 이해할 수 있다.

단계별로 보면 다음과 같다.

  • HTML 파싱 → DOM — HTML을 한 줄씩 읽으며 태그를 트리 노드로 바꾼다.
  • CSS 파싱 → CSSOM — 모든 CSS 규칙을 읽어 선택자·속성 트리를 만든다. 이 작업이 끝나야 다음 단계로 넘어간다.
  • 렌더 트리 — DOM과 CSSOM을 합쳐, 실제로 그려질 노드만 남긴다.
  • 레이아웃(Layout) — 각 노드의 크기와 위치를 계산한다.
  • 페인트(Paint) — 계산된 위치에 실제 픽셀(색, 테두리, 그림자)을 그리고, 레이어를 합성해 화면에 표시한다.

렌더 블로킹 리소스와 defer/async

CSS는 기본적으로 렌더 블로킹(render-blocking) 리소스다. CSSOM이 완성되기 전에는 렌더 트리를 만들 수 없기 때문에, 브라우저는 CSS를 다 읽을 때까지 화면을 그리지 않는다.

JS는 더 심하다. HTML 파서가 <script> 태그를 만나면, 별다른 옵션이 없는 한 파싱을 완전히 멈추고 스크립트를 다운로드·실행한 뒤에야 이어서 파싱한다. 스크립트가 DOM을 조작할 수도 있으니 순서를 보장하기 위해서다. defer와 async는 이 문제를 다르게 해결한다[2].

그림 2. 진하게 칠해진 구간이 실제 스크립트 실행 시점이다. 일반 script는 그 자리에서 파싱을 막고, defer는 파싱이 끝난 뒤 문서 순서대로, async는 준비되는 즉시 순서 보장 없이 실행된다. 출처: MDN — script 요소[2]

요약 브라우저는 항상 "파싱 → DOM/CSSOM → 렌더 트리 → 레이아웃 → 페인트" 순서를 따른다. 이 파이프라인을 늦추는 두 축은 CSS(항상 렌더 블로킹)와 JS(옵션에 따라 다름)다. 다음 §3부터는 "그 HTML 자체를 언제, 어디서 만들어낼 것인가"를 다룬다 — 이 파이프라인이 브라우저에서 도는지, 서버에서 미리 끝내고 오는지의 차이다.

§3렌더링 전략 개관 — CSR / SSR / SSG / ISR / 스트리밍 SSR

"렌더링 전략"이란 결국 하나의 질문이다. HTML을 언제, 어디서 완성하는가? 브라우저에서 완성하면 CSR, 요청이 올 때마다 서버에서 완성하면 SSR, 빌드 시점에 미리 완성해두면 SSG, 그 중간이 ISR이다.

CSR — Client-Side Rendering

CSR은 서버가 거의 빈 HTML 껍데기(<div id="root"></div>)와 JS 번들 링크만 내려주고, 화면은 브라우저에서 JS가 실행되며 그린다.

sequenceDiagram
  participant B as 브라우저
  participant S as 서버
  B->>S: GET /page
  S-->>B: 거의 빈 HTML + JS 번들 링크
  B->>B: JS 다운로드·파싱·실행
  B->>S: API 요청 (데이터)
  S-->>B: JSON 응답
  B->>B: React가 DOM을 그림 → 화면 표시
그림 3. CSR의 요청-응답 흐름. 화면이 뜨기까지 "JS 다운로드 → 실행 → 데이터 요청"을 순서대로 기다려야 한다.

SSR — Server-Side Rendering

SSR은 요청이 올 때마다 서버가 데이터를 조회하고 완성된 HTML을 만들어 내려준다. 브라우저는 그 HTML을 받자마자 화면에 표시할 수 있다.

sequenceDiagram
  participant B as 브라우저
  participant S as 서버
  B->>S: GET /page
  S->>S: 데이터 조회 + HTML 렌더링
  S-->>B: 완성된 HTML
  B->>B: 즉시 화면 표시 (FCP)
  B->>S: JS 번들 요청
  S-->>B: JS 번들
  B->>B: 하이드레이션 완료 → 상호작용 가능
그림 4. SSR의 요청-응답 흐름. HTML은 빨리 보이지만, 클릭 가능해지려면 하이드레이션까지 기다려야 한다.

SSG — Static Site Generation

SSG는 빌드 시점에 모든 페이지의 HTML을 미리 만들어 CDN에 올려둔다. 요청이 오면 서버 연산 없이 정적 파일을 그대로 내려주므로 가장 빠르고, 서버 비용도 가장 낮다. 대신 데이터가 바뀌어도 다시 빌드하기 전까지는 페이지가 갱신되지 않는다.

ISR — Incremental Static Regeneration

ISR은 SSG처럼 정적 HTML을 캐시해 두되, 지정한 주기(예: 60초)가 지나면 다음 요청 시 백그라운드에서 새로 생성해 캐시를 교체한다. "거의 정적만큼 빠르면서, 완전히 굳어있지는 않은" 절충안이다[5].

스트리밍 SSR

스트리밍 SSR은 SSR의 약점 — "가장 느린 데이터 하나가 전체 HTML 응답을 막는다" — 을 해결한다. 페이지를 Suspense 경계로 쪼개서, 준비된 부분부터 먼저 스트리밍하고 느린 부분은 나중에 이어붙인다. §6에서 이 원리를 자세히 다룬다.

server.tsx — renderToPipeableStream 골격
import { renderToPipeableStream } from 'react-dom/server';

app.get('/', (req, res) => {
  const { pipe } = renderToPipeableStream(<App />, {
    // 가장 먼저 그려져야 할 껍데기(shell)가 준비되면 즉시 스트리밍 시작
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      pipe(res);
    },
    onError(err) {
      console.error(err);
    },
  });
});

안에서 느린 데이터를 쓰는 컴포넌트를 <Suspense>로 감싸두면, shell(뼈대)이 먼저 스트리밍되고 느린 조각은 준비되는 대로 같은 연결에 이어붙여 전송된다[10].

§4하이드레이션

SSR이나 SSG로 받은 HTML은 "보이지만 눌리지 않는" 상태다. 버튼처럼 보이는 마크업은 있지만 아직 아무 이벤트 리스너도 붙어있지 않기 때문이다. 하이드레이션(hydration)은 이 정적 HTML 위에 React가 같은 컴포넌트 트리를 클라이언트에서 다시 실행하며, DOM을 새로 만들지 않고 기존 노드에 이벤트 리스너만 "꽂아 넣는" 과정이다.

sequenceDiagram
  participant S as 서버
  participant B as 브라우저(HTML)
  participant J as React(JS)
  S-->>B: 정적 HTML 도착 (보이지만 클릭 안 됨)
  B->>J: JS 번들 로드 완료
  J->>B: 같은 DOM을 순회하며 이벤트 리스너 연결
  Note over B,J: 하이드레이션 완료 → 이제 클릭 가능
그림 6. 하이드레이션은 DOM을 새로 그리지 않고, 이미 있는 노드에 이벤트를 "덧붙이는" 과정이다.

하이드레이션 미스매치가 나는 대표 원인

서버가 만든 HTML과 클라이언트가 처음 렌더링한 결과가 한 글자라도 다르면 React는 경고를 띄우고, 다른 부분을 클라이언트 결과로 덮어쓴다. 대표적인 원인 네 가지는 다음과 같다.

Date / Math.random()

서버가 렌더링한 시각과 클라이언트가 하이드레이션하는 시각은 다르다. new Date().toLocaleString()을 렌더링 중에 직접 쓰면 값이 어긋난다.

localStorage 접근

서버 환경에는 window, localStorage가 없다. 렌더링 중 이를 읽어 초기 상태를 정하면 서버는 기본값, 클라이언트는 저장된 값으로 서로 달라진다.

브라우저 확장 프로그램

일부 확장 프로그램(번역기, 광고 차단기 등)이 HTML이 도착한 직후 DOM에 속성이나 노드를 주입해, React가 기대한 서버 마크업과 어긋나게 만든다.

조건부 렌더링 불일치

typeof window !== 'undefined' 같은 분기를 렌더링 함수 안에 두면, 서버(undefined)와 클라이언트(존재)에서 다른 분기를 타게 된다.

흔한 실수 브라우저 전용 값이 필요하면 렌더링 중이 아니라 useEffect 안에서 읽어야 한다. useEffect는 하이드레이션이 끝난 뒤 클라이언트에서만 실행되므로, 초기 렌더 결과가 서버와 어긋날 일이 없다.

부분 하이드레이션과 아일랜드 아키텍처

페이지 전체를 하이드레이션하면, 페이지 대부분이 정적 텍스트라도 JS 실행 비용은 전체 컴포넌트 트리만큼 든다. 아일랜드 아키텍처(islands architecture)는 상호작용이 필요한 부분(좋아요 버튼, 캐러셀 등)만 "섬"으로 표시해 그 부분만 하이드레이션하고, 나머지는 순수 HTML로 남긴다.

그림 7. 아일랜드 아키텍처 — 상호작용이 필요한 영역만 개별 하이드레이션 대상이 된다.

§5React Server Components(RSC)

RSC는 컴포넌트를 "서버 컴포넌트"와 "클라이언트 컴포넌트" 두 종류로 나눈다. 기본값은 서버 컴포넌트다. 무언가 클라이언트 전용 기능(state, 이벤트 핸들러, 브라우저 API)이 필요할 때만 파일 맨 위에 'use client'를 써서 클라이언트 컴포넌트로 명시한다[8].

그림 8. 서버 컴포넌트는 트리 상단에서 데이터를 직접 조회하고, 상호작용이 필요한 잎(leaf) 노드만 'use client' 경계를 넘는다.

'use client'의 의미

'use client'는 "여기서부터는 클라이언트에서도 실행된다"는 경계 선언이다. 실무에서 확인된 사실만 정리하면 다음과 같다.

  • 번들에 포함되는 것 — 'use client'가 붙은 파일과 그 파일이 import하는 코드는 클라이언트 JS 번들에 포함된다.
  • 번들에 포함되지 않는 것 — 서버 컴포넌트 코드(DB 쿼리, 파일 시스템 접근, 비밀 API 키 사용 코드)는 클라이언트로 전송되지 않는다. 브라우저 devtools에서 열어봐도 그 코드는 보이지 않는다.
  • 데이터 페칭 위치의 변화 — 기존 CSR/SSR 패턴에서는 클라이언트가 useEffect나 TanStack Query로 API를 호출했다. 서버 컴포넌트에서는 컴포넌트 함수 안에서 바로 await fetch(...) 혹은 DB 클라이언트를 호출할 수 있다.
  • 경계는 한 방향 — 서버 컴포넌트는 클라이언트 컴포넌트를 자식으로 가질 수 있지만, 클라이언트 컴포넌트가 서버 컴포넌트를 직접 import해서 그 안에서 쓸 수는 없다(단, children으로 전달받는 것은 가능하다).

Next.js App Router 기준으로는 파일이 'use client' 선언 없이 작성되면 기본적으로 서버 컴포넌트로 취급된다[6]. 반대로 상태·이벤트·브라우저 전용 API가 필요한 컴포넌트는 파일 최상단에 'use client'를 선언해 클라이언트 컴포넌트로 전환한다[7][9].

app/products/page.tsx — 서버 컴포넌트
// 'use client' 없음 → 기본값인 서버 컴포넌트
import { LikeButton } from './LikeButton';

export default async function ProductPage() {
  const products = await db.query('SELECT * FROM products'); // 서버에서만 실행
  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>
          {p.name}
          <LikeButton productId={p.id} />
        </li>
      ))}
    </ul>
  );
}
app/products/LikeButton.tsx — 클라이언트 컴포넌트
'use client'; // 이 파일부터 클라이언트 번들에 포함된다
import { useState } from 'react';

export function LikeButton({ productId }: { productId: string }) {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked((v) => !v)}>
      {liked ? '♥ 좋아요 취소' : '♡ 좋아요'}
    </button>
  );
}
사실만 RSC는 React 자체의 런타임 기능이지만, 실제로 쓰려면 서버 렌더링을 지원하는 프레임워크(Next.js App Router 등)가 필요하다. Vite로만 만든 순수 CSR 앱에는 RSC 개념이 적용되지 않는다.

§6Suspense와 스트리밍

Suspense는 "아직 준비 안 된 컴포넌트가 있으면 그 자리에 로딩 UI를 대신 보여준다"는 한 가지 역할만 한다. 컴포넌트가 데이터/코드를 기다리는 동안 fallback prop으로 넘긴 UI가 대신 그려지고, 준비되면 자동으로 교체된다[10].

워터폴 방지

데이터를 하나씩 순서대로 기다리면(A 끝나야 B 시작) 전체 로딩 시간이 각 요청 시간의 합이 된다. 이를 워터폴(waterfall)이라 부른다. Suspense 자체가 워터폴을 없애주지는 않지만, 여러 데이터 요청을 병렬로 시작해두고 각각을 독립된 Suspense 경계로 감싸면, 먼저 준비된 부분부터 순서 상관없이 화면에 나타나게 만들 수 있다.

워터폴 vs 병렬 요청
// 나쁨 — 순차 워터폴: user 끝나야 posts 시작
const user = await fetchUser(id);
const posts = await fetchPosts(id);

// 좋음 — 두 요청을 동시에 시작하고 함께 기다림
const [user, posts] = await Promise.all([fetchUser(id), fetchPosts(id)]);

아래 예제는 React.lazy로 컴포넌트를 지연 로드하면서, 실제로 준비되기 전까지 Suspense의 fallback이 어떻게 보이는지 직접 확인한다. 지연 로드 모듈을 흉내 내기 위해 1.5초 뒤 resolve되는 Promise를 사용했다 — 실제 import()가 네트워크에서 청크를 받아오는 시간을 흉내 낸 것이다.

무슨 일이 일어나는가

"차트 보기"를 누르면 <Suspense>가 자식(LazyChart)이 아직 준비 안 됐다는 걸 감지하고 fallback을 먼저 그린다.

  • lazy(() => new Promise(...)) — 진짜 import() 대신, 1.5초 뒤 컴포넌트를 resolve하는 가짜 지연 모듈.
  • <Suspense fallback=...> — 자식이 아직 pending 상태면 fallback을 대신 렌더링.
  • Promise가 resolve되는 순간 React가 자동으로 실제 컴포넌트로 교체한다. 별도 상태 관리 코드가 없다.

스트리밍 SSR은 이 원리를 서버 응답 자체에 적용한 것이다. 페이지를 여러 <Suspense> 경계로 나눠두면, 서버는 준비된 조각부터 HTML 스트림으로 먼저 보내고, 느린 조각은 나중에 같은 연결로 이어붙여 보낸다. 사용자는 전체 데이터를 기다리지 않고 먼저 준비된 부분부터 보게 된다.

§7라우팅

SPA에서 "페이지 이동"은 실제 페이지 새로고침이 아니다. 브라우저 내장 History API를 이용해 주소창 URL만 바꾸고, JS가 그 URL에 맞는 컴포넌트를 화면에 그린다[11].

  • history.pushState(state, '', url) — 새로고침 없이 히스토리에 새 항목을 추가하고 주소창 URL을 바꾼다.
  • history.replaceState(state, '', url) — 새 항목을 추가하지 않고 현재 항목을 교체한다(리다이렉트에 사용).
  • popstate — 사용자가 뒤로/앞으로 가기를 누르면 발생하는 이벤트. 이때 현재 URL에 맞춰 화면을 다시 그려야 한다.

클라이언트 라우터(react-router-dom 등)가 실제로 하는 일은 이 세 가지를 감싸는 것뿐이다. 링크 클릭을 가로채 pushState로 바꾸고, popstate를 구독해 현재 경로에 맞는 컴포넌트를 렌더링한다. 아래에서 그 최소 구현을 직접 만들어본다.

무슨 일이 일어나는가

링크를 누르면 실제 페이지 새로고침 없이 pushState로 주소를 바꾸고, 경로에 맞는 화면을 다시 그린다.

  • navigate(path) — history.pushState로 URL 변경 후 render() 직접 호출.
  • window.addEventListener('popstate', render) — 뒤로가기 버튼(또는 history.back())이 눌렸을 때도 화면을 다시 그린다.
  • 실제 <a> 클릭의 기본 동작(새로고침)은 preventDefault()로 막는다.

중첩 라우팅과 코드 스플리팅

실제 라우터는 경로를 계층적으로 매칭한다. /projects/:id/tasks처럼 부모 경로(/projects/:id)의 레이아웃 안에 자식 경로(/tasks)만 갈아끼우는 방식이다. 라우트 단위로 React.lazy를 적용하면, 방문하지 않은 페이지의 JS는 아예 다운로드되지 않는다 — Suspense가 그 로딩 UI를 담당한다.

routes.tsx — 라우트 단위 코드 스플리팅
import { lazy, Suspense } from 'react';
import { Routes, Route } from 'react-router-dom';

const ProjectPage = lazy(() => import('./pages/ProjectPage'));
const ReportPage = lazy(() => import('./pages/ReportPage'));

export function AppRoutes() {
  return (
    <Suspense fallback={<p>로딩 중...</p>}>
      <Routes>
        <Route path="/projects/:id" element={<ProjectPage />} />
        <Route path="/reports" element={<ReportPage />} />
      </Routes>
    </Suspense>
  );
}

§8접근성(a11y) 1 — 왜, 그리고 어떻게 인식되는가

접근성(a11y)을 지켜야 하는 이유는 두 가지다. 첫째, 세계 인구의 상당수가 시각·청각·운동·인지 장애를 가지고 있고, 그 규모는 일시적 손상(팔 부상)이나 상황적 제약(밝은 야외에서 화면이 잘 안 보임)까지 포함하면 훨씬 커진다. 둘째, 여러 국가에서 공공/민간 웹사이트의 접근성 준수를 법적으로 요구한다[19].

스크린 리더가 페이지를 읽는 방식

스크린 리더는 화면의 픽셀을 보지 않는다. 대신 브라우저가 DOM으로부터 만들어낸 접근성 트리(accessibility tree)를 순회하며 읽는다[16]. 접근성 트리의 각 노드는 세 가지 정보만 갖는다: role(무엇인가: 버튼? 링크? 제목?), name(뭐라고 불리는가), state(지금 어떤 상태인가: 눌림/펼침/비활성 등).

flowchart LR
  subgraph DOM["DOM 트리 (눈에 보이는 구조)"]
    d1["div.wrapper"] --> d2["div.header"]
    d2 --> d3["img (장식용 배경, alt 없음)"]
    d2 --> d4["span.title '오늘의 배포 현황'"]
    d1 --> d5["button (아이콘만, 텍스트 없음)"]
  end
  subgraph AT["접근성 트리 (스크린 리더가 읽는 것)"]
    a1["banner"] --> a2["heading: '오늘의 배포 현황'"]
    a1 --> a3["button: (이름 없음 ⚠)"]
  end
그림 9. 장식용 이미지는 접근성 트리에서 제외되고, 이름 없는 아이콘 버튼은 "이름 없음"으로 노출되어 스크린 리더 사용자에게 아무 정보도 주지 못한다.

키보드만으로 조작하기

마우스를 쓰지 않는 사용자(운동 장애, 스크린 리더 사용자, 단순히 키보드가 빠른 사용자 포함)는 Tab과 Shift+Tab으로 페이지를 순회한다. 이때 세 가지가 핵심이다.

  • Tab 순서(tab order) — 기본적으로 DOM에 등장하는 순서를 따른다. tabindex를 양수로 주면 이 순서를 억지로 바꾸게 되어 대부분 혼란만 유발한다[20].
  • 포커스 표시(focus visible) — 지금 어떤 요소에 포커스가 있는지 시각적으로 보여야 한다. outline: none으로 지워버리는 것은 대표적인 접근성 위반이다.
  • 스킵 링크(skip link) — 페이지 맨 앞에 "본문 바로가기" 링크를 숨겨두고 Tab으로 포커스되면 나타나게 하면, 반복되는 내비게이션을 매번 Tab으로 통과하지 않아도 된다.

무슨 일이 일어나는가

Tab 키로 요소를 옮겨가며, 어떤 요소가 포커스를 받을 수 있고 어떤 요소가 받지 못하는지 로그로 확인한다.

  • 스킵 링크 — 평소엔 화면 밖에 있다가 Tab으로 포커스되면 나타난다.
  • 일반 <button> — 브라우저가 자동으로 Tab 대상이 되고, Enter/Space로 클릭된다.
  • tabindex="0" + role="button"인 div — Tab 대상은 되지만, Enter/Space 클릭은 직접 keydown으로 구현해야 동작한다.
  • 아무 설정 없는 div — 클릭은 되지만 Tab으로는 절대 도달할 수 없다.
흔한 실수 ②번처럼 role="button"과 tabindex="0"을 줘도 Enter/Space 클릭은 자동으로 동작하지 않는다. 브라우저가 공짜로 처리해주는 것은 진짜 <button> 요소뿐이다. 가능하면 항상 네이티브 요소(button, a, input)를 먼저 고려한다.

§9접근성(a11y) 2 — WCAG 2.2와 실무 체크포인트

WCAG 2.2는 접근성을 네 가지 원칙(POUR)으로 나눈다[12].

P — Perceivable (인식 가능)

정보와 UI 구성요소를 사용자가 인식할 수 있는 방식으로 제공해야 한다. 대체 텍스트, 색 대비가 여기 속한다.

O — Operable (운용 가능)

UI 구성요소와 내비게이션은 조작 가능해야 한다. 키보드 접근성, 충분한 시간 제공이 여기 속한다.

U — Understandable (이해 가능)

정보와 UI 조작 방법은 이해할 수 있어야 한다. 폼 라벨, 오류 안내가 여기 속한다.

R — Robust (견고성)

다양한 보조 기술이 콘텐츠를 신뢰성 있게 해석할 수 있어야 한다. 올바른 시맨틱/ARIA 마크업이 여기 속한다.

각 원칙 아래 기준마다 A(최소)/AA(대부분 법규가 요구하는 기준)/AAA(최고) 레벨이 있다. 실무에서는 보통 AA를 목표로 삼는다. 아래는 실무에서 가장 자주 걸리는 항목들이다.

색 대비 — 4.5:1 계산법과 검증

WCAG AA는 일반 텍스트에 4.5:1, 18pt 이상(또는 14pt bold 이상) 큰 텍스트에 3:1 이상의 대비율(contrast ratio)을 요구한다[17]. 계산 공식은 sRGB 값을 선형화해 상대 휘도(L)를 구한 뒤, (밝은 쪽 L + 0.05) / (어두운 쪽 L + 0.05)로 구한다. 아래에서 직접 색을 골라 계산해본다.

무슨 일이 일어나는가

WCAG 공식 그대로 sRGB → 선형 RGB → 상대 휘도 → 대비율을 계산한다.

  • srgbToLinear — 0~255 채널값을 감마 보정을 풀어 선형값으로 바꾼다.
  • relLuminance — R·G·B 선형값에 WCAG가 정한 가중치(0.2126/0.7152/0.0722)를 곱해 합산.
  • contrastRatio — 두 휘도 중 밝은 쪽/어두운 쪽을 나눠 최종 비율을 낸다.

대체 텍스트

이미지가 정보를 담고 있으면 alt에 그 정보를 요약한다. 장식용 이미지라면 alt=""(빈 문자열)로 명시해 스크린 리더가 아예 건너뛰게 한다. alt를 아예 생략하면 스크린 리더가 파일명("IMG_2024.png")을 그대로 읽어버리는 경우가 있어 더 나쁘다.

폼 라벨 연결

<label>과 입력 요소는 반드시 연결돼야 한다. htmlFor(React) / for(HTML) 속성이 입력의 id와 일치해야 스크린 리더가 "이 입력창의 이름은 ○○이다"라고 읽는다. placeholder는 라벨을 대신할 수 없다 — 입력을 시작하면 사라지기 때문이다.

올바른 폼 라벨 연결
// 나쁨 — placeholder는 라벨이 아니다
<input placeholder="이메일" />

// 좋음 — label과 input이 id/htmlFor로 연결됨
<label htmlFor="email">이메일</label>
<input id="email" type="email" />

오류 안내

폼 검증 오류는 색상만으로 표시하면 안 된다(색맹 사용자는 구분 불가). 오류 텍스트를 명시하고, aria-invalid="true"와 aria-describedby로 입력 요소와 오류 메시지를 연결해야 스크린 리더가 "이메일 입력, 유효하지 않음, 올바른 이메일 형식이 아닙니다"처럼 함께 읽는다.

포커스 관리 (모달)

모달을 열면 포커스가 모달 안으로 이동해야 하고, 모달 안에서는 Tab이 모달 바깥으로 새어나가지 않아야 하며(포커스 트랩), 닫으면 원래 포커스가 있던 요소로 되돌아가야 한다. §10에서 이를 직접 구현한다.

애니메이션 축소

전정 장애(vestibular disorder)가 있는 사용자는 큰 움직임 애니메이션에 어지러움·메스꺼움을 느낄 수 있다. CSS 미디어 쿼리 prefers-reduced-motion으로 운영체제 설정을 감지해 애니메이션을 줄이거나 끌 수 있다[18].

reduced-motion.css
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.001ms !important;
  }
}

§10ARIA

ARIA는 W3C의 WAI-ARIA 1.2 명세로 표준화되어 있고[14], MDN은 이를 실무 예제와 함께 정리해둔다[15]. 이 절에서는 그중 실무에서 실제로 자주 쓰는 부분만 다룬다.

첫 번째 규칙: "ARIA를 쓰지 않는 것이 최선"

ARIA 명세 스스로 "No ARIA is better than Bad ARIA"를 첫 번째 규칙으로 명시한다[13]. 이유는 단순하다. <button>은 role="button", 키보드 조작, 포커스를 공짜로 제공하지만, <div role="button">은 role만 흉내 낼 뿐 키보드 동작은 직접 구현해야 하고, 실수하면 "겉보기엔 버튼인데 작동은 이상한" 상태가 된다. ARIA는 네이티브 HTML로 표현이 안 될 때만 쓰는 보충 수단이다.

ARIA 속성은 세 종류로 나뉜다.

종류예시의미
rolerole="dialog"이 요소가 "무엇"인지 알려준다
statearia-expanded="false"지금 "어떤 상태"인지 알려준다(변할 수 있음)
propertyaria-label="닫기"요소의 "고정적인 특성"을 알려준다

aria-label vs aria-labelledby

둘 다 접근 가능한 이름을 지정하지만 출처가 다르다. aria-label="닫기"는 문자열을 직접 지정한다(화면에 안 보이는 텍스트). aria-labelledby="title-id"는 이미 화면에 있는 다른 요소의 텍스트를 이름으로 재사용한다. 이미 화면에 제목이 있다면 aria-labelledby가 중복 유지보수를 줄여준다.

aria-live 영역

aria-live는 사용자가 포커스를 옮기지 않아도, 특정 영역의 내용이 바뀌면 스크린 리더가 자동으로 읽게 만든다. polite는 사용자가 하던 작업을 끝낸 뒤 읽고, assertive는 즉시 끼어들어 읽는다. 토스트 알림, 저장 완료 메시지에 흔히 쓰인다.

접근성 있는 모달 완성하기

모달은 접근성 요구사항이 가장 많이 몰리는 컴포넌트다. 아래 구현은 WAI-ARIA APG의 Dialog 패턴을 따른다[13].

  • role="dialog" + aria-modal="true" — 스크린 리더에게 "이건 대화상자이고, 열려있는 동안 배경은 접근할 수 없다"고 알린다.
  • aria-labelledby — 모달 제목 요소의 id를 참조해 이름을 준다.
  • 포커스 이동 — 열릴 때 트리거 버튼을 기억해두고, 모달 첫 포커스 대상으로 이동시킨다.
  • 포커스 트랩 — 모달 안의 첫/마지막 포커스 가능 요소에서 Tab/Shift+Tab이 서로에게 순환하도록 한다.
  • Esc로 닫기 — keydown에서 Escape를 감지해 닫는다.
  • 포커스 복귀 — 닫히면 저장해둔 트리거 버튼으로 포커스를 되돌린다.
  • aria-live 토스트 — 저장 성공 시 aria-live="polite" 영역에 메시지를 넣어 스크린 리더가 자동으로 읽게 한다.

무슨 일이 일어나는가

"설정 열기" 버튼을 누르면 모달이 뜨고 포커스가 그 안으로 이동한다. Tab은 모달 안에서만 순환하고, Esc로 닫으면 원래 버튼으로 포커스가 돌아간다.

  • lastFocused — 모달을 열기 직전의 document.activeElement를 저장.
  • trapFocus — keydown에서 Tab을 가로채, 첫/마지막 요소를 서로 연결.
  • closeModal — Esc, 오버레이 클릭, 취소 버튼 모두 같은 함수를 호출.
핵심 sandbox="allow-scripts"만 걸린 미리보기 iframe에서도 위 코드는 실제 브라우저의 Tab/Shift+Tab/Escape 키 이벤트로 동작한다. 실제 서비스 코드에서는 매번 이 로직을 새로 짜는 대신 검증된 라이브러리(Radix UI, react-aria 등)를 쓰는 것이 안전하다.

탭과 아코디언

탭과 아코디언도 각각 APG 패턴이 정해져 있다. 탭은 role="tablist" 안에 role="tab"들이 있고, 선택된 탭에 aria-selected="true", 연결된 패널은 role="tabpanel" + aria-labelledby로 탭과 연결된다. 아코디언은 각 헤더가 aria-expanded로 펼침 상태를, aria-controls로 연결된 패널을 알린다. 아래 예제에서 두 패턴을 함께 구현한다.

§11검증 도구

Lighthouse

Chrome DevTools의 Lighthouse 탭 → Accessibility 카테고리를 실행하면 색 대비, 대체 텍스트 누락, 폼 라벨 누락 등을 자동으로 점검하고 점수를 매긴다. 빠른 1차 점검 도구로 유용하지만, 자동 검사는 전체 WCAG 기준의 일부만 잡아낸다.

axe DevTools

브라우저 확장 프로그램으로, 현재 페이지를 스캔해 위반 항목과 관련 WCAG 기준, 수정 방법을 함께 보여준다. Lighthouse보다 세밀한 리포트를 제공한다.

NVDA / VoiceOver

자동화 도구는 "코드가 규칙을 지켰는가"만 검사하고 "실제로 잘 들리는가"는 검사하지 못한다. Tab으로 페이지를 순회하며 실제 음성 안내를 들어보는 것이 가장 확실한 검증이다. NVDA는 Windows용 무료 오픈소스, VoiceOver는 macOS/iOS 기본 내장이다.

eslint-plugin-jsx-a11y

JSX 코드를 작성하는 시점에 alt 누락, 라벨 없는 입력, 클릭 핸들러만 있고 키보드 핸들러가 없는 요소 등을 ESLint 규칙으로 잡아낸다. 배포 전이 아니라 코드 작성 중에 바로 피드백을 준다는 점에서 가장 먼저 걸리는 방어선이다.

검증 순서 권장 코드 작성 중(eslint-plugin-jsx-a11y) → 1차 자동 점검(Lighthouse, axe) → 실제 스크린 리더로 핵심 플로우 확인(NVDA/VoiceOver) → 가능하면 실제 사용자 테스트. 자동 도구만으로는 WCAG 위반의 약 30~40%만 잡아낼 수 있다는 것이 업계에서 반복적으로 보고되는 한계다.

§12이해도 점검 체크리스트

  • div만으로 만든 레이아웃과 시맨틱 태그로 만든 레이아웃이 접근성 트리에서 왜 다르게 보이는지 설명할 수 있다.
  • 요청부터 화면 표시까지 DOM/CSSOM/렌더 트리/레이아웃/페인트 순서를 그릴 수 있다.
  • 일반 script, defer, async가 HTML 파싱과 실행 시점에서 어떻게 다른지 설명할 수 있다.
  • CSR/SSR/SSG/ISR/스트리밍 SSR을 TTFB·FCP·SEO·서버비용 기준으로 비교할 수 있다.
  • 내 페이지가 어떤 렌더링 전략을 써야 하는지 결정 트리로 판단할 수 있다.
  • 하이드레이션이 무엇이고, 미스매치가 나는 4가지 대표 원인을 말할 수 있다.
  • 서버 컴포넌트와 'use client' 클라이언트 컴포넌트의 번들 포함 여부 차이를 설명할 수 있다.
  • Suspense의 fallback이 언제 나타나고 언제 사라지는지 직접 구현해봤다.
  • pushState/popstate만으로 최소 라우터를 직접 구현할 수 있다.
  • 스킵 링크, Tab 순서, focus-visible의 필요성을 설명할 수 있다.
  • WCAG POUR 4원칙과 A/AA/AAA 레벨의 차이를 설명할 수 있다.
  • 4.5:1 대비율 공식을 알고, 두 색의 대비율을 직접 계산할 수 있다.
  • "ARIA를 쓰지 않는 것이 최선"이라는 첫 번째 규칙이 뜻하는 바를 설명할 수 있다.
  • 포커스 트랩 + Esc + aria-modal을 갖춘 접근성 있는 모달을 직접 구현할 수 있다.
  • Lighthouse/axe/스크린 리더/eslint-plugin-jsx-a11y가 각각 어떤 역할을 하는지 구분할 수 있다.
