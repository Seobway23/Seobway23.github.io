CHAPTER 08

성능 최적화 & 자료구조

측정 없이 최적화하지 않는다. Core Web Vitals로 무엇이 느린지 재는 법부터, 목록 UI(페이지네이션·무한 스크롤·가상 스크롤)를 실제로 빠르게 만드는 법, React 리렌더링을 줄이는 실전 판단 기준, 그리고 Array.includes를 Set.has로 바꾸는 것만으로 왜 100배 빨라지는지까지 — 자료구조와 복잡도를 코드로 체감한다.

§1성능을 측정하는 법

측정 없는 최적화 금지 "느려 보인다"는 느낌으로 코드를 고치면 대부분 실제 사용자 경험과 무관한 곳을 건드리게 된다. 항상 먼저 측정 → 병목 특정 → 수정 → 재측정 순서를 지킨다. 수정 전후 숫자가 없으면 그건 최적화가 아니라 추측이다.

브라우저는 사용자가 느끼는 속도를 Core Web Vitals라는 3가지 지표로 표준화했다[1]. "빠르다/느리다"를 사람마다 다르게 말하지 않도록, 아래 3가지 숫자로만 이야기한다.

측정 도구 3종

Lighthouse

Lighthouse는 실험실(Lab) 환경에서 페이지를 한 번 로드해보고 점수를 매긴다[2]. Chrome DevTools의 Lighthouse 탭 → "분석" 클릭 한 번으로 실행된다. CI에 넣어 배포마다 자동 체크하기 좋다.

DevTools Performance 패널

실제 상호작용을 녹화해서 어느 함수가 몇 ms 걸렸는지 화염 그래프(Flame Chart)로 보여준다. "느리다"의 원인이 JS 실행인지, 레이아웃 계산인지, 페인트인지를 프레임 단위로 구분할 수 있다.

React DevTools Profiler

React 전용 확장 프로그램의 Profiler 탭. "어떤 컴포넌트가 몇 번, 왜(무슨 props/state 때문에) 다시 렌더링됐는지"를 컴포넌트 단위로 보여준다[6]. §7에서 이 도구로 렌더 원인을 진단한다.

랩(Lab) vs 필드(Field) 데이터 Lighthouse는 개발자 PC에서 재는 랩 데이터다. 실제 사용자의 다양한 기기·네트워크에서 수집되는 값은 필드 데이터라 하고, Chrome 사용자 통계를 모은 CrUX가 대표적 출처다[1]. 랩 점수가 좋아도 필드 지표가 나쁠 수 있다 — 실제 사용자 환경(저사양 기기, 3G)이 더 가혹하기 때문이다.

이 챕터의 모든 예제는 performance.now()로 실제 시간을 재서 화면에 숫자로 찍는다. "빨라진 것 같다"가 아니라 "3.2ms → 0.04ms로 줄었다"를 눈으로 확인하는 방식을 따라간다.

§2브라우저 렌더링 파이프라인

어떤 CSS 속성을 바꾸느냐에 따라 브라우저가 해야 하는 일의 양이 완전히 달라진다. 이 차이를 이해하지 못하면 "왜 transform은 부드러운데 top은 끊기는가"를 설명할 수 없다. 브라우저가 화면 한 장을 그리는 과정은 4단계다[3]. 

flowchart LR
  A["DOM + CSSOM 변경\n(state 업데이트, class 토글 등)"] --> B["Style\n어떤 요소에 어떤 CSS가\n적용되는지 계산"]
  B --> C["Layout (Reflow)\n각 요소의 위치·크기를\n다시 계산"]
  C --> D["Paint (Repaint)\n픽셀 색상을 레이어에\n실제로 칠함"]
  D --> E["Composite\n레이어들을 합성해\n최종 화면 출력"]
  B -.->|"transform / opacity만 바뀌면\nLayout과 Paint를 건너뛴다"| E
그림 1. 브라우저 렌더링 파이프라인. Style → Layout → Paint → Composite 순서로 진행되며, 뒤 단계로 갈수록 비용이 크다. 출처: web.dev — Rendering Performance

핵심은 어떤 속성을 바꾸느냐에 따라 시작 지점이 달라진다는 것이다. width를 바꾸면 Layout부터 다시 해야 하고, color만 바꾸면 Paint부터, transform만 바꾸면 Composite만 다시 하면 된다. 뒤 단계로 갈수록 GPU가 처리하고 앞 단계로 갈수록 CPU가 전체 트리를 다시 계산해야 해서 느리다.

바꾸는 속성 예시다시 해야 하는 단계비용
width, height, top/left, margin, padding, font-size, DOM 추가/삭제Layout → Paint → Composite 전부비쌈
color, background, box-shadow, visibilityPaint → Composite중간
transform, opacityComposite만저렴

transform과 opacity만 예외인 이유는, 이 둘은 합성(Composite) 레이어에서 이동·투명도 조절만으로 결과를 낼 수 있기 때문이다. 반면 top으로 위치를 옮기면 문서 전체의 배치(Layout)가 바뀔 수 있어 다시 계산해야 한다. framer-motion 같은 애니메이션 라이브러리가 기본적으로 transform을 쓰는 것도 이 때문이다.

리플로우(Reflow)와 리페인트(Repaint) 리플로우는 Layout을 다시 계산하는 것, 리페인트는 Paint를 다시 그리는 것이다. 리플로우는 항상 리페인트를 동반하지만, 리페인트가 항상 리플로우를 동반하진 않는다.

§3목록 UI 1 — 페이지네이션

서버에 데이터가 수만 건 있을 때 한 번에 다 내려받을 수 없다. 페이지네이션은 이 문제를 푸는 가장 오래된 방법이다. 서버 쪽 구현 방식은 크게 두 가지다. 

flowchart LR
  subgraph OFFSET["OFFSET 방식"]
    direction TB
    O1["SELECT * FROM posts\nORDER BY id\nLIMIT 20 OFFSET 10000"] --> O2["DB가 10,020행을 순서대로\n스캔한 뒤 앞 10,000행을 버림"]
    O2 --> O3["페이지 번호가 커질수록\n점점 느려진다"]
  end
  subgraph CURSOR["CURSOR 방식"]
    direction TB
    C1["SELECT * FROM posts\nWHERE id < :lastId\nORDER BY id DESC LIMIT 20"] --> C2["인덱스로 :lastId 위치를\n바로 탐색 (스캔 없음)"]
    C2 --> C3["페이지 위치와 무관하게\n항상 일정한 속도"]
  end
그림 2. offset 방식은 건너뛸 행까지 매번 스캔하지만, cursor 방식은 인덱스로 바로 위치를 찾는다.

offset vs cursor — SQL과 응답 구조

offset 방식

"몇 번째 페이지인가"를 그대로 쿼리에 쓴다. 페이지 번호 UI(1, 2, 3 …)를 만들기 쉽지만, 뒤 페이지로 갈수록 DB가 앞부분을 스캔하고 버리는 비용이 계속 커진다. 이를 딥 페이지네이션(deep pagination) 문제라 부른다.

cursor 방식

"마지막으로 본 항목의 id"를 기준점(cursor)으로 전달한다. 인덱스가 있으면 그 위치로 바로 점프하므로 몇 페이지든 속도가 일정하다. 대신 "17페이지로 바로 가기" 같은 UI는 만들기 어렵다.

offset 응답 예시
{
  "data": [ { "id": 10001, "title": "..." }, ... ],
  "page": 501,
  "pageSize": 20,
  "totalCount": 48213
}
cursor 응답 예시
{
  "data": [ { "id": 10001, "title": "..." }, ... ],
  "nextCursor": "10021",
  "hasMore": true
}
언제 뭘 쓰나 페이지 번호 UI(관리자 목록, 게시판)가 필요하면 offset — 대신 페이지 수를 제한하거나 totalCount를 근사치로 캐싱한다. 무한 스크롤·피드처럼 "다음 것만 계속" 필요하면 cursor가 정답이다. §4에서 다루는 무한 스크롤은 거의 항상 cursor 기반이다.

페이지 번호 UI 알고리즘 — "1 … 4 5 6 … 20"

페이지가 20개면 번호를 다 보여줘도 되지만, 200개면 "1 2 3 4 5 6 7 8 ... 200"은 UI가 깨진다. 현재 페이지 주변만 보여주고 나머지는 "…"으로 생략하는 알고리즘이 필요하다.

무슨 일이 일어나는가

오른쪽 코드의 getPageNumbers가 핵심이다. 현재 페이지(current) 좌우로 delta(=1)만큼만 번호를 채우고, 첫 페이지·마지막 페이지는 항상 고정으로 넣는다. 그 사이 간격이 벌어지면 "..."를 끼워 넣는다.

  • Math.max(2, current - delta) — 1페이지는 이미 따로 넣으므로 2부터 시작
  • Math.min(totalPages - 1, current + delta) — 마지막 페이지도 따로 넣으므로 그 앞까지만
  • 왼쪽/오른쪽에 틈이 2 이상 벌어질 때만 "..."를 넣는다 (틈이 1이면 숫자를 그냥 보여주는 게 더 자연스럽다)
  • nav + aria-current="page"로 스크린 리더가 "현재 페이지"를 알 수 있게 한다
흔한 실수 totalCount를 매 요청마다 COUNT(*)로 다시 세면 그 자체가 풀 스캔이라 느리다. 실시간 정확도가 필요 없다면 카운트를 캐싱하거나 "약 48,000건" 처럼 근사치로 보여준다.

§4목록 UI 2 — 무한 스크롤

피드형 UI(SNS, 쇼핑몰 상품 목록)는 페이지 번호보다 "스크롤하면 계속 나온다"는 경험이 자연스럽다. 이를 구현하는 표준 방법이 IntersectionObserver다[4]. 목록 맨 아래에 보이지 않는 "감시용 요소(sentinel)"를 두고, 그 요소가 화면에 들어오는 순간 다음 페이지를 요청한다.

무슨 일이 일어나는가

오른쪽은 실제 DOM으로 동작하는 예제다. 목록 아래 #sentinel이 스크롤 컨테이너(root) 안에 들어오면 loadMore()가 호출되어 10개씩 추가된다.

  • root: listEl — 브라우저 전체가 아니라 이 스크롤 박스 기준으로 교차를 판정
  • threshold: 0.1 — sentinel이 10%만 보여도 콜백 실행
  • 콜백 안에서 loaded < 100으로 멈춤 조건을 둬서 무한 로딩을 방지

무한 스크롤의 대가

스크롤 위치 복원 문제

상세 페이지를 봤다가 뒤로 가기를 누르면 목록을 처음부터 다시 불러오면서 스크롤이 맨 위로 튄다. 방금 보던 위치로 되돌리려면 이미 불러온 페이지 데이터와 스크롤 위치를 함께 캐싱해야 한다(예: TanStack Query의 쿼리 캐시 + history.state에 scrollY 저장).

접근성 / SEO 단점

스크린 리더 사용자는 "얼마나 더 있는지" 가늠하기 어렵고, 키보드만으로 끝까지 도달하기 번거롭다. 검색 엔진 크롤러는 스크롤 이벤트를 실행하지 않으므로 나중에 로드되는 콘텐츠를 아예 못 볼 수 있다(footer의 "문의하기" 링크가 영원히 안 나타나는 문제도 흔하다).

실전 선택 기준 탐색·발견이 목적인 피드(SNS, 쇼핑)는 무한 스크롤이 자연스럽다. 목적지가 명확한 목록(주문 내역, 관리자 화면)은 "더 보기" 버튼이나 §3의 페이지네이션이 더 적합하다.

§5목록 UI 3 — 가상 스크롤(windowing)

10,000개 행을 전부 DOM 노드로 만들면 브라우저는 스크롤할 때마다 10,000개의 레이아웃·페인트를 관리해야 한다. 가상 스크롤(virtual scroll / windowing)은 "화면에 실제로 보이는 20개만" DOM으로 만들고 나머지는 여백으로 흉내 낸다[5].

그림 3. 10,000개 중 뷰포트에 보이는 부분만 실제 DOM으로 렌더링하고, 위아래는 빈 여백(padding)으로 스크롤 길이만 흉내 낸다.

고정 높이 가상 리스트 직접 구현

무슨 일이 일어나는가

행 높이(ROW_H)가 고정이라는 걸 이용해 스크롤 위치만으로 "몇 번째 행부터 보여야 하는가"를 계산한다. 나눗셈 한 번이면 끝난다.

  • startIndex = floor(scrollTop / ROW_H) — 스크롤한 픽셀을 행 높이로 나누면 시작 인덱스
  • visibleCount — 컨테이너 높이만큼만 필요한 행 개수 (+ overscan 여유분)
  • topPad — 보이지 않는 위쪽 행들의 높이 합을 paddingTop으로 채워 스크롤바를 속인다
  • 체크박스를 꺼서 가상화를 끄면 10,000개 <div>가 전부 렌더링된다 — 스크롤이 눈에 띄게 버벅이는지 직접 비교해본다

가변 높이는 왜 어려운가

위 계산은 모든 행이 같은 높이라서 성립한다. 행마다 텍스트 줄 수가 다르거나 이미지가 섞이면 "몇 번째 행이 몇 px 위치인가"를 미리 알 수 없다. 실무에서는 각 행을 한 번 렌더링해서 실제 높이를 측정(getBoundingClientRect)하고 캐싱한 뒤, 그 측정값 배열로 위치를 역산하는 방식을 쓴다. 이 복잡도를 직접 구현하는 대신 TanStack Virtual 같은 라이브러리를 쓰는 것이 현실적이다[7].

TanStack Virtual 사용 예 (실제 라이브러리 API)
import { useVirtualizer } from "@tanstack/react-virtual";

function Rows({ items }: { items: string[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const rowVirtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 32, // 가변 높이는 예상치 → 실측 후 자동 보정
    overscan: 6,
  });

  return (
    <div ref={parentRef} style={{ height: 400, overflow: "auto" }}>
      <div style={{ height: rowVirtualizer.getTotalSize() }}>
        {rowVirtualizer.getVirtualItems().map((row) => (
          <div key={row.key} style={{ transform: `translateY(${row.start}px)` }}>
            {items[row.index]}
          </div>
        ))}
      </div>
    </div>
  );
}

§6입력 최적화

검색창에 타이핑할 때마다 API를 호출하면 "react" 6글자에 6번 요청이 나간다. 디바운스(debounce)와 스로틀(throttle)은 이 호출 횟수를 줄이는 두 가지 다른 전략이다.

그림 4. 디바운스는 입력이 멈춘 뒤 한 번만, 스로틀은 입력 중에도 일정 간격으로 실행된다. 회색 점 = 실제 이벤트, 파란 사각형 = 함수 실행 시점.
디바운스 — "멈추면 실행"

검색 자동완성, 폼 유효성 검사, 창 크기 조절(resize) 후 레이아웃 재계산처럼 최종 값만 중요한 경우에 쓴다.

스로틀 — "꾸준히, 너무 자주는 말고"

스크롤 위치 추적, 무한 스크롤 감시, 마우스 드래그처럼 중간 과정도 계속 반영돼야 하는 경우에 쓴다.

직접 구현 + 호출 횟수 라이브 비교

무슨 일이 일어나는가

같은 입력 이벤트에 raw(순수 키 입력), 디바운스, 스로틀 세 카운터를 동시에 붙였다. 빠르게 타이핑해보면 raw만 폭발적으로 늘고 나머지 둘은 억제되는 걸 숫자로 확인할 수 있다.

  • timer.current에 setTimeout id를 저장, 새 입력이 오면 clearTimeout으로 취소하고 다시 예약 → 디바운스
  • last.current에 마지막 실행 시각을 저장, delay 이상 지났을 때만 실행 → 스로틀

requestAnimationFrame과 passive 리스너

스크롤·리사이즈 이벤트는 1초에 수십~수백 번 발생할 수 있다. 이걸 매번 처리하는 대신 requestAnimationFrame으로 감싸면 브라우저가 다음 프레임을 그릴 때 딱 한 번만 실행되도록 자연스럽게 제한된다.

rAF로 스크롤 이벤트 제한
let ticking = false;

window.addEventListener(
  "scroll",
  () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      updateScrollIndicator(); // 실제 작업은 프레임당 1회만
      ticking = false;
    });
  },
  { passive: true } // 아래 참고
);

이벤트 리스너의 { passive: true } 옵션은 "이 리스너 안에서 preventDefault()를 호출하지 않겠다"고 브라우저에 미리 알려주는 것이다[10]. 그러면 브라우저는 리스너 실행 결과를 기다리지 않고 즉시 스크롤을 진행할 수 있어 스크롤 지연(jank)이 줄어든다. scroll, touchstart, touchmove처럼 자주 발생하는 이벤트에는 기본으로 붙이는 게 좋다.

§7React 렌더링 최적화 실전

React는 state가 바뀐 컴포넌트와 그 아래 모든 자식을 기본적으로 다시 렌더링한다[6]. 대부분의 "느린 React 앱"은 이 기본 동작 때문이 아니라, 정말 필요 없는 리렌더링을 그대로 방치해서 생긴다. 아래는 실무에서 통하는 순서대로의 대응책이다.

1. 상태를 아래로 내리기 (state colocation)

가장 먼저 시도할 것은 memo가 아니라 state 위치 자체를 바꾸는 것이다. state를 실제로 그 값을 쓰는 컴포넌트에 최대한 가깝게 두면, 그 state가 바뀌어도 위쪽 형제 컴포넌트들은 애초에 다시 렌더링될 이유가 없다.

Before — 상위에 state가 있어 전체가 리렌더
function Page() {
  const [query, setQuery] = useState(""); // 검색창 값이 Page에 있음
  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ExpensiveChart />  {/* query와 무관한데 매 타이핑마다 리렌더됨 */}
    </div>
  );
}
After — state를 SearchBox 내부로 내림
function Page() {
  return (
    <div>
      <SearchBox />       {/* 이 안에서만 리렌더 발생 */}
      <ExpensiveChart />  {/* 이제 절대 영향받지 않음 */}
    </div>
  );
}
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

2. children으로 렌더 차단

컴포넌트를 분리할 수 없는 구조라도, children prop으로 넘겨받은 요소는 부모가 리렌더돼도 다시 계산되지 않는다. 이미 만들어진 React 엘리먼트 트리를 그대로 재사용하기 때문이다.

children으로 감싸서 리렌더 전파 차단
function Page() {
  const [query, setQuery] = useState("");
  return (
    <Layout>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ExpensiveChart />
    </Layout>
  );
}
function Layout({ children }) {
  // Page가 리렌더돼도 children은 이미 만들어진 엘리먼트라 재계산되지 않는다
  return <div className="layout">{children}</div>;
}

그림 5. memo류 최적화는 마지막 수단이다. 측정 → state 위치 재검토 → 그래도 필요할 때만 memo/useMemo/useCallback을 적용한다. 출처: react.dev — Referencing Values with Refs / re-render 가이드
memo는 공짜가 아니다 React.memo는 매 렌더마다 이전 props와 새 props를 얕은 비교(shallow compare)한다[12]. props로 매번 새로 생성되는 객체·배열·함수를 넘기면 비교 자체가 항상 "다름"으로 나와 memo가 무력화된다 — 그래서 useMemo/useCallback과 짝을 이룬다.

4. key로 강제 리마운트

컴포넌트를 "업데이트"하는 대신 "완전히 새로 만들고" 싶을 때가 있다(예: 폼을 초기화하고 싶을 때). key를 바꾸면 React는 기존 컴포넌트를 버리고 언마운트 → 재마운트한다[6].

key로 폼 강제 초기화
// userId가 바뀔 때마다 key도 바뀌어 ProfileForm이 완전히 새로 생성된다
// → 내부 useState가 전부 초기값으로 리셋됨 (수동 리셋 로직 불필요)
<ProfileForm key={userId} userId={userId} />

Before / After 렌더 카운터 라이브 비교

무슨 일이 일어나는가

부모의 "관련 없는 상태"를 바꿔서 두 자식이 어떻게 다르게 반응하는지 카운터로 확인한다.

  • useRenderCount — useRef는 렌더링을 유발하지 않으면서 렌더 횟수만 누적한다
  • 일반 자식은 memo가 없어 부모가 리렌더될 때마다 함께 리렌더된다
  • memo 자식은 props(label)가 바뀌지 않는 한 렌더 카운터가 멈춰 있다
요약 순서: ① state 위치를 아래로 내린다 → ② 컴포넌트를 쪼개거나 children으로 감싼다 → ③ 그래도 측정상 느리면 memo/useMemo/useCallback을 붙인다. 처음부터 모든 컴포넌트에 memo를 붙이는 것은 오히려 비교 비용만 늘리는 역효과다.

§8자료구조 & 복잡도

같은 결과를 내는 코드라도 데이터가 100개일 때와 10만 개일 때 걸리는 시간이 전혀 다르게 늘어날 수 있다. 이 "늘어나는 정도"를 표현하는 표기법이 Big-O 표기법이다.

Big-O 개요

표기이름데이터 10배 늘면프론트에서 체감되는 지점
O(1)상수 시간변화 없음Map.get, Set.has, 배열 인덱스 접근 arr[i]
O(log n)로그 시간거의 안 늘어남정렬된 배열 이진 탐색, 균형 트리 탐색
O(n)선형 시간10배Array.includes, .find, .filter, .map 한 번 순회
O(n log n)선형로그 시간10배보다 약간 더Array.prototype.sort (대부분의 정렬 알고리즘)
O(n²)제곱 시간100배배열 안에서 .map마다 .find/.includes 호출(중첩 루프), N+1 문제

프론트엔드에서 체감 성능 문제의 상당수는 화려한 알고리즘이 아니라 목록 안에서 목록을 또 뒤지는 중첩 루프에서 나온다. 아래에서 이 패턴을 실제로 측정해본다.

Array vs Object vs Map vs Set

순서키 타입조회주 용도
Array보장됨(인덱스)정수 인덱스인덱스 접근 O(1), 값 검색 O(n)순서 있는 목록, 순회
Object정수 키는 정렬됨, 문자열 키는 삽입 순서[8]문자열/Symbol만obj[key] 평균 O(1)고정된 필드를 가진 레코드(JSON과 1:1)
Map삽입 순서 보장모든 타입 가능(객체도 키로 사용 가능)Map.get 평균 O(1)동적으로 키가 추가/삭제되는 사전, LRU 캐시(§8 후반)
Set삽입 순서 보장값 자체가 키(중복 불가)Set.has 평균 O(1)중복 제거, "포함 여부"를 빠르게 확인
왜 Map.get / Set.has는 O(1)인가 내부적으로 해시 테이블로 구현되어 있어, 배열처럼 앞에서부터 하나씩 비교하지 않고 값의 위치를 계산으로 바로 찾아간다. 데이터가 100개든 10만 개든 조회 비용이 거의 같다.

라이브 측정 — Array.includes(O(n)) vs Set.has(O(1))

무슨 일이 일어나는가

10만 개짜리 배열에서 2,000개의 값이 "포함되는지" 확인하는 작업을 두 방식으로 반복한다. .includes는 매번 배열을 처음부터 훑고(O(n)), 이를 2,000번 반복하므로 전체는 O(n·m)이 된다. Set은 한 번만 만들어두면(O(n)) 이후 조회는 각각 O(1)이라 전체가 O(n+m)으로 끝난다.

  • performance.now()로 시작/끝 시각을 재서 밀리초(ms) 단위로 출력
  • 실행마다 값이 조금씩 다를 수 있지만, 자릿수 차이 자체는 항상 재현된다
  • ▶ 실행을 눌러 콘솔 출력을 직접 확인해본다
흔한 실수 — 중첩 루프로 N+1 문제 만들기 orders.map(o => users.find(u => u.id === o.userId))는 주문마다 사용자 배열 전체를 다시 훑는다. 주문 1,000건 × 사용자 1,000명이면 최악의 경우 100만 번 비교한다.

인덱싱 — 배열을 Map으로 바꿔 N+1 제거

Before — O(n·m) 중첩 루프
// orders: 1,000건, users: 1,000명이면 최악 100만 번 비교
const result = orders.map((o) => ({
  ...o,
  userName: users.find((u) => u.id === o.userId)?.name,
}));
After — 먼저 Map으로 인덱싱, O(n+m)
// 1) users를 id → user로 미리 색인 O(m)
const userById = new Map(users.map((u) => [u.id, u]));

// 2) 이후 조회는 각각 O(1) → 전체 O(n+m)
const result = orders.map((o) => ({
  ...o,
  userName: userById.get(o.userId)?.name,
}));

정렬 시 comparator 주의

Array.prototype.sort()는 기본적으로 문자열로 변환해서 비교한다. 숫자 배열을 그냥 정렬하면 [10, 2, 1]이 [1, 10, 2]가 되는 사고가 난다[8]. 항상 비교 함수를 명시한다.

comparator 없이 정렬 — 문자열 비교로 오작동
[10, 2, 1].sort();
// [1, 10, 2]  ← "10"이 "2"보다 사전순으로 앞이라 이렇게 됨

[10, 2, 1].sort((a, b) => a - b);
// [1, 2, 10]  ← 올바른 숫자 비교

LRU 캐시 직접 구현 — Map의 삽입 순서를 이용

LRU(Least Recently Used) 캐시는 용량이 차면 가장 오래 안 쓰인 항목을 버린다. Map이 삽입 순서를 보장한다는 성질[11]을 이용하면 별도의 연결 리스트 없이 구현할 수 있다 — 항목을 쓸 때마다 지웠다가 다시 넣으면 자동으로 "가장 최근" 위치(맨 뒤)로 옮겨진다.

큐/스택으로 트리 순회 — DOM 트리 BFS vs DFS

BFS(너비 우선)는 큐(FIFO)로, DFS(깊이 우선)는 스택(LIFO)으로 구현한다. 차이는 딱 한 줄 — shift()(앞에서 꺼냄)냐 pop()(뒤에서 꺼냄)이냐다.

무슨 일이 일어나는가

같은 트리를 두 함수로 순회한다. 실행 버튼으로 순서를 콘솔에서 비교한다.

  • queue.shift() — 큐의 맨 앞을 꺼냄 → 형제 노드를 먼저 다 보고 다음 층으로(BFS)
  • stack.pop() — 스택의 맨 뒤를 꺼냄 → 한쪽 가지를 끝까지 파고듦(DFS)
  • node.children은 element 자식만 담긴 HTMLCollection이라 텍스트 노드는 자동으로 제외된다

트라이(Trie)로 자동완성 구현

트라이(Trie)는 문자열을 한 글자씩 트리의 경로로 저장한다. "re"로 시작하는 단어를 찾을 때, 배열이면 전체를 순회(O(n))해야 하지만 트라이는 "r" → "e" 경로만 따라가면 후보를 바로 좁힐 수 있다.

§9네트워크 · 자산 최적화

지금까지는 "이미 받은 데이터를 화면에 어떻게 효율적으로 그리는가"였다면, 이 절은 "애초에 얼마나 적게, 얼마나 빨리 받아오는가"를 다룬다.

코드 스플리팅 — React.lazy + Suspense

번들 전체를 한 파일로 만들면 사용자가 첫 화면에 필요 없는 코드(관리자 페이지, 모달, 차트 라이브러리)까지 미리 다운로드하게 된다. 코드 스플리팅은 이 번들을 쪼개서 필요한 순간에만 내려받게 한다[9].

src/App.tsx
import { lazy, Suspense } from "react";

// 이 import()는 별도 청크로 분리되어, 실제로 렌더링될 때만 네트워크 요청이 나간다
const AdminDashboard = lazy(() => import("./pages/AdminDashboard"));

function App() {
  return (
    <Suspense fallback={<p>로딩 중...</p>}>
      <AdminDashboard />
    </Suspense>
  );
}

react-router-dom과 조합하면 라우트별로 자동 분리할 수 있다 — 방문하지 않는 페이지의 코드는 아예 다운로드되지 않는다. 청크가 어떻게 만들어지는지는 빌드 도구 챕터에서 다룬 ESM 정적 분석이 기반이 된다.

이미지 최적화

포맷 / 반응형(srcset)

WebP/AVIF를 쓰고, 화면 크기별로 다른 해상도 파일을 제공해 불필요하게 큰 이미지를 모바일에 내려주지 않는다.

<img
  src="photo-800.webp"
  srcset="photo-400.webp 400w, photo-800.webp 800w, photo-1600.webp 1600w"
  sizes="(max-width: 600px) 100vw, 800px"
  alt="설명"
/>
lazy loading / aspect-ratio

화면 밖 이미지는 loading="lazy"로 지연 로드하고, width/height나 aspect-ratio로 이미지가 로드되기 전에도 자리를 미리 차지하게 해 CLS를 방지한다.

<img
  src="thumb.webp"
  loading="lazy"
  width="320" height="180"
  style="aspect-ratio: 16/9"
  alt="설명"
/>
CLS의 가장 흔한 원인 width/height 없이 이미지를 넣으면, 이미지가 로드되기 전엔 브라우저가 높이를 0으로 예약했다가 로드 후 갑자기 늘어나며 아래 콘텐츠를 밀어낸다. 이게 CLS 점수를 가장 크게 깎아먹는 원인이다[1].

폰트 최적화

웹 폰트가 로드되기 전 텍스트를 어떻게 보여줄지는 font-display로 제어한다. swap은 시스템 폰트로 먼저 보여주다가 웹 폰트가 로드되면 교체한다 — 텍스트가 안 보이는 시간(FOIT)을 없애 LCP에 유리하다.

font-display + 서브셋
@font-face {
  font-family: "Pretendard Variable";
  src: url("/fonts/PretendardVariable-subset.woff2") format("woff2");
  font-display: swap; /* 로딩 중엔 대체 폰트, 로드되면 교체 */
  font-weight: 45 920;
}

전체 유니코드 글립스 대신 실제 쓰는 문자(한글+영문+숫자)만 남긴 서브셋(subset) 폰트를 쓰면 파일 크기를 크게 줄일 수 있다.

gzip vs brotlibrotli가 동일 조건에서 더 높은 압축률을 낸다. 대부분의 최신 CDN/서버가 기본 지원

§10메모리 누수

메모리 누수(memory leak)는 대부분 "누군가 계속 참조를 붙잡고 있어서" 생긴다[13]. SPA는 페이지를 새로고침하지 않고 계속 컴포넌트를 마운트/언마운트하기 때문에, 서버 렌더링 위주의 전통적인 웹사이트보다 누수가 누적되기 쉽다.

1. 이벤트 리스너 미해제
useEffect(() => {
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize); // 필수
}, []);

return 정리 함수를 빼먹으면 컴포넌트가 언마운트된 뒤에도 리스너가 살아남아 매번 새로 추가되며 쌓인다.

2. 타이머 미해제
useEffect(() => {
  const id = setInterval(poll, 3000);
  return () => clearInterval(id); // 필수
}, []);

setInterval/setTimeout을 정리하지 않으면 언마운트된 컴포넌트의 state를 계속 업데이트하려 시도하며 콘솔 경고와 함께 메모리를 붙잡는다.

3. 클로저 참조
function attachHandler(hugeData) {
  document.body.onclick = () => console.log(hugeData.length);
  // hugeData 전체가 클로저에 붙잡혀 GC 대상에서 제외된다
}

클로저가 큰 객체를 참조한 채로 오래 살아있는 콜백(전역 이벤트 핸들러 등)에 담기면, 그 큰 객체 전체가 회수되지 않는다.

4. 전역 캐시 무한 증가
const cache = {};
function memoize(key, compute) {
  if (!(key in cache)) cache[key] = compute(); // 삭제 로직이 없음
  return cache[key];
}

§8의 LRU 캐시처럼 용량 제한과 삭제 전략이 없는 캐시는 앱이 오래 켜져 있을수록(대시보드, 관리자 SPA) 계속 커지기만 한다.

DevTools Memory로 확인하는 법

  1. Chrome DevTools → Memory 탭 → Heap snapshot 선택
  2. 의심되는 화면을 열고 스냅샷 1회 촬영
  3. 해당 화면을 닫았다가 다시 열기를 여러 번 반복
  4. 스냅샷을 한 번 더 촬영 후 "Comparison" 뷰로 두 스냅샷을 비교 — 반복한 횟수만큼 늘어나 있고 줄어들지 않는 객체가 누수 후보다
빠른 신호 DevTools Performance Monitor(또는 Performance 탭의 메모리 그래프)에서 "JS Heap Size"가 시간이 지날수록 계단식으로 오르기만 하고 가비지 컬렉션 이후에도 기준선이 내려가지 않는다면 누수를 의심한다.

§11최적화 판단 체크리스트 + 이해도 점검

실전 판단 순서

flowchart TD
  S["체감상 느리다는 리포트/불만 발생"] --> T["Lighthouse / DevTools Performance로\n먼저 측정한다"]
  T --> W{"Web Vitals 중\n무엇이 나쁜가?"}
  W -->|"LCP"| L["큰 이미지 preload,\n서버 응답 시간, 코드 스플리팅"]
  W -->|"INP"| I["긴 JS 작업 쪼개기,\n불필요한 리렌더링 축소(§7)"]
  W -->|"CLS"| C["이미지/폰트에 크기 예약,\naspect-ratio 지정"]
  L --> V["재측정 → 목표 수치 도달 확인"]
  I --> V
  C --> V
그림 6. 최적화는 항상 측정에서 시작해 재측정으로 끝난다. 어떤 지표가 나쁜지에 따라 다른 처방이 필요하다.
  • Lighthouse 또는 실제 사용자 필드 데이터로 LCP/INP/CLS를 측정했다 (§1)
  • 긴 목록에는 페이지네이션·무한 스크롤·가상 스크롤 중 데이터 성격에 맞는 것을 선택했다 (§3~5)
  • 딥 페이지네이션이 필요한 곳은 offset 대신 cursor 방식을 검토했다 (§3)
  • 검색·리사이즈 등 연속 이벤트에 디바운스/스로틀을 적용했다 (§6)
  • React DevTools Profiler로 불필요한 리렌더링을 확인한 뒤 state 위치부터 재검토했다 (§7)
  • memo/useMemo/useCallback을 측정 없이 습관적으로 남발하지 않았다 (§7)
  • 중첩 루프(N+1)를 Map 인덱싱으로 대체할 수 있는지 확인했다 (§8)
  • 코드 스플리팅으로 초기 번들에서 불필요한 페이지 코드를 뺐다 (§9)
  • 이미지에 width/height 또는 aspect-ratio를 지정해 CLS를 방지했다 (§9)
  • useEffect의 이벤트 리스너/타이머에 정리(cleanup) 함수를 빠짐없이 작성했다 (§10)

이해도 점검

  • LCP, INP, CLS가 각각 무엇을 측정하는지 한 문장으로 설명할 수 있다
  • transform/opacity만 바꾸면 왜 Layout·Paint를 건너뛰는지 설명할 수 있다
  • offset 페이지네이션이 뒤 페이지로 갈수록 느려지는 이유를 설명할 수 있다
  • 무한 스크롤이 접근성/SEO에서 불리한 이유 두 가지를 말할 수 있다
  • 고정 높이 가상 스크롤에서 startIndex를 어떻게 계산하는지 설명할 수 있다
  • 디바운스와 스로틀의 차이를 타임라인으로 그릴 수 있다
  • React.memo를 붙이기 전에 먼저 시도해야 할 것이 무엇인지 안다
  • Array.includes 대신 Set.has를 쓰면 왜 빨라지는지 Big-O로 설명할 수 있다
  • LRU 캐시가 Map의 어떤 성질을 이용하는지 설명할 수 있다
  • 메모리 누수의 흔한 원인 4가지를 말할 수 있다
