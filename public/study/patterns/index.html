CH 01상태 설계 L1

프론트엔드에서 "객체 설계"란 사실상 상태를 어떻게 놓느냐다. 버그의 상당수가 상태 구조에서 시작한다. React 공식 결론은 한 줄이다 — "Make your state as simple as it can be — but no simpler."[1]

CH 02Effect — 대부분은 필요 없다 L1

공식 판별 질문[2] "이 코드는 컴포넌트가 표시되었기 때문에 실행되어야 하는가, 아니면 특정 상호작용 때문에 실행되어야 하는가?"
상호작용 때문 → 이벤트 핸들러. 표시 때문 → Effect.
Effect는 "외부 시스템과 동기화"할 때만 쓴다. React 바깥(DOM API, 네트워크, 타이머, 구독)이 외부 시스템이다.
상황해결
계산 가능한 값렌더링 중 계산
비용이 큰 계산useMemo
props 변경 시 전체 리셋key
props 변경 시 일부 조정렌더 중 조정 또는 key
사용자 이벤트에 대한 반응이벤트 핸들러
외부 시스템 동기화✅ Effect

CH 03비동기 안전성 L1

여기가 실무 버그의 진원지다. 해피패스는 누구나 짠다. 겹치고, 늦게 오고, 두 번 눌리는 상황이 실력이다.

3-1. 경쟁 상태 (race condition) ⭐

언제 터지나 검색어를 ab → abc로 빠르게 바꾸면 요청이 두 개 나간다. ab의 응답이 abc보다 늦게 도착하면 화면에는 ab의 결과가 남는다.
사용자는 abc를 입력했는데 ab 결과를 본다. 재현이 어렵고, 느린 네트워크에서만 난다.
BAD
useEffect(() => {
  fetchResults(query).then(setResults);   // 응답 순서를 보장하지 않는다
}, [query]);
GOOD ① — 공식 ignore 패턴[2]
useEffect(() => {
  let ignore = false;

  fetchResults(query).then(json => {
    if (!ignore) setResults(json);      // 최신 요청만 반영
  });

  return () => { ignore = true; };      // 이전 effect의 결과는 버린다
}, [query]);
GOOD ② — AbortController (요청 자체를 취소)
useEffect(() => {
  const ac = new AbortController();

  (async () => {
    try {
      const res  = await fetch(`/api/search?q=${query}`, { signal: ac.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      setResults(await res.json());
    } catch (e) {
      if ((e as Error).name === 'AbortError') return;   // 취소는 에러가 아니다
      setError(e as Error);
    }
  })();

  return () => ac.abort();
}, [query]);
두 방법의 차이 — 반드시 구분할 것 ignore · 응답을 무시만 한다. 네트워크 요청은 끝까지 진행된다. 구현이 단순하다.
AbortController · 요청 자체를 끊는다. 서버 부하·대역폭을 아낀다. 취소 에러를 걸러내는 처리가 필수(안 그러면 화면에 "실패" 표시가 뜬다).
선택 기준 — UI 정합성만 필요하면 ignore, 요청 비용까지 아껴야 하면 AbortController.

3-3. 디바운스 · 스로틀

function useDebounced<T>(value: T, delay = 300): T {
  const [v, setV] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setV(value), delay);
    return () => clearTimeout(id);     // 입력이 이어지면 이전 타이머 취소
  }, [value, delay]);
  return v;
}

const [input, setInput] = useState('');
const query = useDebounced(input, 300);   // query가 바뀔 때만 요청
기법동작쓰는 곳
디바운스멈춘 뒤 한 번 실행검색어 입력, 자동저장, 리사이즈 종료 감지
스로틀일정 간격마다 최대 1회스크롤 위치 추적, 마우스 이동, 무한스크롤 트리거

3-4. 재시도 — 아무거나 재시도하면 안 된다

function isRetryable(e: unknown): boolean {
  if (e instanceof TypeError) return true;             // 네트워크 단절
  if (e instanceof HttpError) {
    if (e.status === 429) return true;                 // 요청 과다
    if (e.status >= 500)   return true;                // 서버 오류
    return false;                                      // 4xx는 재시도해도 똑같다
  }
  return false;
}

async function withRetry<T>(fn: () => Promise<T>, max = 3): Promise<T> {
  for (let i = 0; i < max; i++) {
    try { return await fn(); }
    catch (e) {
      if (!isRetryable(e) || i === max - 1) throw e;
      await sleep(2 ** i * 300 + Math.random() * 100); // 지수 백오프 + 지터
    }
  }
  throw new Error('unreachable');
}

CH 04서버 상태 — TanStack Query L2

핵심 개념 서버 상태는 클라이언트 상태와 다른 물건이다. 내가 소유하지 않고, 언제든 남이 바꾸고, 항상 낡을 수 있다. 그래서 useState로 관리하면 캐시·재검증·중복요청·에러 재시도를 전부 직접 짜게 된다.

4-1. 쿼리 키 설계

// 키는 "이 데이터를 무엇이 결정하는가"를 그대로 적는다
const itemKeys = {
  all:    ['items'] as const,
  lists:  ()                        => [...itemKeys.all, 'list'] as const,
  list:   (q: string, page: number) => [...itemKeys.lists(), { q, page }] as const,
  detail: (id: string)              => [...itemKeys.all, 'detail', id] as const,
};

useQuery({
  queryKey: itemKeys.list(query, page),
  queryFn:  () => fetchItems(query, page),
});
왜 팩토리로 묶나 — invalidateQueries({ queryKey: itemKeys.all }) 한 줄로 목록·상세를 한꺼번에 무효화할 수 있다. 키 문자열이 코드 곳곳에 흩어져 있으면 무효화 범위를 통제할 수 없다.

4-2. staleTime vs gcTime — 반드시 구분

옵션뜻지나면
staleTime이 시간 동안은 데이터가 신선하다고 간주다음 트리거(마운트·포커스·재연결) 때 백그라운드 refetch
gcTime아무 컴포넌트도 안 쓰는 캐시를 메모리에 두는 시간캐시에서 삭제
useQuery({
  queryKey: itemKeys.list(query, page),
  queryFn:  () => fetchItems(query, page),
  staleTime: 30_000,      // 30초간 재요청 안 함 (화면 전환해도 즉시 표시)
  gcTime:  5 * 60_000,    // 안 쓰이면 5분 뒤 메모리에서 제거
});
흔한 오해 — "staleTime을 0으로 두면 캐시가 없다"가 아니다. 캐시는 있고 즉시 낡은 것으로 취급할 뿐이다. 그래서 화면에는 캐시가 먼저 보이고 뒤에서 갱신된다(stale-while-revalidate).

4-3. 뮤테이션 후 갱신 3가지

방법쓸 때비용
invalidateQueries기본값. 서버가 진실요청 1회 추가
setQueryData응답에 갱신된 데이터가 통째로 올 때요청 0회
낙관적 업데이트즉각 반응이 중요할 때(좋아요·수량)롤백 로직 필요
GOOD — 낙관적 업데이트 + 롤백
const qc = useQueryClient();

useMutation({
  mutationFn: updateQty,

  onMutate: async (next) => {
    await qc.cancelQueries({ queryKey: cartKey });          // ① 진행 중 refetch 취소
    const prev = qc.getQueryData(cartKey);                  // ② 롤백용 스냅샷
    qc.setQueryData(cartKey, (old) => applyQty(old, next)); // ③ 화면 먼저 반영
    return { prev };                                        // ④ context로 전달
  },

  onError: (_err, _next, ctx) => {
    qc.setQueryData(cartKey, ctx.prev);                     // ⑤ 실패 → 되돌림
  },

  onSettled: () => {
    qc.invalidateQueries({ queryKey: cartKey });            // ⑥ 성공/실패 무관 최종 동기화
  },
});
①을 빼먹으면 롤백이 깨진다. 진행 중이던 refetch가 나중에 도착해서 낙관적으로 바꾼 값을 옛 서버 데이터로 덮어쓴다. 가장 많이 빠뜨리는 줄이다.

GOOD
function ItemList({ query }: { query: string }) {

CH 05에러 처리 L2

5-1. Error Boundary가 못 잡는 것

반드시 외울 것 ❌ 이벤트 핸들러 · ❌ 비동기 코드(setTimeout, fetch 후속) · ❌ SSR · ❌ 자기 자신에서 난 에러
✅ 잡는 것: 렌더링 중 / 생명주기 / 하위 트리 생성자에서 던져진 에러

그래서 Error Boundary 하나로 모든 에러가 잡히지 않는다. 3층으로 나눠야 한다.
// React에서 class를 쓰는 사실상 유일한 곳
class ErrorBoundary extends React.Component<Props, { error: Error | null }> {
  state = { error: null as Error | null };

  static getDerivedStateFromError(error: Error) { return { error }; }  // 화면 전환

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportToServer(error, info.componentStack);                        // 로깅
  }

  render() {
    if (this.state.error) {
      return <Fallback onReset={() => this.setState({ error: null })} />;
    }
    return this.props.children;
  }
}

5-2. 3층 에러 처리 설계

① 쿼리 · 뮤테이션 레벨

재시도 가능한 네트워크 에러. 화면에 재시도 버튼을 준다. 사용자가 복구할 수 있는 에러.

② 이벤트 핸들러

사용자 행동의 실패(폼 제출 등). try/catch + 토스트. Error Boundary가 못 잡는 영역.

③ Error Boundary

예상 못 한 렌더링 에러. 화면이 하얗게 되는 것을 막는 최후 방어선. 로깅이 주 임무.

BAD

GOOD

6-1. 언제 다시 그려지나

원인범위
자기 상태 변경자신 + 하위 전체
부모 리렌더props가 안 바뀌어도 자식은 다시 그려진다

"다시 그려진다" = 함수가 다시 실행된다는 뜻이지 DOM이 바뀐다는 뜻이 아니다. React는 결과를 비교해서 실제로 달라진 DOM만 건드린다. 그래서 리렌더 자체가 항상 문제인 건 아니다.

7-1. 이벤트 루프 — 실행 순서

규칙 — 콜 스택이 비면 마이크로태스크 큐를 전부 비운 뒤 매크로태스크를 하나 꺼낸다. 그래서 Promise.then은 setTimeout(…, 0)보다 항상 먼저다.

CH 09TypeScript 타입 설계 L2

타입은 문법이 아니라 설계다. 목표는 "에러를 없애는 것"이 아니라 "잘못된 코드를 못 쓰게 만드는 것"이다.

9-1. any 대신 unknown

BAD
function handle(e: any) {
  console.log(e.message.toUpperCase());   // e가 문자열이면 런타임 폭발. 타입 검사 없음.
}
GOOD
function handle(e: unknown) {
  if (e instanceof Error) console.log(e.message.toUpperCase());  // 좁힌 뒤에만 접근
  else console.log('Unknown error', e);
}
any는 타입 검사를 끄는 것이고, unknown은 검사를 강제하는 것이다. 외부에서 들어오는 값(JSON, catch, 라이브러리 경계)은 전부 unknown에서 시작한다.

9-2. 타입 좁히기 (narrowing)

function f(x: string | number | null) {
  if (x === null) return;              // null 제거
  if (typeof x === 'string') {
    x.toUpperCase();                   // 여기서 x는 string
    return;
  }
  x.toFixed(2);                        // 여기서 x는 number
}

// 사용자 정의 타입 가드
function isUser(v: unknown): v is User {
  return typeof v === 'object' && v !== null && 'id' in v;
}

10-1. 멱등키 (idempotency key) ⭐

문제 결제 요청을 보냈는데 응답이 안 왔다. 성공했는지 실패했는지 클라이언트는 알 수 없다.
재시도하면 이중 결제, 안 하면 결제 누락. 양쪽 다 사고다.
function createOrderRequest(cart: Cart): OrderRequest {
  return {
    idempotencyKey: crypto.randomUUID(),   // ① 요청 생성 시점에 딱 한 번 발급
    items: cart.items,
  };
}

async function submitOrder(req: OrderRequest, max = 3) {
  for (let i = 0; i < max; i++) {
    try {
      // ② 재시도해도 같은 키를 보낸다
      //    → 서버는 이미 처리한 키면 새로 처리하지 않고 같은 결과를 돌려준다
      return await api.post('/orders', req);
    } catch (e) {
      if (!isRetryable(e) || i === max - 1) throw e;
      await sleep(2 ** i * 300);
    }
  }
}
핵심은 ①이다. 재시도할 때마다 키를 새로 만들면 서버는 다른 요청으로 보고 또 처리한다. "요청 1건 = 키 1개"를 유지하는 것이 멱등성의 전부다.

10-2. 오프라인 큐

// 단절 감지 → IndexedDB에 적재 → 복구되면 순서대로 전송
async function enqueue(req: OrderRequest) {
  await idb.add('outbox', { ...req, createdAt: Date.now() });
}

async function flush() {
  const pending = await idb.getAllSorted('outbox', 'createdAt');  // 순서 보장
  for (const req of pending) {
    await submitOrder(req);                       // 멱등키 덕분에 중복 전송이 안전
    await idb.delete('outbox', req.idempotencyKey);
  }
}

window.addEventListener('online',  flush);
window.addEventListener('offline', () => setMode('offline'));

async function placeOrder(cart: Cart) {
  const req = createOrderRequest(cart);
  if (!navigator.onLine) { await enqueue(req); return { queued: true }; }
  try { return await submitOrder(req); }
  catch { await enqueue(req); return { queued: true }; }   // 실패해도 유실 없음
}
navigator.onLine은 완전하지 않다. "랜선은 꽂혀 있는데 인터넷은 안 되는" 상태를 못 잡는다. 그래서 실제 요청 실패도 큐로 보내는 위 구조가 필요하다.

CH 11설계 원칙 L2

11-1. 언제 추상화하나 — Rule of Three

1번째   그냥 짠다
2번째   중복이 보여도 참는다 (그대로 복사)
3번째   이제 뽑는다
왜 2번째에 안 뽑나 — 사례가 2개뿐이면 무엇이 변하는 축인지 알 수 없다. 잘못된 축으로 자른 추상화는 되돌리는 비용이 처음부터 안 만든 것보다 크다.

11-2. YAGNI — 미리 만들면 드는 4가지 비용[4]

Cost of build

분석·구현·테스트에 들어간 시간

Cost of delay

그거 만드느라 더 중요한 걸 늦게 냈다

Cost of carry

코드가 복잡해져서 이후 모든 개발이 느려진다

Cost of repair

나중에 실제 필요할 때 방식이 안 맞아 갚아야 하는 빚

원문: "yagni only applies when you introduce extra complexity now"
→ 복잡도를 늘리지 않는 리팩터링 · 테스트 작성 · 배포 자동화는 YAGNI 대상이 아니다. 이건 오히려 먼저 해야 한다.

type OrderHooks = {
  beforeOrder?:  (o: Order)   => Promise<void>;
  afterOrder?:   (o: Order)   => Promise<void>;
  afterPayment?: (p: Payment) => Promise<void>;
};

async function runOrder(order: Order, plugins: OrderHooks[]) {
  for (const p of plugins) await p.beforeOrder?.(order);
  const payment = await pay(order);                  // ← 코어. 기능이 늘어도 안 바뀐다
  for (const p of plugins) await p.afterPayment?.(payment);
  return payment;
}

11-5. 폴더 구조 — 기준을 말할 수 있어야 한다

방식구조적합
타입 기준components/ hooks/ utils/소규모. 커지면 한 기능이 3~4곳에 흩어진다
도메인 기준features/order/ features/cart/대부분의 경우. 기능 단위로 삭제·이동이 쉽다
정답은 없지만 "기준 없음"은 오답이다. 어떤 기준을 썼고 왜 그랬는지 한 문장으로 말할 수 있으면 된다.
자가 점검 · CH11
  1. 중복을 두 번째로 봤을 때 바로 추상화하지 않는 이유는?
  2. YAGNI가 적용되지 않는 작업은 무엇인가?
  3. "기능을 추가하는데 기존 코드를 안 고친다"를 가능하게 하는 구조는?
  4. 커스텀 훅이 잘못 설계됐다는 신호 하나는?
답 보기
  1. 사례 2개로는 무엇이 변하는 축인지 판단할 수 없다. 잘못 자른 추상화는 되돌리는 비용이 더 크다.
  2. 지금 복잡도를 늘리지 않는 것 — 리팩터링, 자동 테스트, 배포 자동화. 원문이 "extra complexity를 지금 도입할 때만 적용된다"고 못 박고 있다.
  3. 확장점(훅·플러그인·슬롯)을 코어에 정의하고, 새 기능은 그 확장점에 붙인다. 코어는 안 바뀐다.
  4. setState를 그대로 반환한다. 내부 구현이 밖으로 새어 캡슐화가 없다는 뜻이다.

12-1. 코드리뷰 대원칙[6]

"Reviewers should favor approving a CL once it is in a state where it definitely improves the overall code health, even if it isn't perfect."
완벽한 코드는 없다. 더 나은 코드만 있다. 리뷰의 목적은 흠집 찾기가 아니라 코드 건강도를 올리는 것.

12-2. 무엇을 어떤 순서로 보나 — 8항목[5]

순서가 곧 중요도다. 초보 리뷰어는 7번(스타일)부터 보고, 실력 있는 리뷰어는 1번(설계)부터 본다. 설계가 틀렸으면 나머지는 볼 필요가 없다.
