§1T0기본 — 여기서 사고가 난다

여기 있는 건 전부 실제 코드에서 반복적으로 터지는 지점이다. 개념 설명이 아니라 동작하는 코드를 손에 붙인다는 마음으로 본다.

1-1. 상태 구조 5원칙 — React 공식[4]

React 공식 결론: "Make your state as simple as it can be — but no simpler." FE에서 "객체 설계"란 사실상 이 5개다.

① 관련된 상태는 묶는다

BAD
const [x, setX] = useState(0);
const [y, setY] = useState(0);   // 항상 같이 바뀌는데 따로 관리 → 동기화 누락
GOOD
const [position, setPosition] = useState({ x: 0, y: 0 });

② 모순되는 상태를 없앤다 ⭐ 가장 중요

BAD
const [isSending, setIsSending] = useState(false);
const [isSent,    setIsSent]    = useState(false);
// 둘 다 true인 "불가능한 상태"가 만들어질 수 있다
GOOD
type Status = 'typing' | 'sending' | 'sent';
const [status, setStatus] = useState<Status>('typing');

const isSending = status === 'sending';   // 파생값은 계산으로
이게 왜 "TypeScript 정적 타입 분석" 자격요건의 실전 형태인가 자격요건 원문이 "TypeScript, Flow를 이용한 정적 타입 분석" 이다. 문법을 아는 게 아니라 불가능한 상태를 타입으로 표현 불가능하게 만드는 것이 그 뜻이다. 아래 판별 유니온이 그 도구다.
BAD — 8가지 조합 중 5개가 불가능
interface State {
  isLoading: boolean;
  error: Error | null;
  data: User | null;
}
// isLoading:true + data:있음 + error:있음 ← 말이 안 되는데 타입이 허용한다
GOOD — 판별 유니온(discriminated union)
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error';   error: Error }
  | { status: 'success'; data: User };

function View({ state }: { state: State }) {
  switch (state.status) {
    case 'idle':    return <Empty />;
    case 'loading': return <Skeleton />;
    case 'error':   return <Retry error={state.error} />;  // error 접근 안전
    case 'success': return <Profile user={state.data} />;  // data 접근 안전
  }
}
이렇게 설명한다 "왜 이 타입이 이렇게 생겼나요?" → "불가능한 조합이 만들어지지 않게 판별 유니온으로 묶었습니다. status가 success일 때만 data가 존재하도록 타입이 보장합니다." — 여기서 점수가 크게 뛴다.

③ 중복 상태를 없앤다 — 계산 가능한 건 저장하지 않는다

BAD
const [firstName, setFirstName] = useState('');
const [lastName,  setLastName]  = useState('');
const [fullName,  setFullName]  = useState('');   // 중복!

useEffect(() => { setFullName(firstName + ' ' + lastName); }, [firstName, lastName]);
// 불필요한 리렌더가 한 번 더 발생한다
GOOD
const [firstName, setFirstName] = useState('');
const [lastName,  setLastName]  = useState('');
const fullName = firstName + ' ' + lastName;   // 렌더링 중 계산

④ 복제를 피한다 — 객체 말고 id를 저장

BAD
const [items, setItems] = useState(initial);
const [selectedItem, setSelectedItem] = useState(initial[0]);
// items를 수정하면 selectedItem은 옛날 객체를 들고 있다 → 화면 불일치
GOOD
const [items, setItems] = useState(initial);
const [selectedId, setSelectedId] = useState<string | null>(null);
const selectedItem = items.find(i => i.id === selectedId) ?? null;

⑤ 깊은 중첩을 피한다 — 평탄화(normalize)

// DB 테이블처럼 id를 키로 눕힌다
const [nodes, setNodes] = useState<Record<string, Node>>({
  '0': { id: '0', title: 'Earth',  childIds: ['1','2'] },
  '1': { id: '1', title: 'Africa', childIds: [] },
});

props를 state로 복사하지 마라

BAD
function Message({ color }) {
  const [c, setC] = useState(color);   // color가 바뀌어도 c는 안 바뀐다
}
GOOD — 정말 무시하고 싶을 때만, 이름으로 의도를 밝힌다
function Message({ initialColor }) {          // initial/default 접두사
  const [color, setColor] = useState(initialColor);
}

1-2. Effect가 필요 없는 경우 — React 공식[5]

공식 판별 질문 (원문) "이 코드는 컴포넌트가 표시되었기 때문에 실행되어야 하는가, 아니면 특정 상호작용 때문에 실행되어야 하는가?"
상호작용 때문이면 → 이벤트 핸들러. 표시 때문이면 → Effect.
상황해결
계산 가능한 값렌더링 중 계산 (Effect 아님)
비용이 큰 계산useMemo
props 변경 시 전체 리셋key
props 변경 시 일부 조정렌더 중 조정 또는 key
사용자 이벤트에 대한 반응이벤트 핸들러
외부 시스템 동기화✅ Effect
데이터 페칭✅ Effect (cleanup 필수)

props 변경 시 상태 리셋 → key를 쓴다

BAD
function ProfilePage({ userId }) {
  const [comment, setComment] = useState('');
  useEffect(() => { setComment(''); }, [userId]);   // 렌더가 한 번 더 돈다
}
GOOD
export default function ProfilePage({ userId }) {
  return <Profile userId={userId} key={userId} />;   // key가 바뀌면 상태 자동 초기화
}
function Profile({ userId }) {
  const [comment, setComment] = useState('');
}

Effect 체인 금지

BAD — 상태가 상태를 깨우는 도미노
useEffect(() => { setGoldCount(...) }, [card]);
useEffect(() => { setRound(...) },     [goldCount]);
useEffect(() => { setIsOver(...) },    [round]);
// 매 단계마다 리렌더. 디버깅 불가.
GOOD — 이벤트 핸들러에서 한 번에
const isGameOver = round > 5;                  // 파생값은 렌더 중 계산

function handlePlaceCard(nextCard) {
  setCard(nextCard);
  if (nextCard.gold) {
    if (goldCount < 3) setGoldCount(goldCount + 1);
    else { setGoldCount(0); setRound(round + 1); }
  }
}

1-3. 경쟁 상태(race condition) ⭐ 가장 많이 놓치는 버그

언제 터지나 검색어를 ab → abc 로 빠르게 바꾸면 요청이 두 개 나간다. ab의 응답이 abc보다 늦게 도착하면 화면에 ab 결과가 남는다. 검색·필터·자동완성이 나오는 과제라면 반드시 검사한다.
GOOD — React 공식 ignore 패턴[5]
useEffect(() => {
  let ignore = false;

  fetchResults(query).then(json => {
    if (!ignore) setResults(json);      // 최신 요청만 반영
  });

  return () => { ignore = true; };      // 이전 요청의 결과는 버린다
}, [query]);
GOOD — AbortController (네트워크까지 실제로 취소)
useEffect(() => {
  const ac = new AbortController();

  (async () => {
    try {
      const res  = await fetch(`/api/search?q=${query}`, { signal: ac.signal });
      const json = await res.json();
      setResults(json);
    } catch (e) {
      if ((e as Error).name === 'AbortError') return;   // 취소는 에러가 아니다
      setError(e as Error);
    }
  })();

  return () => ac.abort();
}, [query]);
두 방법의 차이 ignore: 응답을 무시만 한다. 네트워크 요청은 그대로 진행된다. 간단하다.
AbortController: 요청 자체를 취소한다. 서버 부하와 대역폭을 아낀다. 취소 에러를 걸러내는 처리가 필수.
→ 답변: "UI 정합성만 필요하면 ignore, 요청 비용까지 아껴야 하면 AbortController를 씁니다."

1-4. 상태 3종 — 로딩 / 에러 / 빈 상태

가장 흔한 탈락 사유 이 3개가 없으면 "해피패스만 짰다"로 읽힌다. 기능 개수보다 이게 먼저다.
GOOD
function ItemList({ query }: { query: string }) {
  const { data, isPending, isError, error, refetch } = useItems(query);

  if (isPending) return <Skeleton rows={5} />;                    // ① 로딩
  if (isError)   return <ErrorState msg={error.message} onRetry={refetch} />; // ② 에러 + 재시도
  if (data.length === 0) return <EmptyState query={query} />;     // ③ 빈 상태

  return <ul>{data.map(i => <Row key={i.id} item={i} />)}</ul>;
}
빈 상태는 "결과 0건"과 "아직 검색 안 함"을 구분해야 한다. 둘을 같은 화면으로 처리하면 지적당한다.

1-5. 중복 제출 방지

BAD
<button onClick={submit}>주문</button>
// 더블클릭 → 주문 2건. 결제 도메인에서는 사고다.
GOOD
const [status, setStatus] = useState<'idle'|'submitting'>('idle');

async function submit() {
  if (status === 'submitting') return;      // 가드
  setStatus('submitting');
  try { await createOrder(payload); }
  finally { setStatus('idle'); }            // 실패해도 반드시 푼다
}

<button onClick={submit} disabled={status === 'submitting'}>
  {status === 'submitting' ? '처리 중…' : '주문'}
</button>
실무 정답은 여기서 한 단계 더 간다 — 프론트 가드는 새로고침·네트워크 재시도를 못 막는다. 그래서 멱등키를 같이 보낸다. → §3-1

1-6. 디바운스

function useDebounced<T>(value: T, delay = 300): T {
  const [v, setV] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setV(value), delay);
    return () => clearTimeout(id);          // 입력이 계속되면 이전 타이머 취소
  }, [value, delay]);
  return v;
}

// 사용
const [input, setInput] = useState('');
const query = useDebounced(input, 300);     // query가 바뀔 때만 요청
디바운스 vs 스로틀 — 디바운스는 멈춘 뒤 한 번(검색어 입력), 스로틀은 일정 간격마다(스크롤·리사이즈). 선택 이유를 물어본다.

1-7. React Query — 서버 상태

쿼리 키 설계

// 키는 "이 데이터를 무엇이 결정하는가"를 그대로 적는다
const itemKeys = {
  all:    ['items'] as const,
  list:   (q: string, page: number) => [...itemKeys.all, 'list', { q, page }] as const,
  detail: (id: string)              => [...itemKeys.all, 'detail', id] as const,
};

useQuery({ queryKey: itemKeys.list(query, page), queryFn: () => fetchItems(query, page) });
왜 팩토리로 묶나 — invalidateQueries({ queryKey: itemKeys.all }) 한 줄로 목록·상세를 한꺼번에 무효화할 수 있다. 키 문자열이 흩어져 있으면 무효화 범위를 통제 못 한다.

staleTime vs gcTime — 반드시 구분해서 답할 것

옵션뜻지나면
staleTime이 시간 동안은 신선하다고 간주다음 트리거(포커스·마운트) 때 백그라운드 refetch
gcTime아무도 안 쓰는 캐시를 메모리에 두는 시간캐시에서 삭제
useQuery({
  queryKey: itemKeys.list(query, page),
  queryFn:  () => fetchItems(query, page),
  staleTime: 30_000,   // 30초 동안은 재요청 안 함
  gcTime:  5 * 60_000, // 안 쓰이면 5분 뒤 캐시 제거
});

뮤테이션 후 갱신 3가지 — 언제 뭘 쓰나

방법쓸 때
invalidateQueries기본값. 서버가 진실. 다시 받아온다
setQueryData응답에 갱신된 데이터가 통째로 올 때. 요청 1회 절약
낙관적 업데이트즉각 반응이 중요할 때(좋아요·수량). 실패 시 롤백 필수
GOOD — 낙관적 업데이트 + 롤백 (공식 패턴)
const qc = useQueryClient();

useMutation({
  mutationFn: updateQty,

  onMutate: async (next) => {
    await qc.cancelQueries({ queryKey: cartKey });      // ① 진행 중 refetch 취소
    const prev = qc.getQueryData(cartKey);              // ② 되돌릴 스냅샷 확보
    qc.setQueryData(cartKey, (old) => applyQty(old, next)); // ③ 화면 먼저 반영
    return { prev };                                    // ④ context로 넘김
  },

  onError: (_err, _next, ctx) => {
    qc.setQueryData(cartKey, ctx.prev);                 // ⑤ 실패 → 롤백
  },

  onSettled: () => {
    qc.invalidateQueries({ queryKey: cartKey });        // ⑥ 성공/실패 무관 최종 동기화
  },
});
①번을 빼먹으면 롤백이 깨진다. 진행 중이던 refetch가 나중에 도착해 옛 데이터를 덮어쓴다. 실무에서 자주 새는 지점이다.

1-8. 에러 경계 (Error Boundary)

Error Boundary가 못 잡는 것 — 반드시 외울 것 ❌ 이벤트 핸들러 · ❌ 비동기 코드(setTimeout, fetch 후속) · ❌ SSR · ❌ 자기 자신에서 난 에러
✅ 잡는 것: 렌더링 중 / 생명주기 / 하위 트리 생성자에서 던져진 에러 
// React에서 class를 쓰는 사실상 유일한 곳
class ErrorBoundary extends React.Component<Props, { error: Error | null }> {
  state = { error: null as Error | null };

  static getDerivedStateFromError(error: Error) { return { error }; }  // 화면 전환

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportToServer(error, info.componentStack);                        // 로깅
  }

  render() {
    if (this.state.error) return <Fallback onReset={() => this.setState({ error: null })} />;
    return this.props.children;
  }
}
답변 설계 — "에러는 어디서 잡나요?" 3층으로 나눠 답한다.
① 쿼리/뮤테이션 레벨 — 재시도 가능한 네트워크 에러. 화면에 재시도 버튼
② 이벤트 핸들러 — 사용자 행동 실패(폼 제출 등). try/catch + 토스트
③ Error Boundary — 예상 못 한 렌더링 에러. 화면이 하얗게 되는 걸 막는 최후 방어선

§2T1심화 — 여기서 실력 차가 난다

2-1. 리렌더 — 언제 다시 그려지나

원인범위
자기 상태 변경자신 + 하위 전체
부모 리렌더props가 안 바뀌어도 자식은 다시 그려진다
구독 중인 Context 값 변경그 Context를 쓰는 모든 컴포넌트

상태를 아래로 내려서 리렌더를 줄인다 (memo보다 먼저 시도할 것)

BAD — 입력할 때마다 무거운 목록까지 다시 그려짐
function Page() {
  const [text, setText] = useState('');
  return (<>
    <input value={text} onChange={e => setText(e.target.value)} />
    <HeavyList />

}
GOOD — 상태를 쓰는 곳으로 내린다
function SearchBox() {                     // 상태를 여기 가둔다
  const [text, setText] = useState('');
  return <input value={text} onChange={e => setText(e.target.value)} />;
}
function Page() {
  return (<><SearchBox /><HeavyList /></>);   // HeavyList는 이제 안 그려짐
}

children으로 넘기기 — 리렌더 격리 기법

function Wrapper({ children }) {
  const [n, setN] = useState(0);
  return <div onClick={() => setN(n + 1)}>{children}</div>;
}
// <Wrapper><Heavy /></Wrapper>
// Heavy는 부모(Page)에서 만들어진 엘리먼트라 Wrapper가 리렌더돼도 재생성되지 않는다

2-2. memo / useMemo / useCallback — 언제 쓰면 안 되나

흔한 함정 "성능 최적화했다"의 근거가 "memo를 붙였다"뿐이라면 최적화가 아니다.
기준은 "Profiler로 재고, 실제로 느린 커밋이 있을 때만 붙인다."
도구쓸 때쓰면 안 될 때
React.memoprops가 잘 안 바뀌는 무거운 컴포넌트props가 매번 바뀜(객체·함수 리터럴) → 비교 비용만 추가
useMemo계산이 실제로 비쌀 때 / 참조 동일성이 필요할 때단순 계산. 메모 비용 > 계산 비용
useCallbackmemo된 자식에 콜백을 넘길 때 / effect 의존성일 때그냥 DOM 핸들러
memo는 부모가 넘기는 props가 안정적일 때만 효과가 있다. 부모에서 onClick={() => ...} 를 인라인으로 넘기면 memo는 무력화된다. 이 인과를 설명할 수 있어야 한다.

3-1. 멱등키 (idempotency key) ⭐

문제 결제 요청을 보냈는데 응답이 안 왔다. 성공했는지 실패했는지 클라이언트는 모른다. 재시도하면 이중 결제, 안 하면 결제 누락. 둘 다 사고다.
// 해결: "이 요청은 같은 요청이다"를 서버가 알아볼 수 있게 키를 붙인다
function createOrderRequest(cart: Cart) {
  return {
    idempotencyKey: crypto.randomUUID(),   // ① 요청 생성 시점에 1회만 발급
    items: cart.items,
  };
}

async function submitOrder(req: OrderRequest, retries = 3) {
  for (let i = 0; i < retries; i++) {
    try {
      // ② 재시도해도 같은 키를 보낸다 → 서버는 최초 1건만 처리하고 같은 결과를 돌려준다
      return await api.post('/orders', req);
    } catch (e) {
      if (!isRetryable(e) || i === retries - 1) throw e;
      await sleep(2 ** i * 300);           // ③ 지수 백오프
    }
  }
}
핵심은 ①이다. 키를 재시도할 때마다 새로 만들면 아무 의미가 없다. "요청 1건 = 키 1개"를 유지하는 게 멱등성이다.

3-2. 오프라인 큐

// 단절 감지 → IndexedDB에 적재 → 복구되면 순서대로 전송
async function enqueue(req: OrderRequest) {
  await idb.add('outbox', { ...req, createdAt: Date.now() });
}

async function flush() {
  const pending = await idb.getAllSorted('outbox', 'createdAt');  // 순서 보장
  for (const req of pending) {
    await submitOrder(req);        // 멱등키 덕분에 중복 전송이 안전하다
    await idb.delete('outbox', req.idempotencyKey);
  }
}

window.addEventListener('online',  flush);
window.addEventListener('offline', () => setMode('offline'));

async function placeOrder(cart: Cart) {
  const req = createOrderRequest(cart);
  if (!navigator.onLine) { await enqueue(req); return { queued: true }; }
  try { return await submitOrder(req); }
  catch { await enqueue(req); return { queued: true }; }   // 실패해도 유실 없음
}
localStorage로 하면 안 되는 이유 — 동기 API라 메인 스레드를 막고, 문자열만 저장되며, 용량이 작다(~5MB). IndexedDB는 비동기 + 구조화된 데이터 + 인덱스 조회가 된다. 이 구분을 말할 수 있어야 한다.

contextBridge.exposeInMainWorld('api', {

#항목보는 것

실력 있는 리뷰어는 1번(설계)부터 본다. 설계가 틀렸으면 나머지는 볼 필요가 없다.
리뷰를 받는 쪽도 이 순서를 알고 있어야 한다. 1~3번이 지적되면 나머지는 볼 필요가 없다.

§6설계 · 추상화

6-1. 언제 뽑나 — Rule of Three

1번째   그냥 짠다
2번째   중복이 보여도 참는다 (그대로 복사)
3번째   이제 뽑는다
왜 2번째에 안 뽑나 — 2개로는 무엇이 변하는 축인지 모른다. 잘못된 축으로 자르면 되돌리는 게 더 비싸다.

6-2. YAGNI — 미리 만들면 드는 4가지 비용 — Martin Fowler[7]

Cost of build

분석·구현·테스트에 들어간 시간

Cost of delay

그거 만드느라 더 중요한 걸 늦게 냈다

Cost of carry

코드가 복잡해져서 다른 기능 개발이 느려진다

Cost of repair

나중에 실제 필요할 때 방식이 안 맞아 갚아야 하는 빚

원문: "yagni only applies when you introduce extra complexity now"
→ 복잡도를 늘리지 않는 리팩터링·테스트 작성·배포 준비는 YAGNI 대상이 아니다.
"왜 이걸 추상화 안 했나?"에 대한 답 지금 한 번만 쓰이고, 어느 축으로 변할지 아직 모릅니다.
두 번째 사례가 나오면 그때 공통점이 뭔지 알 수 있습니다.
지금 뽑으면 잘못된 축으로 자를 위험이 있고, 되돌리는 비용이 더 큽니다.

6-3. SOLID를 FE 언어로

원칙FE에서
S단일 책임컴포넌트 하나가 데이터 로딩 + 표시 + 폼 검증을 다 하면 분리
O개방-폐쇄새 기능 추가에 기존 코드를 안 고치는 구조. → 플러그인 SDK 구조가 대표 사례
L리스코프 치환같은 인터페이스면 바꿔 끼워도 동작
I인터페이스 분리props 20개짜리 컴포넌트 → 쪼갠다
D의존성 역전fetch를 컴포넌트에 직접 박지 말고 주입 → 테스트 가능해진다

O(개방-폐쇄)의 실전 형태 — 훅 기반 확장점

// 코어를 안 건드리고 기능을 더한다 (결제 훅 + 플러그인 구조)
type OrderHooks = {
  beforeOrder?:   (o: Order) => Promise<void>;
  afterOrder?:    (o: Order) => Promise<void>;
  afterPayment?:  (p: Payment) => Promise<void>;
};

async function runOrder(order: Order, plugins: OrderHooks[]) {
  for (const p of plugins) await p.beforeOrder?.(order);
  const payment = await pay(order);                    // ← 코어. 절대 안 바뀐다
  for (const p of plugins) await p.afterPayment?.(payment);
  return payment;
}

// 포인트 적립, 영수증 발행, 알림 — 전부 플러그인으로 붙였다 뗀다
결제 도메인에서 반복적으로 나타나는 문제다. 제휴사마다 단말 종속 코드가 N개씩 늘어나는 구조를 플러그인 SDK로 "N×M 코드 → N개 코드"로 줄인다. OCP가 실무에서 값을 하는 대표적 지점이다.

§7성능 — 측정하고 줄이기

대원칙 측정하지 않은 최적화는 최적화가 아니다. "빨라졌다"에는 항상 "무엇을, 어떤 조건에서, 어떻게 쟀는가"가 붙어야 한다.

7-1. Core Web Vitals — 공식 수치 [8]

지표측정 대상Good개선 필요Poor
LCP로딩 성능≤ 2.5s2.5~4s> 4s
INP상호작용 반응성≤ 200ms200~500ms> 500ms

측정 도구 — 필드(실사용자): Chrome UX Report · PageSpeed Insights · Search Console / 랩(개발): Chrome DevTools · Lighthouse(LCP·CLS만)

⚠️ INP는 Lighthouse로 못 잰다. DevTools Performance 탭으로 잰다. 이걸 아는 게 "측정할 줄 안다"의 증거다.

7-3. ⭐ 큰 트래픽을 겪을 수 없을 때 — 만들어서 확인한다

규모가 없으면 규모를 만든다 사내 도구처럼 동시 사용자가 수십 명이면 부하가 안 걸려 병목이 드러나지 않는다.
→ 부하를 인위적으로 만들어서 재면 된다. 실제 대규모 운영은 아니지만 측정 절차는 똑같이 훈련된다.
① 데이터 부풀리기       목록 100건 → 10,000건 → 100,000건 생성
② 기기 조건 낮추기       DevTools → CPU 4x/6x slowdown, Network Fast 3G
③ 기준 측정(baseline)   같은 조건 3회 → 중앙값 기록
④ 한 번에 하나만 바꾼다   변수 하나씩
⑤ 재측정 + 기록          before/after 표로

기록 형식 (그대로 쓸 것)

조건: 10,000건 · CPU 4x slowdown · Chrome 12x · 3회 측정 중앙값
변경: 리스트 가상화 도입 (react-window)

지표              before      after
────────────────────────────────────
스크롤 최장 프레임   [X] ms     [Y] ms
INP                [X] ms     [Y] ms
DOM 노드 수        10,000      ~40

판단: 항목 [N]건을 넘어가면서 프레임 드랍이 체감됐다.
      그 이하에서는 가상화가 과한 최적화라고 판단해 도입하지 않았다.
핵심은 숫자의 크기가 아니라 절차다. 조건 고정 → 기준 측정 → 한 번에 하나만 변경 → 재측정. 이 절차가 몸에 붙으면 규모가 커져도 판단 방식은 그대로 쓴다.
